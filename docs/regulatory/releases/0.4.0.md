# MiniDAQ 0.4.0 release record

The record of SDP section 8 for release 0.4.0 (the book's Part IV). Evidence paths are relative
to this directory's parent, `docs/regulatory/`; the files are in `measurements/release-0.4.0/`
and were written by `tools/release_checks.sh` unless the notes below say otherwise. Checked with
Exercise 14.5's `check()` before the tag was made.

## Release

MiniDAQ 0.4.0, commit 61c2e1a92b17f43a04a3c86525198869a186ceea, tag book-v0.4.0

Part 1 of the release checks (builds, tests, static analysis, starters, stress run, coverage,
benchmarks) ran on this commit with a clean working tree (`commit.txt`). Part 2 (regression
gate, system tests, soak, fuzzing) ran on commit 67664957b612584730c9308747a917faa34cd78b
(`commit-part-2.txt`); between the two commits MiniDAQ's code changed only in comments and
tests, and the programs that part 2 tested are byte-identical to this commit's (notes below).
The release record, the version bump and the documents of this release are committed on top and
change no code.

Notes on the results:

- Build and tests: `ci/run_all.sh` built all six presets and ran 648 to 650 tests each (the count
  differs by preset because some tests exist only in some builds; the timing tests of exercise
  solutions skip in sanitizer builds by design). The documentation tests in the same run include
  `docs.trace` (149 requirements, 145 verified by tests and 4 by measurement), `docs.srs`,
  `docs.risk`, `docs.soup`, `docs.anomalies`, `docs.capa` and `docs.design_file`.
- Starters: every starter of the `Release` build fails at least one test and none hangs (CAPA-0004);
  Exercise 18.3's starter, which exists only in the coverage build, fails there and its solution
  passes (`coverage-exercise.txt`).
- Stress: the concurrent tests, 100 repetitions each under ThreadSanitizer on a loaded machine
  (8 busy loops on 4 CPUs): no failure and no report. The first release run of 0.4.0, on commit
  `643cec8`, failed here and showed that the step had passed anyway (MDQ-PR-032, MDQ-PR-033;
  `first-run-643cec8/stress-tsan.txt`); both are corrected, and this run is the first with them.
- Property-based tests: the eleven properties with the wide search (`MINIDAQ_PROP_CASES`), no
  counterexample, and the harness's own test that it shrinks one.
- Coverage: Clang source-based coverage of the debug tests, per software item (lines, branches,
  MC/DC conditions, functions; `coverage.txt`). All class B items reach at least 75% of their
  lines. Every untaken branch on a line of a class B file changed since 0.3.0 was reviewed
  (`coverage-review.md`): one was a missing test, added before these checks (the link
  resynchronization trace), three are infeasible, and the others are accepted with their
  reasons, most of them the crash report's code, which runs in a dying process that writes no
  coverage profile and is verified by death tests and a system test instead.
- Performance: the baseline gate failed. `BM_EnergyFilter/1` and `/3` ran 18% and 23% slower
  than the baseline recorded for 0.3.0 (p < 0.0001) and `BM_DecodePacked` 48% faster, although no
  code those benchmarks run changed since 0.3.0. An interleaved A/B of the release build of tag
  `book-v0.3.0` against that of `6766495`, on the same machine in one job (`tools/perf_ab.sh`, 5
  rounds of 2 repetitions), found no regression: speed 1.02 and 1.00 for the two rows (row
  "performance"). The first run of 0.4.0 gave the same verdicts (`first-run-643cec8/`). The
  machine was slower than when the baseline was recorded; the baseline is kept (performance
  budget, version 4). SRS-PERF-020: on this commit the pipeline ran at a median of 35.9 M
  words/s in the `hardened` build (5 repetitions), 3.6 times the 10 M singles/s required.
  SRS-PERF-021: the list-mode writer wrote 18.8 to 19.0 M coincidences/s with fsync at close (3
  runs of 200 M), at least 6.2 times the 3 M required. The performance budget and the SRS quote
  the run on `6766495` (36.6 M words/s; 14.0 to 16.4 M coincidences/s), whose programs are
  identical; 0.3.0 measured 15.9 to 17.0 M, so the writer varies with the machine's disk, not
  with the code.
- System tests: 34 test cases on the `release` build, none failed (`system-test-report.md`).
- Soak: 30 minutes at 1 M singles/s, 1.8 G singles, no loss and no fault; resident memory 29.7
  to 30.4 MiB with a trend of -0.004 MiB/h; the 99th percentile of the end-to-end latency at most
  47.5 ms per interval (`soak/`).
- Fuzzing: each of the seven targets ran 600 s on its own CPU from its seed corpus with no crash,
  leak or timeout: config (5.4 M executions, 1,877 coverage points), decoder (15.1 M, 101), raw16
  (661 M, 14), protocol (0.68 M, 2,824), packet (10.6 M, 122), sorter (2.4 M, 324) and listmode
  (24.3 M, 184) (`fuzz/<target>.txt`). CAPA-0003's effectiveness check passed on these results.
- Identical programs: part 2 tested the `release` build of `6766495`. Between that commit and
  this one, MiniDAQ's code changed only in comments and the CMake project description (the
  book's retitling), in an exercise test and a unit test, and in the documents (`git diff
  --stat` in the evidence). The `release` builds of both commits give byte-identical programs,
  MiniDAQ libraries and benchmarks, and the `fuzz` builds byte-identical fuzz targets (SHA-256
  of each, `identical-binaries.txt`), so the system tests, the soak, the gate and the fuzzing
  apply to this commit's code.
- CI: the GitHub run of `ci.yml` on this commit passed every job, and `gates` and `codeql`
  passed on it too (`ci-run.txt`). The release commit on top changes only documents,
  measurements and the version; its own CI run is checked before the tag is made (SDP section
  8).

## Known anomalies

Generated from the problem reports by `tools/anomalies.py` ([known-anomalies.md](../known-anomalies.md)):
three open reports, each evaluated again for this release and released with. No report of Part IV
is open; MDQ-PR-015 to MDQ-PR-034 are closed.

- MDQ-PR-006 (service, relevant to safety): a port fault is noticed up to 20 ms late. Released
  with: a faulted run is incomplete in its verdict whatever the delay; Part IV changed neither the
  fault path nor the verdict.
- MDQ-PR-007 (sorter, not relevant to safety): the sorter holds its last 104 ns of singles until
  more data arrives. Released with: no coincidence is lost; SRS-SRT-013's tie order does not
  change it.
- MDQ-PR-009 (sim, relevant to safety): simulation code is linked into the shipped server.
  Released with for a teaching project: simulated data is identifiable in the run record and in
  the diagnostics of Chapter 21.

## Risk

All nine hazards of the risk file are closed (`risk/hazards.json`, test `docs.risk`); Part IV
added no hazard, and no hazard's residual risk depends on a control that is not verified (the
trace matrix's risk-control column). The threat model, version 2, adds the crash report as a
data store (T-35 to T-38); none of its threats is open. The overall residual risk is acceptable
under the criteria of the risk management plan, section 3, as judged by the software lead (the
author) for this teaching release; a product release adds the clinical expert's judgment
(assumption: confirm with team).

## SOUP review

2026-10-26, for MiniDAQ 0.4 ([SOUP list](../soup-list.md), version 6, test `docs.soup`):
nlohmann/json 3.12.0 is still the latest release and none of its known defects affects a
requirement; the installed OpenSSL package `3.0.13-0ubuntu3.16` is unchanged since the review for
0.3, and MiniDAQ 0.4 needs that version or later.

## Build

The release is built from the tag with the presets, as the checks did:

```sh
git checkout book-v0.4.0
ci/run_all.sh                                     # the six presets, tests and documentation tests
tools/static_analysis.sh build/clang-release
cmake --preset hardened && cmake --build --preset hardened   # the shipped binaries, reproducible
tools/make_sbom.py --validate -o minidaq-0.4.0.cdx.json
tools/release_checks.sh OUT 600 1 && tools/release_checks.sh OUT 600 2   # this record's evidence
```
