# MiniDAQ 2.2.0 release record

The record of SDP section 8 for release 2.2.0: the agent gate and its known-bad library (CR-0036, Theme P1), the agent
files under the quality system (CR-0036, Theme P2), several readout nodes in the simulator with
their merge (CR-0037, Theme S), records that follow the checks (Theme R), and a deviation for
the latency criterion ACC-04 (MDQ-PR-096). Evidence paths
are relative to this directory's parent, `docs/regulatory/`; the files are in `measurements/release-2.2.0/` and were
written by `tools/release_checks.sh` unless the notes below say otherwise. Checked with
`tools/release_record.py check` (Exercise 14.5's `check()`) before the tag was made.

## Release

MiniDAQ 2.2.0, commit 5647d2e558a300cc3011ab25b38d0725f2cb2b88, tag book-v2.2.0

The release checks ran on this commit with a clean working tree (`commit.txt`); the parts that

## Deviation

ACC-04 (SRS-PERF-022, the latency) failed twice on the candidate, by two and then five
intervals, and the regression gate's second run judged `BM_SortFunctor` slower. The criteria
were set before these checks ran (CR-0035, CR-0025) and were not changed after they failed; part
3 ran again only once, under SDP section 8, after its investigation was written.

The evidence points to the machine, not to the commit. The soak ran at 1 M singles/s, a few
percent of the pipeline's capacity; every slow interval in both runs coincides with a server
thread kept from a CPU 20 to 77 ms while runnable, with steal above 2.1.0's; the programs of
2.1.0, built and soaked on the same machine the same evening, had 6 of 600 intervals, at the
limit, against 3 at their own release; the pipeline benchmark ran 38% slower than at 2.1.0 while
the interleaved comparison of the two releases found them equal. The single-node source of
CR-0037 runs the same statements as before, and `BM_SortFunctor`'s machine code is the same in
both builds. The candidate's 19 slow intervals of 1,200 against the control's 6 of 600 is a
rate 1.6 times as high, which two soaks cannot tell from chance.

The software lead decided on 2026-11-24 (the coordinator, under the author's standing
delegation of 2026-11-15, 2026-11-23 and 2026-11-24, given in writing in the project), from
three options: release with this deviation and MDQ-PR-096 open, hold for a series of
interleaved soaks, or hold to investigate the waits in the code. MDQ-PR-096 stays open, and
CR-0038 proposes for 2.3.0 that the latency be judged against the previous release's programs,
interleaved on the same machine, as the regression gate judges the benchmarks.

## Known anomalies

Generated from the problem reports by `tools/anomalies.py` ([known-anomalies.md](../known-anomalies.md)):
2 open report(s), each evaluated again for this release.

- MDQ-PR-006 (service, relevant to safety): a port fault is noticed up to 20 ms late. Released
  with: no change of 2.2.0 touches the service or its ports, so the decision of 1.3.0 to 2.1.0

  CR-0038 is proposed for 2.3.0.

## Risk

All 17 hazards of the risk file are closed (`risk/hazards.json`, test `docs.risk`). One risk
control was added: RC-56 (H-01), the node merge's order and its count of late singles
(CR-0037), verified by `test_readout_nodes.cpp`. No hazard was added. The threat model (version
19) was reviewed for this release: the agent gate, the agent files, their settings and hooks are
development tools and add no element, flow or interface of the running product; its gap on the
AI coding assistant records the review of an agent with shell access (CR-0036). The overall
residual risk is acceptable, as judged for 2.0.0 and unchanged by this release.

## Build

The release is built from the tag with the presets, as the checks did:

```sh
git checkout book-v2.2.0
ci/run_all.sh                                     # the six presets, tests and documentation tests
ci/run_all.sh product                             # the product build, without the simulator
tools/static_analysis.sh build/clang-release
cmake --preset product && cmake --build --preset product     # the shipped binaries (CR-0029)
tools/repro_check.sh OUT                                     # two builds, compared byte for byte
tools/make_sbom.py --validate -o minidaq-2.2.0.cdx.json
tools/release_checks.sh OUT 600 resume                        # this record's evidence
tools/acceptance.py OUT                                       # the acceptance verdict
book/build.sh all both && book/build.sh boox both             # the book and the solutions
```
