# MiniDAQ 0.3.0 release record

The record of SDP section 8 for release 0.3.0 (the book's Part III). Evidence paths are relative
to this directory's parent, `docs/regulatory/`; the files are in `measurements/release-0.3.0/`
and were written by `tools/release_checks.sh` on the released commit unless the measurements
README says otherwise. Checked with Exercise 14.5's `check()` before the tag was made.

## Release

MiniDAQ 0.3.0, commit 57ef123d4317fc91feb92b615e2d736918a92e50, tag book-v0.3.0

The commit is the one the release checks ran on (`commit.txt`: clean working tree). The release
record and the version bump are committed on top of it and change no code.

Notes on the results:

- Build and tests: `ci/run_all.sh` built all six presets and ran 524 to 526 tests each (the
  count differs by preset because some tests exist only in some builds); the tests that a
  sanitizer build skips (four timing tests of exercise solutions) are skipped by design. The
  documentation tests in the same run include `docs.trace` (the trace matrix, 132
  requirements), `docs.srs`, `docs.risk`, `docs.soup`, `docs.anomalies` and `docs.design_file`.
- Starters: every starter fails at least one test and none hangs, checked one by one in a
  `Release` build (CAPA-0004).
- Stress: the concurrent tests, 100 repetitions each under ThreadSanitizer on a loaded machine
  (8 busy loops on 4 CPUs): no failure and no report.
- Performance: `tools/perf_gate.py --strict` finds no benchmark of the budget slower than the
  baseline (the gate of CAPA-0004, run here for the first time on a release). SRS-PERF-020: the
  pipeline ran at 37.2 M words/s in the `hardened` build (median of 5), 3.7 times the 10 M
  singles/s required. SRS-PERF-021: the list-mode writer wrote 15.9 to 17.0 M coincidences/s with
  fsync at close (3 runs), at least 5 times the 3 M required. That is below the 18 to 20 M/s of
  Chapter 12 (`measurements/ch12/`); the requirement is met with margin, and the writer is
  measured again for 0.4.0 to tell a change from the machine's variation.
- Fuzzing: each of the seven targets ran 600 s on its own CPU from its seed corpus with no crash, leak or timeout: config (6.7 M executions, 1,868 coverage points), decoder (14.0 M, 101), raw16 (658 M, 14), protocol (0.86 M, 2,839), packet (11.6 M, 122), sorter (2.9 M, 315) and listmode (23.5 M, 183) (`fuzz/<target>.txt`).
- The run was interrupted once, after the writer benchmark, when the session that ran it was
  restarted; the remaining checks (gate, fuzzing) were resumed on the same commit and clean
  tree, and `release-checks.txt` shows where.
- Correction (2026-10-26, MDQ-PR-029): the run did not stop because of the restart. The writer
  step of `tools/release_checks.sh` ended the whole script with status 0, and it did so again in
  the first run for 0.4.0. The checks resumed by hand are the ones the defect skipped, so the
  evidence above is complete; the explanation was not.

## Known anomalies

Generated from the problem reports by `tools/anomalies.py` ([known-anomalies.md](../known-anomalies.md)):
three open reports, each evaluated and released with.

- MDQ-PR-006 (service, relevant to safety): a port fault is noticed up to 20 ms late. Released
  with: a faulted run is incomplete in its verdict whatever the delay.
- MDQ-PR-007 (sorter, not relevant to safety): the sorter holds its last 104 ns of singles until
  more data arrives. Released with: no coincidence is lost.
- MDQ-PR-009 (sim, relevant to safety): simulation code is linked into the shipped server.
  Released with for a teaching project: simulated data is identifiable in the run record.

## Risk

All nine hazards of the risk file are closed (`risk/hazards.json`, test `docs.risk`); no hazard's
residual risk depends on a control that is not verified (the trace matrix's risk-control column).
The overall residual risk is acceptable under the criteria of the risk management plan, section
3, as judged by the software lead (the author) for this teaching release; a product release adds
the clinical expert's judgment (assumption: confirm with team).

## Build

The release is built from the tag with the presets, as the checks did:

```sh
git checkout book-v0.3.0
ci/run_all.sh                                     # the six presets, tests and documentation tests
tools/static_analysis.sh build/clang-release
cmake --preset hardened && cmake --build --preset hardened   # the shipped binaries
tools/make_sbom.py --validate -o minidaq-0.3.0.cdx.json
tools/release_checks.sh measurements/release-0.3.0 600       # the evidence of this record
```
