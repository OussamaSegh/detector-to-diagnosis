# MiniDAQ 2.0.1 release record

The record of SDP section 8 for release 2.0.1, the first patch release of 2.0: the fixes of the
independent review of 2.0.0 (MDQ-PR-077 to MDQ-PR-080), the rule on running a failed release
check again and the tool that enforces it, and a patch release made from the main branch under
the maintenance plan's version 4. Evidence paths
are relative to this directory's parent, `docs/regulatory/`; the files are in `measurements/release-2.0.1/` and were
written by `tools/release_checks.sh` unless the notes below say otherwise. Checked with
`tools/release_record.py check` (Exercise 14.5's `check()`) before the tag was made.

## Release

MiniDAQ 2.0.1, commit 620dc65150682edb1b21a1bb888f18fc0ea0ca8d, tag book-v2.0.1

The release checks ran on this commit with a clean working tree (`commit.txt`); the parts that
passed: 1, 2, 3, 4 (`release-checks.txt`), in one worktree (`commit.txt`, `commit-part-2.txt`
to `commit-part-4.txt`). Every part passed at its first verdict. Part 4 started three times:
the first two runs were stopped before their verdict (a session's time limit, then a restart of
the machine) and `resume` ran it again; a run stopped without a verdict is not a failure under
SDP section 8 (evidence README).

The main branch held only changes that a patch release may contain since the tag `book-v2.0.0`
(maintenance plan, section 4), so the release is made from it, and `release/2.0` is cut when the
first change for 2.1.0 reaches the main branch. The changes since 2.0.0, each a fix of a problem
report, a documentation correction or a record:

- **MDQ-PR-077** (process): SDP version 21 says when a failed check of the release checks may
  run again, and `tools/release_checks.sh resume` enforces it (status 4, test
  `tools.release_checks`).
- **MDQ-PR-078** (CAPA-0005): the reader of a list-mode file's delayed window is
  `control::metadata_delayed_window_ps`, and `fuzz_documents` reads it as mode 5.
- **MDQ-PR-079**: SRS-CTL-022's test sends a 2.x request and checks that the refusal names the
  migration note.
- **MDQ-PR-080** (the book): the download page and the web edition are built from the latest
  release tag.
- `tools/soak.py` records the per-second measure of MDQ-PR-064; a 100-minute measured soak
  (`measurements/mdq-pr-064/`).
- The maintenance plan's version 4 (a patch release from the main branch), the roadmaps of
  2.1.0 and 3.0.0, and the commit policy's acceptance of one commit whose `Review:` trailer git
  did not parse (b4daafe).

The commits on top of 620dc65 up to the tag change no product code: a unit test from the
coverage review, the evidence, the approval of two documents, this record and the version
strings.

## Verification

Notes on the results:

- Builds and tests: the six presets built and passed their tests (`run_all.txt`), the product
  preset too (`product.txt`); clang-tidy 18 and cppcheck 2.13 found nothing
  (`static-analysis.txt`); every exercise starter fails at least one test and none hangs
  (`starters.txt`).
- Stress and properties: 100 repetitions under TSan, 101 tests, all passed; the wide property
  search, 12 tests, passed.
- Structural coverage: 90.9% of lines and 81.2% of branches of the shipped code
  (`coverage.txt`). The review of the class B lines changed since 2.0.0
  (`coverage-review.md`) found one condition never true, in the new metadata reader; the unit
  test now covers it, in a commit after 620dc65 that changes the test only.
- Performance: the regression gate against `book-v2.0.0`, interleaved, passed
  (`perf-gate.txt`). No benchmark was significantly slower at the gate's level (alpha 0.01).
  `BM_EnergyFilter/1/50/0/4096` measured 0.771 of 2.0.0, but at p = 0.045, which is not
  significant at that level. No source on its path changed since 2.0.0: the only product
  sources changed are the list-mode metadata reader and its caller. The pipeline ran at
  42.7 M singles/s (SRS-PERF-020), and the writer at 22.86 M coincidences/s at its slowest
  (SRS-PERF-021).
- Soak: 30 minutes at 1 M singles/s, no loss, memory flat; the 99th percentile at most 2.44 ms
  in 180 of 180 intervals (ACC-04, SRS-PERF-022); the largest one-second run-queue wait of one
  thread 59.3 ms (MDQ-PR-064's measure).
- System tests: 38 test cases, all passed. End to end: every check of both acquisitions passed,
  with the records equal to the reference.
- Fuzzing: nine targets, 600 s each, no crash; `fuzz_documents` with its mode 5 (MDQ-PR-078).
- Acceptance: 9 of 9 (`acceptance.md`). Reproducible build: two builds of the product preset
  in two checkouts, identical archives (`repro/repro.txt`).
- CI on GitHub: ci, gates, codeql and pages green on 620dc65 (`ci-run.txt`); the release
  commit's own runs are checked before the tag.

## Known anomalies

Generated from the problem reports by `tools/anomalies.py` ([known-anomalies.md](../known-anomalies.md)):
2 open report(s), each evaluated again for this release.

- MDQ-PR-006 (service, relevant to safety): a port fault is noticed up to 20 ms late. Released
  with: no change of 2.0.1 touches the service or its ports, so the decision of 1.3.0 and 2.0.0
  stands, with its two verifying tests. Roadmap 3.0.0 plans its fix (an event-driven fault
  path with control API 4.0).
- MDQ-PR-064 (pipeline, not relevant to safety): the end-to-end latency's 99th percentile
  exceeds 10 ms in about one interval in a hundred, with no change to the code. Released with:
  this release passes ACC-04 with 180 of 180 intervals (at most 2.44 ms), no single is lost,
  and the latency is not a risk control. The finer measure now runs in every soak; no peak has
  occurred with it (the review's 30 minutes, 100 minutes before the checks, the checks' 30
  minutes), so the cause is still unknown. Roadmap 2.1.0, theme I, takes it up.

## Risk

All 17 hazards of the risk file are closed (`risk/hazards.json`, test `docs.risk`); no change of
2.0.1 adds or changes a hazard, a risk control or its verification. The threat model (version
18) was reviewed for this release: the changes add no element, flow or asset of the product
(the metadata reader moved into the library, where it is fuzzed; the release tool and the
book's publication are outside the product), so it stands. The overall residual risk is
acceptable, as judged for 2.0.0 and unchanged by this release.

## Build

The release is built from the tag with the presets, as the checks did:

```sh
git checkout book-v2.0.1
ci/run_all.sh                                     # the six presets, tests and documentation tests
tools/static_analysis.sh build/clang-release
cmake --preset hardened && cmake --build --preset hardened   # the shipped binaries
tools/repro_check.sh OUT                                     # two builds, compared byte for byte
tools/make_sbom.py --validate -o minidaq-2.0.1.cdx.json
tools/release_checks.sh OUT 600 resume                        # this record's evidence
tools/acceptance.py OUT                                       # the acceptance verdict
book/build.sh all both && book/build.sh boox both             # the book and the solutions
```
