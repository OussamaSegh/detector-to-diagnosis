# MiniDAQ 0.9.0 release record

The record of SDP section 8 for release 0.9.0 (the book's Part IX and Appendix A). Evidence paths
are relative to this directory's parent, `docs/regulatory/`; the files are in
`measurements/release-0.9.0/` and were written by `tools/release_checks.sh` unless the notes below
say otherwise. Checked with Exercise 14.5's `check()` before the tag was made.

## Release

MiniDAQ 0.9.0, commit c8d0800160fe972f9b287784b33a0af2b97f5b4f, tag book-v0.9.0

The release checks ran on this commit with a clean working tree, in four parts in one worktree
(`commit.txt`, `commit-part-2.txt` to `commit-part-4.txt`), each ending with its summary line
(`release-checks.txt`). The commits on top of it change no source of the product (`git diff
c8d0800 book-v0.9.0 -- minidaq/src minidaq/include minidaq/apps recon/src recon/include` is
empty) except the version string the programs and the Python packages report (`VERSION`,
`analysis/pyproject.toml`, `minidaq_analysis.__version__`, `recon/python/pyproject.toml`): the tag
lines of Chapters 35 to 37, problem report MDQ-PR-061, and this release's record, evidence,
version and documents. Part IX changed no source of the product either: `git diff book-v0.8.0
c8d0800` over the same paths is empty. Its code is in tools: the DICOM export (TL-44), the commit
policy's check (TL-46) and the report of assisted changes (TL-47).

Notes on the results:

- Build and tests: `ci/run_all.sh` built all six presets and ran 917 to 927 tests each, none
  failed (the count differs by preset because some tests exist only in some builds). The
  documentation tests in the same run include `docs.trace` (237 requirements), `docs.baseline`,
  `docs.srs`, `docs.risk`, `docs.soup`, `docs.anomalies`, `docs.capa`, `docs.changes`,
  `docs.tools`, `docs.design_file` and `tests.waits`. Part IX added `tools.dicom`,
  `tools.commits`, `tools.ai_provenance` and the tests of nine exercises.
- Starters: every starter of the `Release` build fails at least one test and none hangs,
  including the nine exercises of Part IX; Exercise 37.3's starter has too few tests and lets all
  seven mutants live.
  Exercise 18.3's starter fails in the coverage build and its solution passes
  (`coverage-exercise.txt`).
- Stress: the concurrent tests, 100 repetitions each under ThreadSanitizer: 95 tests, no failure
  and no report.
- Property-based tests: the twelve properties with the wide search, no counterexample.
- Coverage: Clang source-based coverage of the debug tests, per software item (`coverage.txt`).
  Every class B item covers at least 75% of its lines. No product line changed since 0.8.0, so
  the figures are those of 0.8.0 and the review of untaken branches on changed lines has no line
  to review.
- Performance, SRS-PERF-020: the pipeline ran at a median of 41.5 M words/s in the `hardened`
  build (5 repetitions), 4.15 times the 10 M singles/s required (ACC-01: at least 20 M).
  SRS-PERF-021: the list-mode writer wrote 21.1 to 21.6 M coincidences/s with fsync at close (3
  runs of 200 M), at least 7.0 times the 3 M required.
- Performance: no regression, judged under the deviation below by the gate run between this
  commit and release 0.8.0 on the same machine. The gate against the baseline
  (`benchmarks/baseline/book-vm.json`) **failed** on one benchmark of six: the energy filter with
  three channels at 0.882 of the baseline (p = 0.0001), and with one channel at 0.889; the other
  four ran at 1.06 to 1.83. The suites of release 0.8.0 and of this commit, built in two worktrees
  and run one after the other twice on the same machine the same day, show the same: 0.8.0's own
  programs failed the energy filter in their second round (0.862 and 0.893), this commit failed
  it in both rounds (0.888 to 0.917), and this commit against 0.8.0 passed the gate in the
  second round (every speed 0.864 to 1.080, no significant difference) and flagged the energy
  filter with one channel at 0.882 in the first (`perf-interleaved.txt`). The code the energy
  filter runs is the same in both: no source of the product changed between them.
- System tests: 34 test cases on the `release` build, none failed (`system-test-report.md`).
- Soak (SRS-SYS-003): 30 minutes at 1 M singles/s, 1.8 G singles, no loss and no fault; resident

## Deviation

Two acceptance criteria failed, as at release 0.8.0: ACC-04 (SRS-PERF-022, the latency) and ACC-08
(the performance gate, as part of the release checks). No source of the product changed between
release 0.8.0 and this commit. The programs of release 0.8.0 fail the same benchmark of the gate
on the same machine on the same day, and the latency's tail is smaller than at 0.8.0 (one
interval of 181 above the limit, against 15). The cause is the reference machine, not the release.
No criterion was changed after it failed.

The record of 0.8.0 asked the next release to judge both criteria on its own evidence, and to
treat the baseline of the gate and the margin of the latency limit as questions for a change
request if the machine stayed slower. It did, for a second release: CR-0025 is opened for both,
to be decided before release 1.0.0 with the measurements of releases 0.7.0 to 0.9.0 side by side.

The software lead (the author) approved the release with this deviation on 2026-11-08, after reading
this evidence.

## Corrective actions

No CAPA is open. CAPA-0001 (tests that depend on the speed of the machine) stayed effective: no
test failed for a timing reason in CI, in the release checks or in the stress run of the period;
the gate and the latency limit are measurements of the machine by design, not tests that the CAPA
covers.

## Known anomalies

Generated from the problem reports by `tools/anomalies.py` ([known-anomalies.md](../known-anomalies.md)):
three open reports, each evaluated again for this release and released with. No report of Part
IX is open; MDQ-PR-059 to MDQ-PR-061 are closed.

- MDQ-PR-006 (service, relevant to safety): a port fault is noticed up to 20 ms late. Released
  with: a faulted run is incomplete in its verdict whatever the delay; Part IX does not change the
  server.
- MDQ-PR-007 (sorter, not relevant to safety): the sorter holds its last 104 ns of singles until
  more data arrives. Released with: no coincidence is lost; the end-to-end accounting balances
  every single at the end of a run.
- MDQ-PR-009 (sim, relevant to safety): simulation code is linked into the shipped server.
  Released with for a teaching project: simulated data is identifiable in the run record and in
  the diagnostics; Appendix A records the architectural resolution a product would make.

## Risk

All 17 hazards of the risk file are closed (`risk/hazards.json`, test `docs.risk`). Part IX added
H-15 to H-17 (the DICOM export: the wrong patient, wrong values or positions, a series that does
not arrive whole) with RC-47 to RC-51, and the preliminary hazard HZ-5, which no item of the
server carries; in this book the export is a tool (TL-44), and Chapter 35 and Appendix A say what
its class would be in a scanner. No hazard's residual risk depends on a control that is not
verified (the trace matrix's risk-control column). The threat model, version 12, was reviewed for
this release: Part IX added the DICOM export as a recorded gap and the AI coding assistant as a
gap of the development environment, and no element, flow or interface to the running server. The
overall residual risk is acceptable under the criteria of the risk management plan, section 3,
as judged by the software lead (the author) for this teaching release; a product release adds
the clinical expert's judgment (assumption: confirm with team).
