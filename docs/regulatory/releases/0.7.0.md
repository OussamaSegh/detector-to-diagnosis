# MiniDAQ 0.7.0 release record

The record of SDP section 8 for release 0.7.0 (the book's Part VII). Evidence paths are relative
to this directory's parent, `docs/regulatory/`; the files are in `measurements/release-0.7.0/`
and were written by `tools/release_checks.sh` unless the notes below say otherwise. Checked with
Exercise 14.5's `check()` before the tag was made.

## Release

MiniDAQ 0.7.0, commit cfb708fb44b22b8e9648f2ad211600c96ae55490, tag book-v0.7.0

The release checks ran on this commit with a clean working tree, in four parts in one worktree
(`commit.txt`, `commit-part-2.txt` to `commit-part-4.txt`), each ending with its summary line
(`release-checks.txt`). A first run of part 1 on the commit before, 1572784, failed and found
MDQ-PR-052 and MDQ-PR-053 (`part1-1572784/`); this commit fixes both and changes no code of the
product. One commit on top of it adds only the tag line of Chapter 32 (`.github/tags.txt`). The
release record, the version and the documents of this release are committed on top and change no
code except the version string that the programs report. Part VII changed none of MiniDAQ's
sources (`git diff book-v0.6.0 cfb708f -- minidaq/src minidaq/apps minidaq/include` is
empty): its changes are the analysis package, the build, tools, tests, exercises and documents.

Notes on the results:

- Build and tests: `ci/run_all.sh` built all six presets and ran 872 to 882 tests each (the count
  differs by preset because some tests exist only in some builds; the timing tests of exercise
  solutions skip in sanitizer builds by design). The documentation tests in the same run include
  `docs.trace` (211 requirements), `docs.srs`, `docs.risk`, `docs.soup`, `docs.anomalies`,
  `docs.capa`, `docs.changes`, `docs.tools` and `docs.design_file`, and `tests.waits` with its
  new checks of clock reads and thread starts (CAPA-0001). Part VII added the analysis package's
  tests (pytest, mypy, ruff), the installed package's consumer test `cmake.consumer`, the wheel's
  test `recon.wheel` (in CI's job `python`), the formatting check and the lock file audit.
- Starters: every starter of the `Release` build fails at least one test and none hangs,
  including the six exercises of Part VII; Exercise 18.3's starter, which exists only in the
  coverage build, fails there and its solution passes (`coverage-exercise.txt`).
- Stress: the concurrent tests, 100 repetitions each under ThreadSanitizer on a loaded machine (8
  busy loops on 4 CPUs): 95 tests, the longer list of 0.6.0, no failure and no report.
- Property-based tests: the twelve properties with the wide search (`MINIDAQ_PROP_CASES`), no
  counterexample.
- Coverage: Clang source-based coverage of the debug tests, per software item (`coverage.txt`).
  Every class B item covers at least 75% of its lines, and the figures are those of 0.6.0
  (no class B source file changed, so the review of untaken branches on changed lines has no
  line to review).
- Performance: the baseline gate passed, every benchmark within its limit (speeds 0.956 to
  1.031 against the baseline). SRS-PERF-020: the pipeline ran at a median of 37.5 M words/s in
  the `hardened` build (5 repetitions, 35.1 to 39.1), 3.75 times the 10 M singles/s required.
  SRS-PERF-021: the list-mode writer wrote 12.0 to 15.8 M coincidences/s with fsync at close (3
  runs of 200 M), at least 4.0 times the 3 M required.
- System tests: 34 test cases on the `release` build, none failed (`system-test-report.md`).
- Soak: 30 minutes at 1 M singles/s, 1.8 G singles, no loss and no fault; resident memory 30.2
  to 30.9 MiB with a trend of +0.000 MiB/h (standard error 0.033); the 99th percentile of the
  end-to-end latency at most 4.42 ms per interval (`soak/`).
- Fuzzing: each of the eight targets ran 600 s on its own CPU from its seed corpus with no
  crash, leak or timeout: config (6.0 M executions, 1,907 coverage points), decoder (14.7 M,
  101), raw16 (634 M, 14), protocol (0.86 M, 2,902), packet (11.4 M, 123), sorter (2.7 M, 324),
  listmode (23.0 M, 183) and, new and owed by the record of 0.6.0, calibration (12,401
  executions, 1,631 coverage points) (`fuzz/<target>.txt`). The calibration target is slow, 20
  executions per second, because each input writes and reads a whole calibration table; its
  coverage still grew to the end of the run. Making it faster is planned for 0.8.0.
- CI: the GitHub run of `ci.yml` on the checked commit passed every job, among them `format`,
  `python` (with the lock file audit) and `reproducible-build`; `gates`, `codeql`, `kdp` and
  `pages` passed on it too (`ci-run.txt`). The release commit on top changes only documents,
  measurements and the version; its own CI run is checked before the tag is made (SDP section 8).
  Every failed CI run of Part VII was read job by job (SDP section 7): on 83f2e4c, c72ed58 and
  db7314d only the job `reproducible-build` failed (MDQ-PR-049, fixed in e6ac69a), and on
  ebbe4fa all six build jobs failed only Exercise 6.3's ADR test (MDQ-PR-050).

## Corrective actions

- CAPA-0001 (tests that depend on the speed of the machine): **not effective** at 0.7.0. Three
  tests of exercises failed for a timing reason in the period: Exercise 31.3's speed test in CI
  (MDQ-PR-047), Exercise 21.3's concurrent snapshot test locally (MDQ-PR-048) and Exercise 10.4's
  absolute rate in part 1 of these checks (MDQ-PR-052). Further action (record in the CAPA):
  `tests.waits` requires every clock read and thread start in every test to state why it does not
  depend on the machine's speed, the margin table lists every speed test and criterion, and the
  gate self-test plants an untagged clock read; next check at release 0.8.0.

## Known anomalies

Generated from the problem reports by `tools/anomalies.py` ([known-anomalies.md](../known-anomalies.md)):
three open reports, each evaluated again for this release and released with. No report of Part
VII is open; MDQ-PR-047 to MDQ-PR-053 are closed.

- MDQ-PR-006 (service, relevant to safety): a port fault is noticed up to 20 ms late. Released
  with: a faulted run is incomplete in its verdict whatever the delay; Part VII does not change
  the fault path.
- MDQ-PR-007 (sorter, not relevant to safety): the sorter holds its last 104 ns of singles until
  more data arrives. Released with: no coincidence is lost; the analysis package reads only
  closed runs.
- MDQ-PR-009 (sim, relevant to safety): simulation code is linked into the shipped server.
  Released with for a teaching project: simulated data is identifiable in the run record and in
  the diagnostics; the analysis package of Part VII reads the data and does not change this.

## Risk

All 14 hazards of the risk file are closed (`risk/hazards.json`, test `docs.risk`). Part VII added
H-14 (a quality control report that passes a degraded detector or a run that lost data), with the
controls RC-45 and RC-46. No hazard's residual risk depends on a control that is not verified (the
trace matrix's risk-control column). The threat model, version 7, was reviewed for this release:
Part VII added no element, flow or interface to the running MiniDAQ, none of its 57 threats is open,
and its section 8 now covers the tools' lock file (MDQ-PR-051). The overall residual risk is
acceptable under the criteria of the risk management plan, section 3, as judged by the software lead
(the author) for this teaching release; a product release adds the clinical expert's judgment
(assumption: confirm with team).

## SOUP review

2026-11-04, for release 0.7.0 ([SOUP list](../soup-list.md), version 15, test `docs.soup`):
nlohmann/json 3.12.0 is still the latest release; the OpenSSL project lists no advisory for 3.0
after 2026-09-29, so the installed package `3.0.13-0ubuntu3.16` still patches every one, and
MiniDAQ 0.7 needs that version or later; pybind11 3.1.0 is the latest release. Every package of
the analysis lock file was looked up in the Python Package Index's vulnerability records for the
first time: Pillow 12.3.0 and Pygments 2.17.2 had published advisories, none reachable from their
use, and were raised to 13.0.0 and 2.21.0 (MDQ-PR-051, CR-0019); `tools/lock_audit.py` (TL-39)
now runs in CI.

## Build

```sh
cmake --preset hardened && cmake --build --preset hardened   # the shipped binaries, reproducible
tools/make_sbom.py --validate -o minidaq-0.7.0.cdx.json
for p in 1 2 3 4; do tools/release_checks.sh OUT 600 $p; done   # this record's evidence
```
