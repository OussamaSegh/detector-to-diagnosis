# MiniDAQ 0.5.0 release record

The record of SDP section 8 for release 0.5.0 (the book's Part V). Evidence paths are relative
to this directory's parent, `docs/regulatory/`; the files are in `measurements/release-0.5.0/`
and were written by `tools/release_checks.sh` unless the notes below say otherwise. Checked with
Exercise 14.5's `check()` before the tag was made.

## Release

MiniDAQ 0.5.0, commit 6ef606e986a16f3986a624fe4be5a8811363fc4c, tag book-v0.5.0

The release checks ran on this commit with a clean working tree, in four parts in one worktree
(`commit.txt`, `commit-part-2.txt` to `commit-part-4.txt`), each ending with its summary line
(`release-checks.txt`). Four parts, not one run, because the machine restarted about once an hour
during the release (MDQ-PR-041); each part refuses to run on another commit than part 1's. The
release record, the version and the documents of this release are committed on top and change no
code except the version string that the programs report.

Notes on the results:

- Build and tests: `ci/run_all.sh` built all six presets and ran 802 to 804 tests each (the count
  differs by preset because some tests exist only in some builds; the timing tests of exercise
  solutions skip in sanitizer builds by design). The documentation tests in the same run include
  `docs.trace` (178 requirements, 172 verified by tests and 6 by measurement or inspection),
  `docs.srs`, `docs.risk`, `docs.soup`, `docs.anomalies`, `docs.capa` and `docs.design_file`.
- Starters: every starter of the `Release` build fails at least one test and none hangs;
  Exercise 18.3's starter, which exists only in the coverage build, fails there and its solution
  passes (`coverage-exercise.txt`).
- Stress: the concurrent tests, 100 repetitions each under ThreadSanitizer on a loaded machine
  (8 busy loops on 4 CPUs): 66 tests, no failure and no report.
- Property-based tests: the twelve properties with the wide search (`MINIDAQ_PROP_CASES`), no
  counterexample.
- Coverage: Clang source-based coverage of the debug tests, per software item (`coverage.txt`).
  Every class B item covers at least 75% of its lines; the new items of Part V cover `hw` 94.8%,
  `platform` 96.2% and `update` 85.1% of their lines. The review of every untaken branch on a
  changed line of the 38 class B files changed since 0.4.0 (`coverage-review.md`) added tests
  for the updater's refusals, the stores the updater must not trust, the board's own protection
  findings, the refusals of the hardware description and the slow control's failed writes, and
  those tests found three defects, corrected before these checks: an empty `schema_version` was
  accepted (MDQ-PR-042), a board's overcurrent trip was reported as a measured current
  (MDQ-PR-043), and a board that refused every write never latched a fault (MDQ-PR-044). Branch
  coverage fell only for `server`, from 75.0% to 73.8%, by the start-up paths of the hardware
  port and the watchdog that the review accepts with their reasons.
- Performance: the baseline gate failed. `BM_EnergyFilter/3`, `BM_HistogramRecord` and
  `BM_Pipeline` ran 10%, 16% and 15% slower than the baseline recorded for 0.3.0 (p < 0.0001),
  and the verdicts changed from run to run of this release (`BM_DecodePacked` flagged in one run
  and 15% faster in the next; earlier runs are in MDQ-PR-041's evidence). An interleaved A/B of
  the release build of tag `book-v0.4.0` against that of this commit, on the same machine in one
  job (`tools/perf_ab.sh`, 5 rounds of 2 repetitions), found no regression: speeds 0.92 to 1.07,
  none significant (row "performance"). The machine is slower than when the baseline was
  recorded, as at 0.4.0; the baseline is kept. SRS-PERF-020: the pipeline ran at a median of
  29.6 M words/s in the `hardened` build (5 repetitions, 25.0 to 33.5), 2.96 times the 10 M
  singles/s required; 0.4.0 measured 35.9 M on a faster spell of the same machine, and the A/B
  gives this commit 1.07 times 0.4.0's speed. SRS-PERF-021: the list-mode writer wrote 10.3 to
  12.2 M coincidences/s with fsync at close (3 runs of 200 M), at least 3.4 times the 3 M
  required; 0.4.0 measured 18.8 to 19.0 M, so the writer varies with the machine's disk.
- System tests: 34 test cases on the `release` build, none failed (`system-test-report.md`).
- Soak: 30 minutes at 1 M singles/s, 1.8 G singles, no loss and no fault; resident memory 29.9
  to 30.6 MiB with a trend of +0.011 MiB/h (standard error 0.033); the 99th percentile of the
  end-to-end latency at most 18.4 ms per interval (`soak/`).
- Fuzzing: each of the seven targets ran 600 s on its own CPU from its seed corpus with no crash,
  leak or timeout: config (5.1 M executions, 1,873 coverage points), decoder (11.0 M, 101), raw16
  (557 M, 14), protocol (0.54 M, 2,838), packet (8.8 M, 121), sorter (2.5 M, 324) and listmode
  (17.8 M, 183) (`fuzz/<target>.txt`).
- CI: the GitHub run of `ci.yml` on this commit passed every job, and `gates`, `perf` and
  `codeql` passed on it too (`ci-run.txt`). The release commit on top changes only documents,
  measurements and the version; its own CI run is checked before the tag is made (SDP section
  8).

## Corrective actions

- CAPA-0001 (tests that depend on the speed of the machine): **not effective** at 0.5.0. Three
  tests failed for a timing reason in the period: Exercise 5.2's speed test in CI (MDQ-PR-034),
  Exercise 12.3's trickle test under AddressSanitizer (MDQ-PR-039) and Exercise 10.4's speed test
  (MDQ-PR-040), all in the release checks or CI and none in MiniDAQ's own tests. The last showed
  that the margin rule of 0.4.0 had been applied only to the test that failed. Further action:
  every timing test that the CAPA names was checked against the rule at this release (record in
  the CAPA); next check at release 0.6.0.
- CAPA-0004 (checks that never run): **effective**, closed. This record cites a complete run of
  `tools/release_checks.sh` on the released code, four parts each ending with its summary line;
  no problem report since 0.4.0 has the cause "a check that could not run passed". The two runs
  cut by a restart reported themselves as failed (MDQ-PR-041), which is the guard of MDQ-PR-029
  doing its work.

## Known anomalies

Generated from the problem reports by `tools/anomalies.py` ([known-anomalies.md](../known-anomalies.md)):
three open reports, each evaluated again for this release and released with. No report of Part V
is open; MDQ-PR-035 to MDQ-PR-044 are closed.

- MDQ-PR-006 (service, relevant to safety): a port fault is noticed up to 20 ms late. Released
  with: a faulted run is incomplete in its verdict whatever the delay; the hardware port of Part V
  ends a run on a board fault through the same fault path.
- MDQ-PR-007 (sorter, not relevant to safety): the sorter holds its last 104 ns of singles until
  more data arrives. Released with: no coincidence is lost; Part V's end-of-run drain does not
  change it.
- MDQ-PR-009 (sim, relevant to safety): simulation code is linked into the shipped server.
  Released with for a teaching project: simulated data is identifiable in the run record and in
  the diagnostics; the hardware port does not change it.

## Risk

All ten hazards of the risk file are closed (`risk/hazards.json`, test `docs.risk`). Part V added
H-10 (detector gain drifts with temperature, controlled by the slow control's bias law and its
limits) and extended H-05 (a hung register read, an update that leaves a version that does not
start) and H-08 (replaced programs, threat T-07, now controlled by signed updates). No hazard's
residual risk depends on a control that is not verified (the trace matrix's risk-control
column). The threat model, version 3, adds updates as elements of the diagram (T-39 to T-53);
none of its 53 threats is open. The overall residual risk is acceptable under the criteria of
the risk management plan, section 3, as judged by the software lead (the author) for this
teaching release; a product release adds the clinical expert's judgment (assumption: confirm
with team).

## SOUP review

2026-10-26, at release 0.5.0 ([SOUP list](../soup-list.md), version 9, test `docs.soup`):
nlohmann/json 3.12.0 is still the latest release and none of its known defects affects a
requirement; the installed OpenSSL package `3.0.13-0ubuntu3.16` patches every advisory of
OpenSSL 3.0 up to 2026-09-29, and MiniDAQ 0.5 needs that version or later. Part V's new use of
OpenSSL (Ed25519 verification and SHA-256 in the updater) is covered by the same review.

## Build

The release is built from the tag with the presets, as the checks did:

```sh
git checkout book-v0.5.0
ci/run_all.sh                                     # the six presets, tests and documentation tests
tools/static_analysis.sh build/clang-release
cmake --preset hardened && cmake --build --preset hardened   # the shipped binaries, reproducible
tools/make_sbom.py --validate -o minidaq-0.5.0.cdx.json
for p in 1 2 3 4; do tools/release_checks.sh OUT 600 $p; done   # this record's evidence
```
