# MiniDAQ 0.8.0 release record

The record of SDP section 8 for release 0.8.0 (the book's Part VIII). Evidence paths are relative
to this directory's parent, `docs/regulatory/`; the files are in `measurements/release-0.8.0/`
and were written by `tools/release_checks.sh` unless the notes below say otherwise. Checked with
Exercise 14.5's `check()` before the tag was made.

## Release

MiniDAQ 0.8.0, commit d262ff01c3766cf0e57582c00d1635858bf7d32e, tag book-v0.8.0

The release checks ran on this commit with a clean working tree, in four parts in one worktree
(`commit.txt`, `commit-part-2.txt` to `commit-part-4.txt`), each ending with its summary line
(`release-checks.txt`); part 3 ran twice. The commits on top of it change no source of the
product (`git diff d262ff0 HEAD -- minidaq/src minidaq/include minidaq/apps recon` is empty):
CI's packages and the error path of `tools/e2e.py` (MDQ-PR-056), a fuzz target's oracle
(MDQ-PR-057), the release checks' log of the gate step (MDQ-PR-058), the SOUP list, the tag lines
of Chapters 33 and 34, and this release's record, version and documents. Part VIII changed one
source of the product: the simulator's model of the readout link (`readout_link.hpp` and `.cpp`,
SRS-SIM-024, CR-0020), which only the simulator and the test sender `minidaq_send` call, not
the server.

Notes on the results:

- Build and tests: `ci/run_all.sh` built all six presets and ran 896 to 906 tests each, none
  failed (the count differs by preset because some tests exist only in some builds). The
  documentation tests in the same run include `docs.trace` (219 requirements), `docs.baseline`,
  `docs.srs`, `docs.risk`, `docs.soup`, `docs.anomalies`, `docs.capa`, `docs.changes`,
  `docs.tools`, `docs.design_file` and `tests.waits`. Part VIII added `system.e2e`,
  `tools.acceptance`, `tools.req_baseline`, `tools.survey` and the tests of six exercises.
- Starters: every starter of the `Release` build fails at least one test and none hangs,
  including the six exercises of Part VIII; Exercise 34.3's starter is caught by one mutant of
  seven. Exercise 18.3's starter fails in the coverage build and its solution passes
  (`coverage-exercise.txt`).
- Stress: the concurrent tests, 100 repetitions each under ThreadSanitizer on a loaded machine:
  95 tests, no failure and no report.
- Property-based tests: the twelve properties with the wide search, no counterexample.
- Coverage: Clang source-based coverage of the debug tests, per software item (`coverage.txt`).
  Every class B item covers at least 75% of its lines. The figures are those of 0.7.0 except
  `sim`, whose 11 new lines (the link model) are all covered (645 of 677 lines before, 656 of
  688 now), so the review of untaken branches on changed lines has no line to review.
- Performance, SRS-PERF-020: the pipeline ran at a median of 33.7 M words/s in the `hardened`
  build (5 repetitions, 31.2 to 34.9), 3.37 times the 10 M singles/s required (ACC-01: at least
  20 M). SRS-PERF-021: the list-mode writer wrote 12.2 to 13.2 M coincidences/s with fsync at
  close (3 runs of 200 M), at least 4.0 times the 3 M required.
- Performance: no regression, judged under the deviation below by the gate run between this
  commit and release 0.7.0 on the same machine. The gate against the baseline **failed** in
  both runs of part 3. Every gated benchmark, including those
  whose code Part VIII did not touch, ran at 0.86 to 0.95 of the baseline
  (`benchmarks/baseline/book-vm.json`). The suites of release 0.7.0 and of this commit, built in
  two worktrees and run one after the other twice on the same machine the same day, were equally
  slow against the baseline (0.86 to 0.95), and this commit against 0.7.0 passed the gate in both
  rounds (speeds 0.970 to 1.045, no significant difference) (`perf-interleaved.txt`). The
  reference machine was slower that day; the code was not. The first run's gate step also left
  an empty log (MDQ-PR-058); run again by hand with its output kept, it built and failed as the
  second run did (`part3-first/`).
- System tests: 34 test cases on the `release` build, none failed (`system-test-report.md`).
- Soak (SRS-SYS-003): 30 minutes at 1 M singles/s, 1.8 G singles, no loss and no fault; resident
  memory 30.3 to 30.9 MiB with a trend of +0.010 MiB/h (standard error 0.033).
- Latency (SRS-PERF-022, new in Part VIII): **failed.** The 99th percentile of the end-to-end
  latency stayed at or below 10 ms in 165 of the soak's 180 intervals and reached 55.6 ms at
  most; in the first run of part 3, 172 of 180 and 26.6 ms. The median over the intervals was
  1.61 ms in both runs, against 1.57 ms at release 0.7.0, whose soak never passed 4.42 ms. The
  programs of release 0.7.0, soaked for 30 minutes on the same machine right after with nothing
  else running, reached 206.6 ms, with 13 intervals above 10 ms (`soak-0.7.0.txt`). The tail
  of the latency follows the machine's scheduling, not the release.
- End to end (SRS-SYS-006 to SRS-SYS-008): both acquisitions wrote the reference's records
  (equal SHA-256), every count balanced between the stages, the QC report passed, and the
  phantom's image has a radius of 80.25 mm and a center over periphery of 1.042 (`e2e.txt`).
- Fuzzing: each of the eight targets ran 600 s from its seed corpus with no crash, leak or
  timeout: config (5.7 M executions, 1,902 coverage points), decoder (14.4 M, 101), raw16 (573 M,
  14), protocol (0.58 M, 2,887), packet (10.2 M, 123), sorter (2.6 M, 324), listmode (19.1 M,
  184) and calibration (11,311, 1,651) (`fuzz/<target>.txt`). The calibration target's speed,
  owed by the record of 0.7.0, was analyzed and not changed: an edit input takes about 70 ms,
  about 90% of it in the JSON reader's document tree for the table's 73,728 values under
  AddressSanitizer (sampled with gdb); changes to the target gave 5% and were reverted. Its
  coverage still grows to the end of a run, and the CI smoke run and the release run together
  reach it.
- Acceptance (`acceptance.md`, `tools/acceptance.py` in the worktree at this commit): 7 of 9
  criteria pass; ACC-04 (the latency above) and ACC-08 (every part of the release checks passed,
  which the gate above prevents) fail. The deviation below applies to both.
- CI: on this commit the six build jobs of `ci.yml` failed only `system.e2e`, whose daily QC could
  not import SciPy on GitHub's runners (MDQ-PR-056); every other job and `gates`, `codeql` and

  product source, passed every workflow, and so did every later commit before the release
  commit (`ci-run.txt`). The release commit's own CI run is checked before the tag is made (SDP
  section 8). Every failed CI run of the period was read job by job (SDP section 7); one of them,
  the job `fuzz-smoke` on the Part VII review's branch, had not been read before the branch was
  merged and found MDQ-PR-057.

## Deviation

Two acceptance criteria failed, ACC-04 (SRS-PERF-022, the latency) and ACC-08 (the performance
gate, as part of the release checks). The evidence above shows, for both, that the programs of
release 0.7.0 fail the same way on the same machine on the same day, and that 0.8.0 is equal to
0.7.0 where the two were measured together: the cause is the reference machine as it ran that
day, not the release. No criterion was changed after it failed. The software lead (the author)
approved the release with this deviation on 2026-11-04, after reading this evidence. The next
release runs part 3 again and judges both criteria on its own evidence; if the machine stays
slower, the baseline of the gate and the margin of the latency limit are questions for a change
request, with the measurements of release 0.7.0 and 0.8.0 side by side.

## Corrective actions

- CAPA-0001 (tests that depend on the speed of the machine): **effective** at 0.8.0, closed. No
  test failed for a timing reason in CI, in the release checks or in the stress run of the period,
  the first period after `tests.waits` began to check every clock read, thread start and sleep
  mechanically; the gate and the latency limit above are measurements of the machine by design,
  not tests that the CAPA covers. Record in the CAPA.

## Known anomalies

Generated from the problem reports by `tools/anomalies.py` ([known-anomalies.md](../known-anomalies.md)):
three open reports, each evaluated again for this release and released with. No report of Part
VIII is open; MDQ-PR-054 to MDQ-PR-058 are closed.

- MDQ-PR-006 (service, relevant to safety): a port fault is noticed up to 20 ms late. Released
  with: a faulted run is incomplete in its verdict whatever the delay; Part VIII does not change
  the fault path, and the end-to-end checks name a damaged run as incomplete.
- MDQ-PR-007 (sorter, not relevant to safety): the sorter holds its last 104 ns of singles until
  more data arrives. Released with: no coincidence is lost; the end-to-end accounting balances
  every single at the end of a run.
- MDQ-PR-009 (sim, relevant to safety): simulation code is linked into the shipped server.
  Released with for a teaching project: simulated data is identifiable in the run record and in
  the diagnostics; Part VIII's link model is called only by the
  simulator and the test sender, not by the server.

## Risk

All 14 hazards of the risk file are closed (`risk/hazards.json`, test `docs.risk`). Part VIII
added no hazard and no risk control. No hazard's residual risk depends on a control that is not
verified (the trace matrix's risk-control column). The threat model, version 9, was reviewed for
this release: Part VIII added no element, flow or interface to the running MiniDAQ. The overall
residual risk is acceptable under the criteria of the risk management plan, section 3, as judged
by the software lead (the author) for this teaching release; a product release adds the clinical
expert's judgment (assumption: confirm with team).

## SOUP review

2026-11-04, for release 0.8.0 ([SOUP list](../soup-list.md), version 17, test `docs.soup`):
nlohmann/json 3.12.0 is still the latest release; the OpenSSL project lists no advisory for 3.0
after 2026-09-29, so the installed package `3.0.13-0ubuntu3.16` still patches every one, and
MiniDAQ 0.8 needs that version or later; pybind11 3.1.0 is the latest release, with no advisory;
the lock file audit reports 28 packages and none with a known vulnerability (`lock-audit.json`
in the evidence). Part VIII added no SOUP item.

## Requirements

The requirements were frozen against SRS version 21 in Part VIII; the eight differences up to
SRS version 23 are each explained by a change request (CR-0020: SRS-SIM-024, SRS-SYS-006 to
SRS-SYS-008, SRS-PERF-022; CR-0021: SRS-SVY-001 to SRS-SVY-003). The baseline is retaken at SRS
version 23 for this release (`srs-baseline.json`, test `docs.baseline`).

## Build

The release is built from the tag with the presets, as the checks did:

```sh
git checkout book-v0.8.0
ci/run_all.sh                                     # the six presets, tests and documentation tests
tools/static_analysis.sh build/clang-release
cmake --preset hardened && cmake --build --preset hardened   # the shipped binaries, reproducible
tools/make_sbom.py --validate -o minidaq-0.8.0.cdx.json
for p in 1 2 3 4; do tools/release_checks.sh OUT 600 $p; done   # this record's evidence
tools/acceptance.py OUT                                         # the acceptance verdict
```
