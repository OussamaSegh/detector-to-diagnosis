# MiniDAQ 1.0.0 release record

The record of SDP section 8 for release 1.0.0, the complete and packaged book. Evidence paths are
relative to this directory's parent, `docs/regulatory/`; the files are in
`measurements/release-1.0.0/` and were written by `tools/release_checks.sh` unless the notes below
say otherwise. Checked with Exercise 14.5's `check()` before the tag was made.

## Release

MiniDAQ 1.0.0, commit 517cd49456fa598028b3de70bacd8a28568b5f02, tag book-v1.0.0

The release checks ran on this commit with a clean working tree, in four parts in one worktree
(`commit.txt`, `commit-part-2.txt` to `commit-part-4.txt`), each ending with its summary line
(`release-checks.txt`). The commits on top of it change no source of the product (`git diff
517cd49 book-v1.0.0 -- minidaq/src minidaq/include minidaq/apps recon/src recon/include` is
empty) except the version string the programs and the Python packages report (`VERSION`,
`analysis/pyproject.toml`, `minidaq_analysis.__version__`, `recon/python/pyproject.toml`): this
release's record, evidence, version, problem report MDQ-PR-064 and documents. No source of the
product changed since release 0.8.0 either: `git diff book-v0.8.0 517cd49` over the same paths is
empty. The changes since 0.9.0 are in the tools and documents of the release checks: CR-0025 (the
gate and the latency criterion) and MDQ-PR-063 (the requirements freeze).

## Deviation

One acceptance criterion failed: ACC-04 (SRS-PERF-022, the latency), by one interval. No source
of the product changed since release 0.8.0, and the programs of release 0.9.0 fail the criterion
the same way on the same machine the same evening. The criterion was set by CR-0025 before these
checks ran and was not changed after it failed, and the soak was not run again to obtain a pass.

The cause of the latency peaks is not known. The steal time that CR-0025 added to the soak does
not show them, and is too coarse to rule the machine out. MDQ-PR-064 is opened to find the cause,
with a finer measure of the machine during the soak, before the latency limit is judged again.

The software lead (the author) approved the release with this deviation on 2026-11-08, after reading
this evidence, from three options: release with the deviation and MDQ-PR-064, hold the release
until the cause is found, or run the soak again (not recommended: it would hide a result).

## Known anomalies

Generated from the problem reports by `tools/anomalies.py` ([known-anomalies.md](../known-anomalies.md)):
four open reports, each evaluated again for this release and released with. MDQ-PR-062 and
MDQ-PR-063 are closed.

- MDQ-PR-006 (service, relevant to safety): a port fault is noticed up to 20 ms late. Released
  with: a faulted run is incomplete in its verdict whatever the delay; the server did not change.
- MDQ-PR-007 (sorter, not relevant to safety): the sorter holds its last 104 ns of singles until
  more data arrives. Released with: no coincidence is lost; the end-to-end accounting balances
  every single at the end of a run.
- MDQ-PR-009 (sim, relevant to safety): simulation code is linked into the shipped server.
  Released with for a teaching project: simulated data is identifiable in the run record and in
  the diagnostics; Appendix A records the architectural resolution a product would make.
- MDQ-PR-064 (pipeline, not relevant to safety): the end-to-end latency's 99th percentile
  exceeds 10 ms in about one 10 s interval in a hundred on the reference machine, with no change
  to the code. Released with: no single is lost or late beyond the sorter's window in those
  intervals (the soak counts no loss), and the latency is not a risk control of a hazard.

## Risk

All 17 hazards of the risk file are closed (`risk/hazards.json`, test `docs.risk`). No hazard's
residual risk depends on a control that is not verified (the trace matrix's risk-control column).
The threat model, version 12, was reviewed for this release: CR-0025 and MDQ-PR-063 change tools
of the release checks only, and add no element, flow or interface to the running server. The
overall residual risk is acceptable under the criteria of the risk management plan, section 3,
as judged by the software lead (the author) for this teaching release; a product release adds
the clinical expert's judgment (assumption: confirm with team).

## Requirements

The requirements were frozen against SRS version 26 at release 0.9.0; the one difference up to
SRS version 27 is explained by a change request (CR-0025: SRS-PERF-022). Since MDQ-PR-063 a
request accepted before the baseline no longer counts; the baseline names CR-0001 to CR-0024 as
such. The baseline is retaken at SRS version 27 for this release (`srs-baseline.json`, test
`docs.baseline`).
