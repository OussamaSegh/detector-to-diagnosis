# MiniDAQ 2.0.0 release record

The record of SDP section 8 for release 2.0.0, the Second Edition: the breaking changes of the
2.0.0 roadmap (C++23, the product build without the simulator, control API 3.0 and
configuration schema 2.0), the time base monitor and the boards' clock status, time of flight
in the reconstruction tool, and the maintenance plan. Evidence paths are relative to this
directory's parent, `docs/regulatory/`; the files are in `measurements/release-2.0.0/` and were
written by `tools/release_checks.sh` unless the notes below say otherwise. Checked with
`tools/release_record.py check` (Exercise 14.5's `check()`) before the tag was made.

## Release

MiniDAQ 2.0.0, commit c977dd967a3f39870efa8042bb9c2c7a0dfcece9, tag book-v2.0.0

The release checks ran on this commit with a clean working tree (`commit.txt`); the parts that
passed: 1, 2, 3, 4 (`release-checks.txt`), in one worktree (`commit.txt`, `commit-part-2.txt`
to `commit-part-4.txt`). Parts 1, 2 and 4 passed at their first attempt. Part 3 failed once on
the performance regression gate alone and passed when it ran again in full; the notes below
say why the first verdict is not a regression. An earlier run on d38fd04 is not evidence of
this release: its part 2 failed because the reconstruction tool's test ran past its timeout in
the coverage build, which c977dd9 fixes (the tool is no longer instrumented there; the report
never measured it).

The changes since 1.3.0. Breaking, each with its migration path in `docs/migration-2.0.md`:

- **CR-0029**: the product build (preset `product`) contains no simulator, and a shipped server
  refuses a synthetic source or simulated boards (RC-52 of H-06, closes MDQ-PR-009).
- **CR-0030**: control API 3.0 (every request names its API; renamed status fields) and
  configuration schema 2.0 (`source.type` required, renamed keys), with `tools/migrate_config.py`
  (TL-49) to convert a 1.x configuration (ADR 0036).

Not breaking: the C++23 baseline (CR-0028, ADR 0035); the time base monitor, register map 1.3
with the boards' clock status, API 3.1 and schema 2.1 (CR-0031, ADR 0037, RC-53 and RC-54);
time of flight in the reconstruction tool (CR-0032, ADR 0038, RC-55); the software maintenance
plan, `affects` in the problem reports, the SOUP items' end of support and the problem report
trends (CR-0033); the fixes MDQ-PR-072 to MDQ-PR-076; the internal audit of 2026-11-16 and
CAPA-0005. The commits on top of c977dd9 up to the tag change no product code: the tests and
the evidence of the coverage review, the trace matrix, the threat model's review and approval,
this record, and the version strings.

## Verification

Notes on the results:

- Build and tests: `ci/run_all.sh` built all six presets and ran 988 to 998 tests each, none
  failed, the documentation tests among them (`docs.trace`, `docs.baseline`, `docs.risk`,
  `docs.soup`, `docs.anomalies`, `docs.capa`, `docs.changes`, `docs.design_file`,
  `docs.interfaces`, `book.xrefs`, `book.errata`). The product build (CR-0029) built and passed
  its own 20 tests and its gates (`product.txt`).
- Static analysis: clang-tidy 18.1.3 and cppcheck 2.13.0 on the `clang-release` build: clean.
- Starters: every starter of the `Release` build fails at least one test and none hangs.
  Exercise 18.3's starter fails in the coverage build and its solution passes
  (`coverage-exercise.txt`).
- Stress: the concurrent tests, 100 repetitions each under ThreadSanitizer: 100 tests, no
  failure and no report.
- Property-based tests: the twelve properties with the wide search, no counterexample.
- Coverage: Clang source-based coverage of the debug tests, per software item (`coverage.txt`):
  90.8% of the lines and 80.8% of the branches over all items (89.8% and 79.5% at 1.3.0).
  Three class B items have a lower branch coverage than at 1.3.0: `config` (new branches of
  schema 2.0 and 2.1), `hw` (smaller since CR-0029 moved the simulated board out of it) and
  `rt` (no source changed; the machine granted every real-time request this time). The review
  of every untaken branch on the class B lines changed since 1.3.0 (`coverage-review.md`)
  found 23 lines in 9 files: tests were added after the checks (763946a, tests only) for 11 of
  them, and found that no test sent a request without an API version, which CR-0030 refuses
  (the server refused it; the case is now tested). The rest are infeasible or accepted with a
  reason.
- Performance, SRS-PERF-020: the pipeline ran at a median of 39.1 M singles/s in the `hardened`
  build (5 repetitions), 3.9 times the 10 M required (ACC-01: at least 20 M). It was 47.7 M at
  1.3.0 on another day; the gate, which runs both releases interleaved on the same machine,
  puts `BM_Pipeline` at 0.961 of 1.3.0 (p = 0.083), so most of the difference is the machine's
  day, and the rest is within the gate's threshold (the time base monitor costs about 3%,
  CR-0031). SRS-PERF-021: the list-mode writer wrote 18.2 to 20.9 M coincidences/s with fsync
  at close (3 runs of 200 M).
- Performance (the gate, CR-0025): release 1.3.0 (book-v1.3.0) and this commit, built with the
  `release` preset and run interleaved (`perf-ab/`): every benchmark at 0.961 to 1.078 of 1.3.0,
  none slower by a significant margin (`perf-gate.txt`). The first run of part 3 put
  `BM_HistogramRecord` at 0.917 (p = 0.0057) and failed the gate (`perf-ab-first/`). The
  benchmark's machine code is the same in both builds but for addresses
  (`perf-ab-first/bm_histogram-record.s`), no source it uses changed since 1.3.0, and the two
  builds run alternately by hand measured 2.10 to 2.72 ns (1.3.0) and 2.09 to 2.39 ns (this
  commit) per record; the second run put it at 1.002 (p = 0.51). A 2 ns benchmark moved by the
  machine, not a regression; no problem report. The trend against
  `benchmarks/baseline/book-vm.json` is recorded, not judged (`perf-trend.txt`).
- System tests: 38 test cases on the `release` build, none failed or skipped
  (`system-test-report.md`).
- Soak (SRS-SYS-003): 30 minutes at 1 M singles/s, 1.8 G singles, no loss and no fault; resident
  memory 30.5 to 31.2 MiB with a trend of -0.002 MiB/h (standard error 0.033).
- Latency (SRS-PERF-022): the 99th percentile stayed at or below 10 ms in 180 of the soak's 180
  intervals, at most 5.70 ms; steal time 0.46% on average, 0.78% at most. The second run of
  part 3 had a debug build and `llvm-cov` of the coverage review running beside it (README of
  the evidence), so the soak passed with more load than the release checks give it.
- End to end (SRS-SYS-006 to SRS-SYS-008): both acquisitions wrote the reference's records, 33
  of 33 checks passed, and the phantom's image has a radius of 80.25 mm and a center over
  periphery of 1.042 (`e2e.txt`).
- Fuzzing: each of the nine targets ran 600 s from its seed corpus with no crash, leak or
  timeout: config (8.1 M executions, 2,032 coverage points), decoder (30.1 M, 117), raw16
  (820 M, 14), protocol (0.85 M, 2,228), packet (12.4 M, 123), sorter (4.6 M, 324), listmode
  (32.3 M, 185), calibration (15,557, 1,657) and documents (1.5 M, 3,546), the target of
  CAPA-0005 for the files MiniDAQ wrote and reads again (`fuzz/<target>.txt`).
- Acceptance (`acceptance.md`, `tools/acceptance.py` in the worktree at this commit): 9 of 9
  criteria pass.
- Reproducible build: `tools/repro_check.sh` built the shipped programs of this commit in two
  checkouts of different paths; the two product archives are identical (`repro/repro.txt`).
- CI: this commit passed `ci` (every job, `fuzz-smoke` with `fuzz_documents`), `codeql` and
  `pages` (`ci-run.txt`). Of the commits after it, which change no product code, one failed
  `docs.trace` (fixed by regenerating the trace matrix) and one `codeql` run failed before its
  build on the runner's package sources. The release commit's own CI run is checked before the

## Internal audit

The [internal audit of 2026-11-16](../qms/internal-audit-2026-11-16.md) was held before the
release checks of this record, on the history since release 1.3.0: two minor nonconformities
and eight observations. N-1: the three breaking change requests had not been marked
implemented; corrected before the checks. N-2: the readers of the files MiniDAQ writes and reads
again were not treated as readers of untrusted input; three defects of that kind were found and
fixed (MDQ-PR-074 to MDQ-PR-076) and CAPA-0005 was opened. O-4 records the approval of the
eight controlled documents, given after the review of the release candidate (PR #18) and before
the checks.

## Corrective actions

CAPA-0005 is open: implemented (coding standard version 9, the fuzz target `fuzz_documents` in
CI and in the release checks, the three fixes), with its effectiveness check due at release
2.1.0 (`docs.capa`). This release's checks are the first part of that evidence: `fuzz_documents`
ran 600 s without a crash. CAPA-0001 to CAPA-0004 are closed, and none is due at this release.
The release checks' first failure on d38fd04 (the coverage build's timeout) and the gate's first
verdict were each found by the control designed for it and explained before the release, so no
CAPA was opened for them.

## Known anomalies

Generated from the problem reports by `tools/anomalies.py` ([known-anomalies.md](../known-anomalies.md)):
two open reports, each evaluated again for this release and released with. MDQ-PR-009 was closed
by CR-0029 and MDQ-PR-071 by the review of 1.3.0; MDQ-PR-072 to MDQ-PR-076 were reported and
closed since 1.3.0.

- MDQ-PR-006 (service, relevant to safety): a port fault is noticed up to 20 ms late. Released
  with: decided again for this release. No change of 2.0.0 depends on the delay: the time base
  monitor and the clock status (CR-0031) report through the status and the integrity verdict,
  not through the port monitor, and a faulted run is still incomplete in its verdict whatever
  the delay (RC-01). The decision of 1.3.0 and its two verifying tests stand.
- MDQ-PR-064 (pipeline, not relevant to safety): the end-to-end latency's 99th percentile
  exceeds 10 ms in about one 10 s interval in a hundred on the reference machine, with no
  change to the code. Released with: this release passes ACC-04 with 180 of 180 intervals (at
  most 5.70 ms), no single is lost in the soak, and the latency is not a risk control of a
  hazard. The finer measure of the machine that the decision asks for is still to be made.

## Risk

All 17 hazards of the risk file are closed (`risk/hazards.json`, test `docs.risk`). No hazard's
residual risk depends on a control that is not verified (the trace matrix's risk-control column).
CR-0029 adds RC-52 to H-06 (the product build cannot present simulated data as real), which
closes MDQ-PR-009; CR-0031 adds RC-53 (the time base monitor) and RC-54 (the boards' clock
status) to the time base; CR-0032 adds RC-55 of H-13 (no time of flight on an untrusted time
base). The threat model was reviewed for this release (version 17, approved as version 18): no
change request adds an element or flow, none of the 57 threats is open, and the gaps of
section 7 stand. The overall residual risk is acceptable under the criteria of the risk
management plan, section 3, as judged for this teaching release under the software lead's
standing delegation; a product release adds the clinical expert's judgment (assumption: confirm
with team).

## SOUP review

2026-11-16, for MiniDAQ 2.0 ([SOUP list](../soup-list.md), version 30, test `docs.soup`): the
trackers and advisories were read again. nlohmann/json 3.12.0 is still the latest release, with
no advisory. OpenSSL lists no advisory after the five of 2026-11-10 triaged for 1.2, and the
installed package is still `3.0.13-0ubuntu3.16`. CR-0033 found that the OpenSSL project's own
support for 3.0 ended on 2026-09-07: its fixes reach MiniDAQ through Ubuntu's backports, which
the known-anomaly review now reads first, and the move to OpenSSL 3.5 is planned with the next
platform definition. Every shipped item now records when its support ends. The lock file audit
reports 30 packages and none with a known vulnerability (`lock-audit.json`).

## Build

The release is built from the tag with the presets, as the checks did:

```sh
git checkout book-v2.0.0
ci/run_all.sh                                     # the six presets, tests and documentation tests
ci/run_all.sh product                             # the product build, without the simulator
tools/static_analysis.sh build/clang-release
cmake --preset product && cmake --build --preset product     # the shipped binaries
tools/repro_check.sh OUT                                     # two builds, compared byte for byte
tools/make_sbom.py --validate -o minidaq-2.0.0.cdx.json
tools/release_checks.sh OUT 600 resume                        # this record's evidence
tools/acceptance.py OUT                                       # the acceptance verdict
book/build.sh all both && book/build.sh boox both             # the book and the solutions
```
