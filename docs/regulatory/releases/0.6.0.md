# MiniDAQ 0.6.0 release record

The record of SDP section 8 for release 0.6.0 (the book's Part VI). Evidence paths are relative
to this directory's parent, `docs/regulatory/`; the files are in `measurements/release-0.6.0/`
and were written by `tools/release_checks.sh` unless the notes below say otherwise. Checked with
Exercise 14.5's `check()` before the tag was made.

## Release

MiniDAQ 0.6.0, commit 893413de586704b9e76ed10806f0ff76a3af8ec2, tag book-v0.6.0

The release checks ran on this commit with a clean working tree, in four parts in one worktree
(`commit.txt`, `commit-part-2.txt` to `commit-part-4.txt`), each ending with its summary line
(`release-checks.txt`). Three commits on top of it changed only tests, documents and a tool of
the checks, after the reviews of this release: ef85887 and 7fa5b1d (the tests of the coverage
review), and a9c5ba7 (MDQ-PR-045's test, MDQ-PR-046's threat model, CAPA-0001, the SOUP list and
the stress run's list of tests). The `release` and `hardened` programs built from a9c5ba7 are
identical, byte for byte, to those of the checked commit (`binaries-893413d.txt`,
`binaries-a9c5ba7.txt`), and the checks that those commits change ran again on a9c5ba7: the
debug tests and the documentation tests, the stress run with its longer list
(`stress-tsan-extended.txt`) and the coverage review (`coverage-a9c5ba7.txt`). The release
record, the version and the documents of this release are committed on top and change no code
except the version string that the programs report.

Notes on the results:

- Build and tests: `ci/run_all.sh` built all six presets and ran 859 to 863 tests each (the count
  differs by preset because some tests exist only in some builds; the timing tests of exercise
  solutions skip in sanitizer builds by design). The documentation tests in the same run include
  `docs.trace` (200 requirements, 193 verified by tests and 7 by measurement or inspection),
  `docs.srs`, `docs.risk`, `docs.soup`, `docs.anomalies`, `docs.capa` and `docs.design_file`.
  Part VI added the tests of the reconstruction tool, run against both projectors
  (`tools.recon`, `tools.recon_cpp`) and the C++ projector's own (`recon_tests`).
- Starters: every starter of the `Release` build fails at least one test and none hangs,
  including the 15 exercises of Part VI; Exercise 18.3's starter, which exists only in the
  coverage build, fails there and its solution passes (`coverage-exercise.txt`).
- Stress: the concurrent tests, 100 repetitions each under ThreadSanitizer on a loaded machine (8
  busy loops on 4 CPUs): 69 tests, no failure and no report. After MDQ-PR-045 the list also has the
  `ServiceManager`, `Health` and `SlowControl` tests; on a9c5ba7 the 95 tests of that list passed
  100 repetitions each under the same load, with no report (`stress-tsan-extended.txt`).
- Property-based tests: the twelve properties with the wide search (`MINIDAQ_PROP_CASES`), no
  counterexample.
- Coverage: Clang source-based coverage of the debug tests, per software item (`coverage.txt`
  on the checked commit, `coverage-a9c5ba7.txt` with the tests of the review). Every class B item
  covers at least 75% of its lines. The review of every untaken branch on a changed line of the
  11 class B source files changed since 0.5.0 (`coverage-review.md`) added seven tests (the
  calibration table's timestamps and file forms, an oversized profile, the singles counter, the
  simulator's delays alone, an empty batch and the identity table in the pipeline); they found
  no defect. They leave 26 lines, one infeasible and 25 accepted with their reasons, 23 of them
  the simulator's command-line options, which the measurements of Chapters 26 to 30 run. No
  item's branch coverage is lower than at 0.5.0; `processing` went from 78.1% to 89.7% of its
  branches, `pipeline` from 90.1% to 93.3% and `config` from 75.7% to 80.6%.
- Performance: the baseline gate failed, as at 0.5.0, on the same three rows: `BM_EnergyFilter/3`,
  `BM_HistogramRecord` and `BM_Pipeline` ran 10%, 18% and 21% slower than the baseline recorded for
  0.3.0 (p < 0.0001). That first run shared the machine with a build started by mistake during it;
  run again alone, the gate flagged the same three at 12%, 14% and 15% (`gate-rerun/`). An
  interleaved A/B of the release build of tag `book-v0.5.0` against that of this commit, on the same
  machine in one job (`tools/perf_ab.sh`, 5 rounds of 2 repetitions), found no regression: speeds
  0.91 to 1.09, none significant (row "performance"). Since Part VI the pipeline's decode stage also
  feeds the photopeak monitor and the singles counter on every batch; the benchmark applies no
  calibration table, and the A/B shows that this extra work did not make it measurably slower. The
  machine is slower than when the baseline was recorded, as at 0.4.0 and 0.5.0; the baseline is
  kept. SRS-PERF-020: the pipeline ran at a median of 33.9 M words/s in the `hardened` build (5
  repetitions, 29.3 to 34.9), 3.39 times the 10 M singles/s required. SRS-PERF-021: the list-mode
  writer wrote 9.28 to 10.45 M coincidences/s with fsync at close (3 runs of 200 M), at least 3.09
  times the 3 M required.
- System tests: 34 test cases on the `release` build, none failed (`system-test-report.md`).
- Soak: 30 minutes at 1 M singles/s, 1.8 G singles, no loss and no fault; resident memory 30.2
  to 30.9 MiB with a trend of +0.028 MiB/h (standard error 0.033); the 99th percentile of the
  end-to-end latency at most 17.4 ms per interval (`soak/`).
- Fuzzing: each of the seven targets ran 600 s on its own CPU from its seed corpus with no crash,
  leak or timeout: config (5.1 M executions, 1,900 coverage points), decoder (11.2 M, 101), raw16
  (476 M, 14), protocol (0.47 M, 2,881), packet (8.0 M, 122), sorter (1.9 M, 324) and listmode
  (14.0 M, 184) (`fuzz/<target>.txt`). The calibration table file of Part VI is read with the
  configuration's reader, which `fuzz_config` covers; a target of its own is planned for 0.7.0.
- CI: the GitHub runs of `ci.yml` on the checked commit and on a9c5ba7 passed every job, and
  `gates`, `perf` and `codeql` passed on a9c5ba7 too (`ci-run.txt`). The release commit on top
  changes only documents, measurements and the version; its own CI run is checked before the
  tag is made (SDP section 8).

## Corrective actions

- CAPA-0001 (tests that depend on the speed of the machine): **not effective** at 0.6.0. One
  test failed for a timing reason in the period, and it is one of MiniDAQ's own:
  `ServiceManager.TheWatchdogPingsOnlyWhileEveryLoopBeats` once in CI on ec4c2e6 (MDQ-PR-045),
  found at this release by reading every failed CI run of Part VI job by job. Part VI added no
  timing test. Further actions (record in the CAPA): code review checklist item 4.7, the stress
  run's longer list, and the SDP's rule that a failed CI run is investigated job by job; next
  check at release 0.7.0.

## Known anomalies

Generated from the problem reports by `tools/anomalies.py` ([known-anomalies.md](../known-anomalies.md)):
three open reports, each evaluated again for this release and released with. No report of Part VI
is open; MDQ-PR-045 and MDQ-PR-046, found by this release's reviews, are closed.

- MDQ-PR-006 (service, relevant to safety): a port fault is noticed up to 20 ms late. Released
  with: a faulted run is incomplete in its verdict whatever the delay; the calibration of Part VI
  does not change the fault path.
- MDQ-PR-007 (sorter, not relevant to safety): the sorter holds its last 104 ns of singles until
  more data arrives. Released with: no coincidence is lost; the sort stage's hold of the
  calibration (SRS-CAL-003) is before the sorter and does not change it.
- MDQ-PR-009 (sim, relevant to safety): simulation code is linked into the shipped server.
  Released with for a teaching project: simulated data is identifiable in the run record and in
  the diagnostics; Part VI's uncalibrated detector is part of the simulator and is identified the
  same way.

## Risk

All 13 hazards of the risk file are closed (`risk/hazards.json`, test `docs.risk`). Part VI
added H-11 (a wrong calibration table is applied), H-12 (corrections computed from inputs that do
not belong to the data) and H-13 (a reconstruction whose model differs from the measurement), with
the controls RC-35 to RC-44. No hazard's residual risk depends on a control that is not verified
(the trace matrix's risk-control column). The threat model, version 4, adds the calibration
tables as a data store (T-54 to T-57, MDQ-PR-046) and records unsigned tables as a gap; none of
its 57 threats is open. The overall residual risk is acceptable under the criteria of the risk
management plan, section 3, as judged by the software lead (the author) for this teaching
release; a product release adds the clinical expert's judgment (assumption: confirm with team).

## SOUP review

2026-11-03, at release 0.6.0 ([SOUP list](../soup-list.md), version 12, test `docs.soup`):
nlohmann/json 3.12.0 is still the latest release and none of its known defects affects a
requirement; the OpenSSL project lists no advisory for 3.0 after 2026-09-29, so the installed
package `3.0.13-0ubuntu3.16` still patches every one, and MiniDAQ 0.6 needs that version or
later; pybind11 3.1.0, new in Part VI as a tool of the reconstruction, is the latest release.

## Build

The release is built from the tag with the presets, as the checks did:

```sh
git checkout book-v0.6.0
ci/run_all.sh                                     # the six presets, tests and documentation tests
tools/static_analysis.sh build/clang-release
cmake --preset hardened && cmake --build --preset hardened   # the shipped binaries, reproducible
tools/make_sbom.py --validate -o minidaq-0.6.0.cdx.json
for p in 1 2 3 4; do tools/release_checks.sh OUT 600 $p; done   # this record's evidence
```
