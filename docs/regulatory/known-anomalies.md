| ID | Item | Anomaly | Relevant to safety | Why | Decision |
|---|---|---|---|---|---|
| MDQ-PR-006 | service | A port fault is noticed up to 20 ms late | yes | Data acquired in those 20 ms after a fault is part of a run that ends in a fault anyway; the fault is reported and the run is not used. No data is presented as complete. | Release with it. Reviewed against the risk file for release 0.3.0: a faulted run is incomplete in its integrity verdict whatever the delay (assess_integrity, RC-01), and H-05 covers the interrupted scan; 20 ms more data in a run that ends in a fault changes neither sequence of events nor harm, so no hazard needs a faster reaction. Chapter 15 was to decide this and did not; the release review did. Decided again for release 1.3.0 (roadmap 2.0.0, theme B), with the cost of the fix weighed: a faster reaction needs every port to wake the monitor from its own thread (the UDP receiver, the sink's I/O thread, the slow control), a callback into the service across the layers and a new lock order to prove, in class B code, to shorten by at most 20 ms a run that ends in a fault anyway. Kept open as a known anomaly, deliberately, because the behavior exists and a release must state it; RunIntegrity.AFaultMakesTheRunIncompleteWithoutALossCounter and AcquisitionService.DetectorFaultStopsTheRunAndNeedsAReset verify the two properties the decision rests on. To be decided again only if a hazard analysis finds a harm that depends on the delay. |
| MDQ-PR-009 | sim | Simulation code is linked into the shipped server | yes | A clinical acquisition configured with a simulated source would produce plausible but invented data. The run record states the source type and metadata carries 'simulated', so the data is identifiable. | Release with it for 0.3.0 (MiniDAQ is a teaching project); a product build excludes the simulator or refuses it outside service mode. |
| MDQ-PR-064 | pipeline | The end-to-end latency's 99th percentile exceeds 10 ms in about one interval in a hundred, with no change to the code | no | No single was lost or arrived after the sorter's window in those intervals (the soak counts no loss), the latency is not a risk control of a hazard, and the delay before a fault is noticed is MDQ-PR-006, which does not depend on it. | Release 1.0.0 with a recorded deviation for ACC-04. Find the cause with a finer measure of the machine during the soak (the steal and run-queue time of the pipeline's threads per second, from /proc/self/task/*/schedstat) before the latency limit is judged again. |
| MDQ-PR-071 | output | verify-run ends with an exception on a signed record whose digest has a field of the wrong type | no | The record must first pass the Ed25519 check with a key the site installed, so only a trusted signer can make such a record, and the server writes the fields with the right types. The tool then stops with an uncaught nlohmann::json type_error instead of a refusal: no run is believed that should not be, and the failure is visible. | Release 1.3.0 with it: the defect needs a malformed record signed with a trusted key, and the release checks ran on the code as it is. Fix in milestone 2.0.0-dev: verify_signed_run checks that sha256 is a string and bytes an unsigned number before it reads them, with a test that signs such a record (the test of malformed signed records added in this review shows the pattern). |
