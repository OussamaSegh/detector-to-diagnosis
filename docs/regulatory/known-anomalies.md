# MiniDAQ known anomalies

Generated by `tools/anomalies.py --write` from [the problem reports](problem-reports.json).
Do not edit by hand: the test `docs.anomalies` fails when this file is out of date.

4 open problem reports, 3 of them relevant to safety.

| ID | Item | Anomaly | Relevant to safety | Why | Decision |
|---|---|---|---|---|---|
| MDQ-PR-006 | service | A port fault is noticed up to 20 ms late | yes | Data acquired in those 20 ms after a fault is part of a run that ends in a fault anyway; the fault is reported and the run is not used. No data is presented as complete. | Release with it; Chapter 15 decides whether a hazard needs a faster reaction. |
| MDQ-PR-007 | sorter | The sorter holds its last 104 ns of singles until more data arrives | no | The singles are processed at the end of the run, so no coincidence is lost; only their latency grows while the source is silent. | Release with it; time markers from the readout would flush the sorter (Chapter 23). |
| MDQ-PR-008 | protocol | The control API has no authentication or encryption | yes | A local attacker or a misdirected script can stop a scan or change its settings; the audit trail records it but does not prevent it. | Do not release for use beyond a test bench before Chapter 17's controls are in place. |
| MDQ-PR-009 | sim | Simulation code is linked into the shipped server | yes | A clinical acquisition configured with a simulated source would produce plausible but invented data. The run record states the source type and metadata carries 'simulated', so the data is identifiable. | Release with it for 0.3.0 (MiniDAQ is a teaching project); a product build excludes the simulator or refuses it outside service mode. |
