# IEC 62304: the software life cycle {#ch14}

::: box-why
A medical device software team plans its work, writes requirements and keeps records as the
regulations require. For the software of a medical device, that means IEC 62304. It is the standard that says which activities a software team performs, which
outputs those activities leave behind, and how both depend on how much harm the software could
contribute to. It does not tell you how to write a sorter, and it does not ask for any
particular method. It asks that you plan the work, write requirements someone can test, design
an architecture with named parts, verify each part, know every piece of software you did not
write, keep everything under configuration control, and handle every problem through a
recorded process. This chapter walks through the standard with MiniDAQ as the product: by the
end, MiniDAQ has a development plan, 114 testable requirements, classified software items, a
SOUP list with a real known-anomaly review, problem reports, and a trace matrix that the build
regenerates from the tests.
:::

**A day in the life.** The notified body's auditor is in the building, and the quality manager
asks you to join the session on software. The auditor opens the trace matrix, picks a line at
random, SRS-OUT-003, "the list-mode sink shall make each file durable before the file has its
final name", and asks to see the evidence. You open the test it names,
`ListModeSink.MakesEachFileDurableBeforeItsFinalName`, show that it runs for every fsync policy,
and open the CI log of the release where it passed. The auditor nods and asks a harder question:
the test uses a fake file system, so how do you know that the real one behaves the same? You
show the crash test in the measurements and the integration test that writes real files through
the service. Then the auditor asks which software item the requirement belongs to, what its
safety class is, and why. The answer is in the architecture description, with the hazard it
traces to. Twenty minutes, one requirement, and nothing had to be prepared for the visit. That
is what a life cycle that leaves evidence behind buys you, and what this chapter builds.

## What IEC 62304 is

### The intuition

A medical device regulation asks "how do you know?" (Chapter 13). For software, the honest
answer has two parts. The first is about the product: requirements, a design, tests that pass.
The second is about the process that produced it: the product you test today is not the one you
ship next month, so the regulator needs confidence that the *way* you make changes keeps the
product safe. IEC 62304 is about the second part. It describes the processes of a software life
cycle and what each must produce, and it scales the rigor of those processes to the harm the
software could contribute to.

Two consequences shape everything else. First, the standard never inspects code quality
directly. A team can conform with terrible code, as long as it has planned, specified,
designed, verified and controlled that code as described; and a team with excellent code fails
an audit if nobody can show which requirement a test verifies. Second, the standard is
indifferent to method. Waterfall, iterations, continuous integration, pair programming: any of
them works if the activities happen and their outputs exist and agree with each other by the
time you release. That is why the rest of this chapter speaks of outputs and checks rather
than of phases.

### Scope and structure

IEC 62304 applies to medical device software: software that is itself a medical device and
software that is part of one. The NeuroLF's DAQ software is the second kind. The current
edition is IEC 62304:2006 with Amendment 1 of 2015, usually written IEC 62304:2006+A1:2015;
in Europe it is published as EN 62304, and, as Chapter 13 showed, it is not harmonised under
the MDR, yet notified bodies and FDA (where it is a recognized consensus standard) expect it.

The standard has five process clauses after its general requirements:

- **Clause 4, general requirements:** a quality management system, risk management according
  to ISO 14971, software safety classification, and, since the amendment, how to treat legacy
  software that was developed before the standard was applied.
- **Clause 5, software development:** planning (5.1), requirements analysis (5.2),
  architectural design (5.3), detailed design (5.4), unit implementation and verification
  (5.5), integration and integration testing (5.6), system testing (5.7) and release (5.8).
- **Clause 6, software maintenance:** how changes after release are planned, analyzed and
  implemented.
- **Clause 7, software risk management:** how software contributes to hazardous situations,
  how risk controls in software are specified and verified, and how changes are analyzed for
  their effect on safety.
- **Clause 8, configuration management** and **clause 9, problem resolution**: identifying
  every configuration item, controlling changes, recording status, and handling every problem
  through reports that are investigated, evaluated, resolved and verified.

Each activity in clauses 5 to 9 is marked with the safety classes it applies to. The
amendment of 2015 changed several of those markings and the classification itself; if you read
an older summary, check it against the amended text (verify: the class table of your copy).

### The second edition

A second edition has been in preparation for years. A draft that would have widened the scope
to all health software and replaced the three classes with two levels of process rigor did not
pass its vote in 2021, and work started again (verify: the current draft's content). At the
time of writing its publication is expected in 2028 (verify: the IEC project page). Until a
new edition is published and your quality system adopts it, the 2006+A1:2015 text is the one
your technical documentation claims, and the one this chapter follows.

## Software safety classification

### The intuition

Not all software in a device deserves the same effort. A bug in the code that draws the
operator's logo should not cost the same documentation as a bug in the code that decides which
photons form a line of response. IEC 62304 makes that difference explicit with three classes,
decided by the worst harm that a failure of the software could contribute to:

- **Class A:** no injury or damage to health is possible.
- **Class B:** non-serious injury is possible.
- **Class C:** death or serious injury is possible.

The amendment turned this into a short decision, shown in the figure below in this book's
words. First: can a failure of the software contribute to a hazardous situation at all? If not,
class A. If it can: once you take into account the risk controls *outside* the software (the
hardware, the clinical workflow, a person who reviews the result), is the remaining risk
acceptable? If yes, class A again. If not, the severity of the possible harm decides between B
and C.

```{.dot include="book/src/diagrams/ch14-classification.dot" caption="Software safety classification after Amendment 1, in this book's words. Probability does not appear: the standard tells you to assume that software can fail." width="85%"}
```

Two features of the decision surprise newcomers. Probability plays no part: the classification
asks whether harm is *possible*, and the standard tells you to assume that the software can fail
rather than to argue that it will not. And the risk controls that lower the class must be
outside the software being classified. A check inside the sorter that catches its own bug does
not make the sorter class A; a physician who reviews every image, or a hardware interlock, can
change the answer, and then the classification depends on them and must say so.

### Who decides, and from what

The manufacturer decides, from the risk analysis. ISO 14971 (Chapter 15) produces the hazards,
the hazardous situations and the severity of the possible harms; the classification reads them.
That is why IEC 62304 cannot be applied without ISO 14971: there is no classification without a
risk analysis. Until a software system has been classified, the standard treats it as class C
(verify: the wording in clause 4.3 of your copy), so an unclassified system costs the most.

The software safety class is not the device's MDR class. The NeuroLF is MDR class IIa (Chapter
13); its software items could be class A, B or C. The MDR class decides the conformity
assessment route; the safety class decides how your team works on each item. Different
decisions, different owners, different documents.

### Items, systems and segregation

A software system is decomposed into software items, and items into smaller items down to
software units, the smallest pieces the team chooses to verify on their own. The standard leaves
the granularity to you. What it fixes is inheritance: an item has the class of the system or
item it belongs to, unless the manufacturer documents why a lower class is justified. The only
justification the standard accepts is **segregation**: the lower-class item is separated from
the higher-class one so that its failure cannot affect it. The architecture must say what the
segregation is and why it is effective.

What counts as effective is the hard part. Two items in one process share an address space: a
buffer overflow in the logger can corrupt the sorter's memory, a thread that deadlocks can starve
the pipeline, an exception that escapes can end the process. So segregation inside a process is
very hard to argue, and most teams do not try. Separate processes, with the operating system's
memory protection between them and an interface that validates everything it receives, are the
usual segregation in software. Separate processors or separate hardware are stronger still.

### A worked example: classifying MiniDAQ

MiniDAQ's classification lives in `docs/architecture/software-items.json` and in section 4 of the
architecture description. It starts from four preliminary hazards, written for the
classification and to be replaced by Chapter 15's risk analysis:

- **HZ-1:** coincidences are lost, duplicated or altered without being reported, so an image
  with wrong values or artifacts is read.
- **HZ-2:** an acquisition fails or stops before its end, so the scan is repeated with a second
  injection or the diagnosis is delayed.
- **HZ-3:** data is recorded with wrong or unidentifiable settings.
- **HZ-4:** an unauthorized party controls the acquisition.

For each, the classification needs the severity of the worst harm *after* the risk controls
outside the software. A brain PET image is read by a trained physician, the scanner passes daily
quality control with a phantom, and the result is interpreted with the patient's clinical
picture. MiniDAQ assumes that with these controls the worst harm of HZ-1 is a non-serious injury
(a delayed diagnosis that is corrected), and the same for the others (assumption: confirm with
team). That is a judgment, and it is the most important sentence in the classification: if the
risk analysis decides that a subtly wrong image could lead to a serious injury, for example an
unnecessary invasive procedure, the data path becomes class C.

With that judgment, every item that can contribute to a hazard is class B: the sorter (HZ-1),
the pipeline (HZ-1 and HZ-2), the configuration reader (HZ-3), the control protocol (HZ-2 and
HZ-4), and so on. Then the interesting cases:

- **The metrics and the audit log** contribute to no hazard: a broken latency histogram or a
  missing audit record harms nobody. Alone, they would be class A. But they run in
  `minidaq_server`, in the same process as the sorter, and nothing segregates them; a memory
  error in the histogram code could corrupt the sorter. So they are class B, developed and
  verified like the sorter.
- **The client `minidaq_ctl`** is class A. It runs in its own process and reaches the server
  only through the control protocol, whose input the server validates completely (SRS-CTL-020
  to SRS-CTL-022). The worst a defective client can do is send a valid but wrong command, which
  the server reports back. The segregation argument rests on two things that are verified:
  process isolation, and the protocol's input validation.
- **The simulator** is the uncomfortable one. It is a test tool, but `minidaq_core` contains it
  and `minidaq_server` can select it with one configuration key. A clinical acquisition
  configured with a simulated source would produce plausible, invented data (HZ-3). So it is
  class B and a problem report (MDQ-PR-009): a product build should leave it out.
- **The benchmarks and measurement programs** are not shipped and have no class; they are tools,
  controlled as Chapter 20 describes.

The software system is class B, its highest item. A tool checks the mechanical part of this:

```{.python include="tools/check_items.py" snippet="rules"}
```

The test `architecture.items` runs it on every build, together with two more checks: every source
file belongs to exactly one item, so a new file cannot escape classification, and every
requirement of the SRS names an item of the list. The judgment, which hazards and how severe,
stays with people; the rules that follow from it are enforced.

::: box-mistakes
- **Classifying by how complex the code is.** The class follows the harm, not the size: a
  five-line function that selects the energy window can be the most important code in the
  device.
- **Claiming that an internal check lowers the class.** Risk controls inside the software are
  verified as requirements; only controls outside it enter the classification.
- **Claiming segregation between threads or libraries in one process.** Without a mechanism that
  stops one item's failure from reaching the other, there is no segregation. Write "none" and
  classify accordingly.
- **Forgetting the test code you ship.** Simulators, debug commands and service backdoors in the
  release binary are items too, and they inherit the class of their process.
- **Never revisiting the classification.** A new hazard, a removed external control or a merged
  process changes the class. The classification is a controlled document with a history.
:::

## The development process

### Planning (5.1)

The software development plan says how the team will do everything else: the life cycle model,
the deliverables, how requirements trace to tests, which standards, methods and tools are used,
how configuration and changes are managed, how problems are handled, how integration and
verification are planned, and how the release is made. In a company with a quality system, most
of the plan points to existing procedures rather than restating them. The plan is also a living
document: it is updated as the work proceeds, under the same document control as the rest.

MiniDAQ's plan, `docs/regulatory/sdp.md`, is short because the repository already does most of
what it describes. Its section 6 is the verification table: the six build presets of Chapter 7,
the documentation checks of this chapter, static analysis with zero findings, the exercises,
fuzzing at each release, the performance requirements measured at each release, and code review
of every change. Its section 2 maps each activity of clause 5 to the place in the repository
where its output lives, which is the first thing an auditor asks for.

### Requirements analysis (5.2)

A software requirement says what the software shall do, precisely enough that someone else can
verify it. The standard lists what the requirements should cover: functions and capabilities,
inputs and outputs, interfaces, alarms and warnings, security, the user interface, data
definitions, installation, operation and maintenance, networking, and the requirements that
implement risk controls. It also asks that the requirements are verified: that they do not
contradict each other, are unambiguous, can be tested, are uniquely identified and trace to the
system requirements or risk controls they come from.

Most bad requirements fail in a few ways, and each has a fix:

- **Vague words** ("fast", "robust", "appropriately") give the tester nothing to measure.
  Replace them with the quantity and its unit.
- **Two requirements in one sentence** ("shall sort and shall report") cannot pass or fail as
  one. Split them, or rewrite them as one behavior.
- **"Should" and "may"** make a requirement optional. A requirement says "shall".
- **A bare number** ("a window of 4000") leaves the unit to the reader. Picoseconds and
  nanoseconds differ by a factor of a thousand.
- **Design disguised as a requirement** ("shall use a ring buffer") ties the requirement to one
  implementation. State the behavior that matters (no allocation on the hot path, a bounded
  latency) and let the architecture choose.

Some of these faults are mechanical, and a tool can find them. MiniDAQ's `tools/req_lint.py`
reads every requirement row and reports the form faults:

```{.python include="tools/req_lint.py" snippet="rules"}
```

It is crude on purpose: a regular expression decides whether a number has a unit. It catches the
draft that says "the window shall be 4000", and it lets through the subtle fault that makes a
requirement wrong rather than vague. Its job is to make review time go to content.

### A worked example: rewriting the sorter's first draft

Exercise 14.2's starter holds the kind of first draft every team writes:

> SRS-SRT-101. The sorter shall find coincidences quickly and reliably.
> SRS-SRT-103. The sorter shall use an energy window of 435 to 585 and shall reject other singles.

The first has no measurable content at all. "Quickly" becomes two requirements, one for
throughput and one for latency, and each needs a number and a method. Throughput: "The sorter
shall process at least 30,000,000 singles/s on one core of the reference machine with the
`hardened` preset", verified by measurement, because a unit test cannot measure a rate that
depends on the machine. Latency is subtler. The sorter cannot emit a coincidence until a later
single proves that its window is closed (Chapter 10), so a requirement with a time ("within 1
ms") would be false whenever the source falls silent. The testable form states the event:
"The sorter shall output a coincidence at the latest when it receives a single inside the
energy window that is more than the window plus the delay later than the coincidence's first
single." "Reliably" turns into the accounting requirement: every single received is counted as
rejected by energy, out of order, alone, or in a window of a counted size.

The second draft has a bare number, two "shall"s, and a hidden question: is 585 keV inside the
window? The rewrite: "The sorter shall pass to coincidence search only singles whose energy is
inside the inclusive energy window in keV (default 435 to 585 keV)." One requirement, a unit,
and "inclusive", which is what the test `CoincidenceSorter.EnergyGateAndOrder` checks.

Writing the twenty requirements of Exercise 14.2 against the code also finds things. Checking
the multiples requirement against `coincidence_sorter.hpp` shows four policies, not three:
`keep_if_only_one_good` was missing from the first version of MiniDAQ's own SRS, and the delayed
window turned out to be disabled by a delay of zero, which the configuration check allows. Both
are now in the SRS. A requirement checked against the code is a review of the code, too.

### MiniDAQ's SRS

Before this chapter, MiniDAQ's tests carried `REQ:` tags for requirements that existed only as
IDs: Chapters 1 to 12 named 111 of them, and none had a text. `docs/regulatory/srs.md` now
defines every one, in areas that follow the code (CFG for configuration, SRT for the sorter, OUT
for the list-mode output, and so on), with the item that implements it and its verification

```

Writing them meant reading each test and stating what it actually checks, which found
differences: the first draft of SRS-FMT-002 said the raw single parser rejects a bad magic number

negative times, crystals and energies. The text was corrected to the test. Three requirements

requirement had stated. The total is 114: 112 verified by test and 2 by measurement.

### Architectural design (5.3)

The architecture turns the requirements into named software items with defined interfaces. The
standard asks that it describes the items and their interfaces (including those to SOUP), states
the functional and performance requirements of each SOUP item and the hardware and software the
SOUP needs, identifies the segregation needed for risk control, and is verified against the
requirements.

MiniDAQ's architecture description has done most of this since Chapter 6: the layers, the
interfaces table, the threads, the SOUP section. Version 5 adds the software items and their
classes (section 4) and rewrites the segregation section (section 10) to say plainly that the
server process has none inside it, which is the argument behind every class B in the table.

### Detailed design and units (5.4)

For class B, the standard asks that the items are refined into software units. For class C it
asks more: a documented detailed design of each unit and of its interfaces, detailed enough to
implement from, and verified against the architecture. This is the largest difference between
B and C, and it is why teams try hard to keep items out of C.

MiniDAQ's units are its classes and free functions with their headers. The headers are the
detailed design at class B: each documents its contract (for example the ports in
`control/ports.hpp`, or the sorter's rules at the top of `coincidence_sorter.hpp`), and the
format specification `docs/formats/mdq-l1.md` is the detailed design of the list-mode codec.
For class C, a team writes the same contracts down before the code and reviews them as a
design: preconditions, postconditions, error behavior, timing, memory use.

### Implementation and unit verification (5.5)

Every unit is implemented, and for class B and C the team defines how a unit is verified and
what its acceptance criteria are, then verifies it. Class C adds acceptance criteria the
standard lists, such as proper event sequence, data and control flow, fault handling,
initialization, boundary conditions and memory management (verify: the full list in clause 5.5.4
of your copy). Verification is not only testing: code review and static analysis are
verification too, and the plan says which applies to what.

MiniDAQ's development plan states its unit acceptance criteria in one sentence: a unit is
accepted when its tests pass under every preset, static analysis reports nothing, its interface
is documented in its header, and every requirement it implements is traced. Chapter 7's tooling
makes three of the four automatic.

### Integration, system testing and release (5.6 to 5.8)

Integration testing checks that the items work together as the architecture says: MiniDAQ's
service tests run the real pipeline with scripted ports, the protocol tests run the real server
over a socket, and the list-mode test writes real files through the service. System testing
checks the whole software against its requirements; for MiniDAQ that is the unit and
integration tests that verify each requirement, plus the measurements of the performance
requirements. The standard asks that the results of each are recorded with enough detail to
repeat them: which version, which configuration, which tester, which result.

Release closes the cycle. Before it, the team makes sure that verification is complete, that the
known residual anomalies are documented and evaluated, that the released versions are
identified, that the way the release was built is documented so it can be repeated, and that the
release is archived and can be delivered without corruption. MiniDAQ's development plan turns
that into a six-point release record (section 8 of `sdp.md`), and Exercise 14.5 turns the record
into a check that refuses "pass (2 flaky)".

## SOUP

### The intuition

SOUP, software of unknown provenance, is software that is already developed and generally
available, or that was developed without a process you can show, and that you use in your
device. Every open-source library is SOUP. So are the C++ standard library, the C library, the
Linux kernel, a vendor's driver, a commercial database. You did not develop it under your
process, so you cannot show its requirements, design and tests. What you can show is that you
know exactly what it is, what you need it to do, how you checked that it does, and what is known
to be wrong with it.

### What to record

For every SOUP item the standard asks for its identification (title, manufacturer, and a unique
version designation), and for class B and C its functional and performance requirements, the
hardware and software it needs, and an evaluation of its published anomaly lists against your
use. The risk analysis then treats a SOUP failure like any other software failure: a SOUP item
can contribute to a hazardous situation, and your risk controls must account for that.

The answer to the most common question, whether you may use an open-source library in class C
software, is yes. The standard does not forbid SOUP in any class. It asks you to identify it,
specify what you require of it, include its failures in the risk analysis, evaluate its known
anomalies, and verify your use of it, and the effort rises with the class: in class C, the
argument that a library's failure is controlled is part of the class C evidence.

Identification means exact. "nlohmann/json 3.11" is not an identification; "nlohmann/json
3.11.3, archive `json.tar.xz` with SHA-256 `d6c65aca…`" is, because it names the same bytes for
everyone. MiniDAQ pins every dependency by commit or hash in `cmake/Dependencies.cmake`, and from
this chapter on `tools/check_soup.py` (test `docs.soup`) fails if the SOUP list does not name
every pin and version of the build, or if a shipped item's known-anomaly review is not dated for
the current MiniDAQ minor version. A minor release therefore cannot be built without someone
reviewing the shipped SOUP again.

### A worked example: reviewing nlohmann/json 3.11.3

A known-anomaly review asks one question per reported defect: does it affect a requirement we
have of this item, given how we use it? MiniDAQ's first real review, recorded in section 4 of
`docs/regulatory/soup-list.md`, went like this.

The pinned version is 3.11.3. The only later release at the time of the review was 3.12.0,
published on 11 April 2025; its release notes list no vulnerability and fourteen fixes. For each
fix the review asks whether MiniDAQ uses the affected feature, and answers it by reading the
code, not by guessing. MiniDAQ parses strings only (no `FILE*`), uses no SAX interface, never
converts an enum to JSON directly, does not define `JSON_DIAGNOSTICS`, never compares
default-constructed iterators and uses no tuples. Twelve fixes are thereby irrelevant, one more
(a regression in the input adapters) probably is, with a *verify* on its trigger.

One fix matters: integers could be parsed as floating-point numbers when `errno` held `EINTR`
(issue #4506). MiniDAQ's control server parses each request after `poll()`, and `poll()` can
return `EINTR` when a signal arrives, so the condition is plausible (verify: the exact condition
in the fix). The effect is the next question: what does MiniDAQ do with an integer that arrives
as a float? The configuration reader requires integers to be integers (`is_number_integer()` for
signed and `is_number_unsigned()` for unsigned values), so it refuses the value with a
`config_error` and nothing is configured. The worst case is a refused request that the operator
sends again; no wrong setting can be accepted. The review records this as a known anomaly
(MDQ-PR-005), evaluated as not relevant to safety, and decides to keep 3.11.3 for MiniDAQ 0.3.0
and plan the upgrade as a change.

Two things in that review are typical. The decision rests on a fact about MiniDAQ's code (the
integer check), so that fact is now load-bearing: if someone later reads a number without it,
the evaluation becomes wrong. And the review is incomplete in a way it says: it read the release
notes, not the open issues of the tracker, which a real review also reads.

### The platform is SOUP too

The C++ standard library, the C library and the kernel are SOUP whose versions MiniDAQ does not
pin: the acquisition PC's operating system supplies them. They are identified by the platform
definition (Chapter 25), and a platform change, such as Exercise 13.2's move to a new Ubuntu
release, is a SOUP change with the same review. The compilers and analyzers are not shipped, but
their output is evidence, so they are listed with their versions and qualified as tools
(Chapter 20).

::: box-mistakes
- **"Latest" or a version range as identification.** Two builds a week apart then contain
  different SOUP. Pin by commit or hash and name the pin in the list.
- **Copying the vendor's feature list as the requirements.** The requirements are what *your*
  software needs from the item, which is usually a small part of what it offers.
- **An anomaly review that lists issues without evaluating them.** The output is a decision per
  relevant anomaly, with the reason, not a copy of the tracker.
- **Reviewing once.** New anomalies are found after you pin. Review at each release and when the
  supplier announces a security fix.
- **Forgetting the SOUP that is not a library:** the kernel, the C library, a container base
  image, a driver, firmware on the network card.
:::

## Traceability

### The intuition

Traceability answers four questions in both directions. For every requirement: which design
implements it, which code, which test verifies it? For every test: which requirement does it
verify? For every risk control: which requirement implements it, and which test shows it works?
For every change: which requirements, items and tests does it touch? The standard asks for
traceability between system requirements, software requirements, software system tests and the
risk control measures implemented in software, and the development plan says how it is kept.

A traceability matrix kept by hand in a spreadsheet is wrong within a week of being written: a
test is renamed, a requirement split, a file moved. The fix is to put the trace where it cannot
drift from the code: in the code.

### Tags in the tests

MiniDAQ's tests have carried tags since Chapter 1:

```cpp
TEST(ListModeSink, MakesEachFileDurableBeforeItsFinalName) {
  // REQ: SRS-OUT-003
```

`tools/trace_matrix.py` reads the requirements from the SRS and the tags from every test in
`minidaq/tests/`, `fuzz/` and `tools/`, assigns each tag to the test above it, and splits a tag
that lists several IDs:

```{.python include="tools/trace_matrix.py" snippet="parse"}
```

Then it checks the trace in both directions:

```{.python include="tools/trace_matrix.py" snippet="check"}
```

A requirement verified by test without a test is a gap; a test that names a requirement the SRS
does not define is a typo or a deleted requirement; a requirement verified by measurement or
inspection without its evidence is a claim without proof. Each fails the test `docs.trace`, which
also fails if the committed `docs/regulatory/trace-matrix.md` differs from the one the sources
produce. The matrix names tests by file and name, never by line number, so that it changes only
when the trace does: a pull request that moves a test does not touch it, and one that removes the
last test of a requirement fails before review.

Today the matrix holds 114 requirements, 112 of them verified by at least one of 136 tests (the
counts grow in each later chapter; every count in this book is the one at its chapter's tag), and
the other two by the measurements in the performance budget. The trace from requirement to
design is the item column of the SRS, checked against `software-items.json`; the trace from
item to code is the item's file list, checked against the source tree. Chapter 15 adds the last
link, from hazard to risk control to requirement.

### What the matrix cannot prove

A tag is a claim that a test verifies a requirement, not a proof. A test tagged SRS-SRT-001 that
checks only that the sorter returns a vector would pass the matrix and verify nothing. So the
review still reads each new tag against its requirement, and the matrix's real service is to
tell the reviewer where to look: the diff of `trace-matrix.md` in a pull request is the change to
the trace, line by line.

## Maintenance, problems and configuration

### Configuration management (clause 8)

Configuration management means that every item of the software, the documents and the SOUP is
identified with its version, that changes to them are controlled, and that the team can say at
any time which versions make up a release and what changed between two releases. Git does most
of the identification: a commit names an exact state of every file, a tag names a release. What
git does not do is decide which changes are allowed: that is change control, a reviewed pull
request with a stated reason, and, after release, a change control board and the regulatory
assessment of Chapter 13. MiniDAQ's plan adds two things that git alone misses: the SOUP pins
mirrored in the SOUP list and the SBOM, and the build tools' versions recorded in the CI logs.

### Problem resolution (clause 9)

A problem report is opened for every problem found in released software, or in software under
configuration control, depending on your plan. The standard asks that each is investigated and
evaluated for its relevance to safety, that the relevant parties are told, that the fix goes
through change control, that the fix is verified, that records are kept, and that reports are
analyzed for trends.

MiniDAQ's reports live in `docs/regulatory/problem-reports.json`. The first nine come from this
book: four closed problems found by fuzzing, measurement and development in earlier chapters,
such as the configuration reader that crashed on `6e688` (Chapter 7) and the sequence tracker
that counted a jump of 2^31 as two billion lost packets (Chapter 9), and five open ones, such as
the 20 ms delay before a port fault is noticed and the missing authentication of the control API.
`tools/anomalies.py` (test `docs.anomalies`) refuses a report without an evaluation of its
safety relevance and its reason, an open report without a decision, and a closed one without its
change and verification:

### A worked example: from a SOUP review to a release note

Follow MDQ-PR-005 through the processes. The SOUP review (clause 7's evaluation of published
anomaly lists) found a fix in a later release that affects a feature MiniDAQ uses. That is a
problem in released software, so it became a problem report (clause 9) with an evaluation: not
relevant to safety, because the configuration reader refuses non-integers, and the rationale
names that fact. The decision is to release with it and to upgrade the SOUP as a planned change
(clause 6 for maintenance, clause 8 for the change to the pin). The generated known-anomalies
list carries it into the release record (5.8), and the release check of Exercise 14.5 refuses a
record that leaves it out. When the upgrade lands, the same report is closed with the change and
the test that verifies the parser's behavior, and the next release's list no longer shows it.
Four processes, one problem, and each step leaves a record that the next one checks.

### Maintenance (clause 6)

After release, a change follows the development process again, scaled to what it touches: the
requirements, items, tests and risk analysis it affects are updated, and the change is verified
and released. The maintenance plan adds the inputs that exist only after release: feedback from
users, complaints, the post-market surveillance of Chapter 13, and new SOUP anomalies. The point
to remember is that maintenance is not a lighter process: a one-line fix in a class B item is a
class B change.

## Agile under IEC 62304

Many teams fear that the standard forces a waterfall. It does not: it requires activities and
their outputs, not an order of phases, and it allows the activities to overlap and repeat. AAMI
TIR45, whose current edition is from 2023, is the usual guide to mapping agile practice onto the
standard. Its main points, in this book's words: plan at several levels (the release, the
increment, the story) and keep each plan current; treat the backlog as the place where
requirements are elaborated, but make sure the requirements exist as controlled documents when
you release; define "done" for a story so that it includes the documentation and the trace, not
only the code; and keep the system in a releasable, verified state by integrating and testing
continuously.

MiniDAQ is developed this way. Each chapter is an increment that changes requirements, design,
code and tests together and ends with every check green; the documentation tests make "done"
include the trace, the classification and the SOUP list; and the release record collects the
evidence that already exists rather than producing it at the end. The risk of agile under the
standard is not the method: it is the temptation to leave the documents for later, when nobody
remembers why.

Three facts about this file are worth carrying into your work. Every document has a check that

change. And none of them judges content: the classification's severities, the requirements'
correctness and each problem's evaluation remain decisions that people make and reviewers check.

::: box-regulated
What IEC 62304 means for your daily work as a DAQ engineer:

- **Know the class of the item you are changing.** It decides how much design documentation,
  which acceptance criteria and which reviews your change needs.
- **Every change touches the trace.** A new behavior needs a requirement and a test that names
  it; a removed test needs a requirement that is still verified some other way.
- **Never add a dependency without the SOUP work.** Pin it, list it with what you need from it,
  review its known anomalies, and ask whether it changes a class.
- **A problem found after merge is a problem report,** even if you fix it in an hour. The record
  is what lets the organization see trends and show that nothing was lost.
- **"Done" includes the documents.** Requirements, design notes, trace and tests are part of the
  change, reviewed with the code.
- **Segregation is a claim you must prove.** Do not assume that a separate thread, library or
  namespace separates anything.
:::

## Summary {.unnumbered}

- IEC 62304:2006+A1:2015 describes the software life cycle of medical device software (planning,
  requirements, architecture, design, implementation, integration, testing, release, maintenance,
  risk management, configuration management and problem resolution) and scales it by safety
  class; a second edition is expected in 2028 (verify).
- The safety class follows the worst possible harm after risk controls outside the software: A
  for no injury, B for non-serious injury, C for death or serious injury. The manufacturer decides
  it from the ISO 14971 risk analysis, and it is not the device's MDR class.
- Items inherit their parent's class unless a documented segregation separates them; inside one
  process there is almost never such segregation, so MiniDAQ's server items are all class B and
  its separate client is class A.
- Class C mainly adds a documented detailed design of every unit and its interfaces and stricter
  unit acceptance criteria.
- Requirements must be testable: one "shall", no vague words, numbers with units, a verification
  method; a linter finds the form faults and frees review for content.
- SOUP is allowed in every class, if it is exactly identified, its requirements are stated, its
  failures are in the risk analysis and its known anomalies are evaluated at every release.
- Traceability belongs in the code: tags in the tests, a generated matrix, and a check that fails
  on every gap; the review still judges whether a tagged test really verifies its requirement.
- Problem reports carry an evaluation of safety relevance and a decision; the open ones become
  the known residual anomalies that a release states.
- The standard asks for activities and outputs, not for a waterfall; AAMI TIR45 maps agile
  practice onto it.
- MiniDAQ now has a development plan, 114 requirements, a generated trace matrix, classified
  items, a reviewed SOUP list and problem reports, each kept true by a test.
