# The embedded Linux platform: services, watchdogs and updates {#sol-ch25}

## Exercise 25.1: What systemd asks of a service

```{.cpp include="exercises/ch25/e1_watchdog_env/solution/watchdog_env.cpp"}
```

**Key points.**

- Accept digits only, then let `from_chars` reject what does not fit in 64 bits. A sign, a space or
  a unit suffix means the unit and the program disagree; that is `invalid`, not a number.
- Zero is not an interval. A watchdog that must be pinged every 0 microseconds cannot be met.
- WATCHDOG_PID names the process the watchdog is meant for. Every child inherits the variable, so a
  process that is not the one named must not ping: the watchdog is `off` for it.
- Ping at half the interval. A late thread or a lost datagram is then followed by another ping
  before the deadline.
- A notification is newline-separated `KEY=VALUE` lines in one datagram. The value runs to the end
  of the line and may hold `=`; empty lines are skipped.

**Common wrong answers.** Using `std::stoll` or `atoi`, which accept "5s" as 5 and wrap or throw on
overflow. Treating a malformed value as "no watchdog", which runs the system without a risk control
and without a message. Pinging at the full interval. Splitting a line at the last `=` instead of the
first.

## Exercise 25.2: Which version is newer

```{.cpp include="exercises/ch25/e2_semver/solution/semver.cpp"}
```

**Key points.**

- Parse from the outside in: build metadata after the first `+`, the pre-release after the first `-`
  before it, then exactly three numbers without leading zeros.
- A pre-release is lower than its release. Two pre-releases compare identifier by identifier:
  numbers by value, other identifiers by ASCII, a number lower than a word, and a prefix lower than
  the longer list.
- Numeric identifiers have no leading zero, so the longer one is the larger. That avoids converting
  them, and works for any length.
- Build metadata never decides precedence. Two builds that differ only after `+` are the same
  version to the updater, which is why MiniDAQ's manifest also carries the commit.
- MiniDAQ's own `update::Version` compares pre-release labels as strings, so `rc.10` sorts before
  `rc.2`. That is safe only while labels stay `rc.1` to `rc.9` and pre-releases never reach a
  clinical system. Both are rules the release procedure must state.

**Common wrong answers.** Comparing the whole pre-release string, which orders `rc.10` before `rc.2`
and `alpha.beta` against `alpha.1` by character. Treating a release as lower than its pre-release
because it has fewer parts. Accepting `01.2.3`, which gives one version two spellings.

## Exercise 25.3: Survive a power cut at any step

```{.cpp include="exercises/ch25/e3_power_cut/solution/ab_slots.cpp"}
```

**Key points.**

- One invariant, checked after every write: `current` always names a checked slot. Extract into the
  slot that does not run, check it, and only then let anything point at it.
- Install records the trial, then switches. A cut between the two leaves a recorded trial that is
  not current, which repair discards; the good version runs.
- Rollback switches, then records. A cut between the two again leaves a trial that is not current.
  Recording first would leave the untested version running and looking confirmed.
- The general rule behind both orders: at every moment, the state on disk may only claim something
  safer than the truth.
- `repair()` runs before anything else and knows how each operation can be cut. It needs two rules.
  With a state and no `current`, switch to the good slot. With a trial that is not current, forget
  the trial.
- The model's writes are atomic and durable in order. A real program makes that true with a rename
  for each switch and each state file, and an `fsync` of the file and its directory. Before the
  switch, the slot's files must be on disk too.

**Common wrong answers.** Switching before checking, which runs a half-written slot after a cut.
Writing into whichever slot is not `current`: after a cut that left a trial recorded but not
running, that slot is the good one. Making `repair()` finish an interrupted install instead of
discarding it, which runs a version nobody asked to run after the restart. Recording a rollback
before switching.

## Exercise 25.4: Check an unpacked tree against its manifest

```{.cpp include="exercises/ch25/e4_verify_tree/solution/verify_tree.cpp"}
```

**Key points.**

- Compare in both directions. Every listed file must be there with its digest, and every regular
  file that is there must be listed, hidden files included.
- Never follow a link. Use `symlink_status`, and let the iterator stay out of linked directories.
  Report every type other than a regular file or a directory.
- Check a listed path before using it. It must be relative, with no empty, `.` or `..` component.
  Otherwise `root / path` can name a file outside the slot, and the check would vouch for it.
- Accept exactly the line format the release tool writes. A second spelling of the same line is a
  second way for a reviewer to be fooled.
- Collect every problem and sort them. The person reading the refusal should see the whole
  difference at once.

**Common wrong answers.** Checking only the listed files. Hashing through a link. Joining a listed
path to the root without checking it. Stopping at the first problem. Accepting `sha256sum`'s binary
marker `*`, which the release tool never writes.
