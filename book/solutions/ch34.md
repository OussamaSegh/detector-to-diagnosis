**Key points.**

- `itertools.combinations` over the sorted, de-duplicated files of a commit gives each unordered
  pair once; `permutations` gives it twice.
- Leave out a commit above `max_files` entirely, from the pairs and from each file's count; keeping
  it in the counts only would lower the degree of every file it touched.
- The degree divides by the smaller count: it says how often the less busy file changed without
  the other.
- On MiniDAQ the strongest pair across items is the configuration's interface and the acquisition
  service: a dependency worth a sentence in the architecture.

**Common wrong answers.** Counting a file's commits before the size filter. Sorting by degree
first, which puts a pair of files changed together once at the top. Treating coupling as proof of
a code dependency without reading the commits.

## Exercise 34.2: Who owns this file?

```{.python include="exercises/ch34/e2_item_map/solution/item_map.py"}
```

**Key points.**

- Keep each item's longest matching prefix, then compare items: an item with two matching
  prefixes competes with the longer one.
- `owner` raises on a tie and names the items in sorted order; `check_map` catches it and lists the
  file, so that one report shows every problem of the map.
- A shadowed file is legal under the rule and still worth reporting: the directory says one item,
  the map another.
- A dead prefix is a report, not a failure: it misclassifies nothing but shows drift.

**Common wrong answers.** The first match, which changes with the order of the map. A tie broken by
the order of the items, which hides an ambiguity. A file stem compared with the directory only,
which lets `src/ab/x.cpp` match `src/a/x`.

## Exercise 34.3: Pin down what legacy code does

**Key points.**

- Test both sides of every comparison in the code: an interval of 0 and of 1, a live time of 0,
  a live time one microsecond longer than the interval, a rate at and just above the display
  limit.
- Find an input where truncation and rounding differ (5 counts in 3 s), and one where the order of
  the multiplication and the division matters (999 counts in 2 ms).
- Name each test after the behavior; mark the one that looks wrong (a dead block shows 0) and
  report it instead of changing it.

**Common wrong answers.** Tests that assert what the code should do (a dead block as an error),
which fail on the original. Ordinary values only, which every boundary mutant passes. A test of
the display limit with a rate far above it, which passes the mistyped limit of 5 M.
