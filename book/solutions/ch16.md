**Key points.**

- The map is organized by what an auditor asks, so every design and development clause from 7.3.2

## Exercise 16.2: A change request for a 3 ns window

```{.python include="exercises/ch16/e2_window_change/solution/change.py" snippet="rules"}
```

**Key points.**

- A default is the value of every document that omits it. Changing the constant alone would change
  the acquisition of every old configuration file, which is H-04 (settings other than intended); the
  request keeps 4 ns for schema versions 1.0 to 1.3 and makes 3 ns the default of schema 1.4.
- The window is also set explicitly in `minidaq/configs/default.json` (4000 ps), so changing only
  the constant would leave the shipped configuration at 4 ns. Search for every spelling of the
  number.
- A narrower window loses true coincidences if the timing resolution is worse than assumed, which is
  H-07, and the risk manager must approve. RC-12 (the effective configuration, defaults included, is
  recorded) is what lets a reviewer see which window a run used, and RC-16's verification against
  the simulator's ground truth must be repeated with the new window.
- SRS-SRT-001's text does not change, but its tests do: they assert counts with the old default.
  "Requirements whose verification must be repeated" is part of the analysis.
- The physics claim (3 ns keeps every true pair for the new crystals) is an assumption until it is
  measured, and is marked as one. The request stays `proposed` until someone with the authority
  decides.

**Common wrong answers.** "Risk: none"; the request approved by its author; commits listed before
the decision; a new test named as if it existed; the configuration schema left at its version; the
randoms measurement of Chapter 11 forgotten.

## Exercise 16.4: A CAPA for values at the limits of their types

```{.python include="exercises/ch16/e4_boundary_capa/solution/capa.py" snippet="rules"}
```

**Key points.**

- The two problem reports share a cause, which is why they need one CAPA: inputs at the limit of
  their type (`6e688`, beyond the range of `double`; a jump of exactly 2^31, where serial-number
  arithmetic is undefined) that no requirement named and so no unit test reached.
- The investigation covers every function that reads external input, from the table of fuzz targets
  in `fuzz/README.md`, not only the two that failed.
- The root cause is about the process: tests written from the requirements' examples, and no rule
  asking for the limits of the carrying type. Fuzzing found both defects by chance, from seeds with
  typical values.
- The corrective action changes `docs/coding-standard.md` and the review checklist; the preventive
  action adds limit seeds to `fuzz/corpus/`, so that every smoke run starts from the limits.
- The effectiveness check names a number and a check, and a release. It can fail, which is what
  makes it worth having.

**Common wrong answers.** "Human error" or "the developer did not think of it"; the two fixes as the
corrective action; an effectiveness check of "no new problems"; the CAPA closed because both
defects are fixed.

## Exercise 16.5: Document control between two releases

```{.python include="exercises/ch16/e5_document_control/solution/doc_control.py" snippet="problems"}
```

**Key points.**

- Compare texts, not dates or commits: a document that is byte-for-byte the same has not changed,
  and one that changed by a space has.
- A version identifies what a reader of a release holds, so a document may go up by two in one
  release (the fixture's SDP goes from 1 to 3) but may never stay the same after a change, or go
  down.
- The history of the new release must contain every row of the old one, unchanged. A history row
  describes something that was approved and released; correcting it changes what other records seem
  to say.
- A document that disappears is withdrawn without a record. In a QMS an obsolete document is marked
  obsolete and kept, so that old records that cite it can still be read.

**Common wrong answers.** Requiring exactly one new version per release; comparing modification
times; allowing a typo fix in an old row; ignoring documents that were deleted.

## Check yourself: model answers

1. Verification shows that the design outputs meet the design inputs; validation shows that the
   device meets the needs of its intended use, on representative product. MiniDAQ's verification is
   the trace matrix with its tests (for example `CoincidenceSorter.MatchesTheSimulatorsGroundTruth`
   for SRS-SRT-010); its validation would be the scanner's phantom and clinical evaluation. MiniDAQ
   alone cannot be validated because its intended use is to be part of a scanner whose images a
   physician reads.
2. The people the change control procedure names, before the change is implemented: in MiniDAQ the
   software lead for every change request, plus the risk manager when a risk control, a safety class
   or the intended use is affected, plus regulatory affairs when the change may be significant.
   After release, typically a change control board. The author never approves alone, because the
   author is the person least likely to see what the analysis missed, and an approval by the author
   is a review that did not happen.
3. 7.3.2 planning (the SDP); 7.3.3 inputs (the SRS, the intended use); 7.3.4 outputs (the
   architecture, the code); 7.3.5 review (the ADRs and the Part reviews); 7.3.6 verification (the
   trace matrix and tests); 7.3.7 validation (the plan in the design file); 7.3.8 transfer (the
   release process and SBOM); 7.3.9 changes (the change requests); 7.3.10 the file (the design file
   index). 7.3.1 is the general requirement for documented procedures.
4. A record exists only if others can retrieve it. An untracked file or an empty directory exists on
   one machine and nowhere else; git would not even push the directory. The check passed once on
   such a directory, which is why the rule was added.
5. At least one, and possibly two; what matters is that a reader of the next release holds a version
   that differs from the last release's. The comparison is against the release because a version
   identifies what a reader holds, and readers hold releases, not intermediate commits.
6. A correction fixes the instances found; a corrective action removes the cause. CAPA-0001's
   correction is the seven tests that now wait for their condition; its corrective action is coding
   standard rule 5.5 and the check `tests.waits`, which stop any test from asserting after a fixed
   sleep again.
7. Because people always make errors, and the question that leads to an action is why the process
   let this one through. Ask what made the error possible, and why nothing caught it before merge.
8. "Criterion: no further timing failures are reported." It cannot fail in a useful way: nothing
   obliges anyone to report, no date bounds it, and it would also be true if the actions had done
   nothing. A useful criterion names the stress run, its repetitions and a release.
9. A default is the value of every document that omits the key, so changing it changes the meaning
   of existing files without anyone editing them. A schema version lets the reader apply the default
   of the version the document was written for: documents of 1.0 to 1.3 keep 4 ns, and 3 ns is the
   default only of 1.4.
10. The truth, briefly: "Commit `11feccb`, recorded in the commit and the CHANGELOG; no reviewer
    other than its author, although the SDP requires one. That is a nonconformity; it is recorded in
    the internal audit as A-1 with CAPA-0002." Before the audit, the gap should have been found,
    recorded and acted on, so that the answer shows a system that found its own problem.
11. A record: evidence that a test was run with a result. It is never edited; if it is wrong, a new
    record says so and why, and the old one stays.
