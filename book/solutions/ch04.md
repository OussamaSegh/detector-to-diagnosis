## Exercise 4.1: Measure your machine with cyclictest

```{.cpp include="exercises/ch04/e1_cyclictest/solution/cyclictest_report.cpp" snippet="percentile"}
```

**Key points.** The parser is a three-state machine (banner, histogram rows, summary lines)
with consistency checks: rows start at 0 and are consecutive, the column count never changes,
and `# Total:` equals the sum of the rows. The checks catch truncated files, which otherwise
produce believable but wrong percentiles. In rt-tests 2.5, `# Total:` counts only in-range
samples, so the rank is computed over `total + overflows`, and a rank among the overflows
returns no value: the honest answer is "larger than the histogram range".

**Reference results** (book's machine, 30 s at 200 µs on CPU 1, about 150,000 samples idle,
microseconds):

| Run | p50 | p99 | p99.9 | p99.99 | max |
|---|---|---|---|---|---|
| idle, `--policy=other` | 60 | 80 | 171 | 815 | 2,202 |
| idle, `--policy=fifo -p80` | 10 | 26 | 96 | 978 | 6,655 |
| load, `--policy=other` | 66 | 103 | 6,604 | 10,441 | 12,603 |
| load, `--policy=fifo -p80` | 17 | 41 | 267 | 1,457 | 8,431 |

The 60 µs median under the normal policy is timer slack (50 µs by default), which the kernel
does not apply to real-time threads. **Common wrong answers.** Using `-p0` for the normal
baseline (it measures `SCHED_FIFO` 2); computing percentiles over `Total` alone; reporting the
top bin when the rank is among the overflows.

## Exercise 4.2: Pin the pipeline stages and compare the tail

```{.cpp include="exercises/ch04/e2_pin_stages/solution/pin_stages.cpp" snippet="assign"}
```

**Key points.** The CPU-list parser is strict on purpose: a typo in `isolcpus=` that silently
becomes "no CPUs" would put real-time threads on the interrupt CPU. Placement keeps the one
invariant that matters, at most one busy `SCHED_FIFO` thread per CPU, by giving the busy stages
dedicated CPUs in priority order and leaving everything else on the housekeeping CPU under the
normal scheduler. `make_profile` sets FIFO only for dedicated stages, so the invariant holds for
any number of CPUs; the test checks 1 to 8.

**Measured** (book's machine, `minidaq_latency --rate 10e6 --seconds 20 --batch 4096`, three
runs each): see the table in Section 4.5 of the chapter. The pattern to explain in your notes:
idle, pinning alone changes little and the real-time throttle makes the FIFO profile's tail
worse than the default one (p99 44 ms); under load, a pinned normal-priority source is worse than
an unpinned one (it cannot leave its loaded CPU), and only `SCHED_FIFO` on the busy stages keeps
up with no drops and no backlog.

**Splitting a stage.** Sort is the bottleneck at large batches. With more cores, partition it by
detector sector and merge (a k-way merge of sorted streams), with one dedicated CPU per
partition and one for the merge.

## Exercise 4.3: Per-stage latency you can query while it runs

```{.cpp include="exercises/ch04/e3_stage_histograms/solution/stage_latencies.cpp" snippet="interval"}
```

**Key points.** Snapshots are copies of the bucket counts; an interval is the difference of two
snapshots. Nothing is ever reset, so the reader needs no cooperation from the writer, and the
single-writer `record()` stays a plain relaxed load and store. The interval count is the sum of
the bucket deltas, not the difference of `count()`, because `record()` bumps the bucket before
the total: a snapshot taken between the two stores would otherwise disagree with itself. A
bucket count that decreased means the snapshots were swapped, which is reported as an error.

**Common wrong answers.** Calling `reset()` from the reader (a lost update when it races with
the writer's load and store); taking a mutex in `record()`; reporting the interval maximum as
the cumulative maximum.

## Exercise 4.4: An arena that never page-faults on the hot path

**Key points.** Touch by writing, one byte per page, through a `volatile` pointer. Disable
transparent huge pages for the measured baseline, or the kernel may back the region with 2 MiB
pages and the baseline shows 16 faults instead of 8,192. Measured: 8,192 faults to write 32 MiB
of plain `mmap` memory, about 1.5 µs each; zero for the prefaulted arena. `mlock` is best effort
and reported through `locked()`.

## Exercise 4.5: A calibrated TSC clock

```{.cpp include="exercises/ch04/e5_tsc_clock/solution/tsc_clock.cpp" snippet="calibrate"}
```

**Key points.** Bracketing the `CLOCK_MONOTONIC` read between two TSC reads bounds each pair's
error. Over 50 ms, a 100 ns error is 2 ppm, far inside the test's 0.1%. The flag check must match
whole words in the `flags` line only. **Detector timestamps:** the coincidence window is a few
nanoseconds and the detector's timing resolution tens of picoseconds; no clock read through an
operating system is that precise or stable, so events are timestamped by the front-end
electronics from a common clock (assumption: confirm with team).

## Exercise 4.6: Coordinated omission

```{.cpp include="exercises/ch04/e6_coordinated_omission/solution/omission.cpp" snippet="corrected"}
```

**Key points.** Naive: p99 = p99.99 = 100 µs, the stall visible only in the maximum. From the
intended start: 223 late requests and p99 = 110 ms. Corrected: 198 synthetic samples (199 ms down
to 2 ms) and p99 = 99 ms. The two corrections differ because the intended-start measurement also
charges the queue that builds up behind the stall.

**MiniDAQ.** Before this chapter's fix, `origin_ns` was taken when the source *read* a batch's
first word, so a delayed source stamped its backlog late and hid its own stalls. With
`PipelineConfig::due_time_ns`, the pipeline measures from when the data was due, which
`PacedSource::due_ns` knows and a real receiver gets from hardware timestamps. With the block
policy and no due time, back-pressure makes the source read late and under-reports in the same
way.

## Check yourself: model answers

1. **The mean.** Buffers overflow because of the rare long stalls, and the mean hides them: one
   batch in a thousand at 50 ms barely moves a 1 ms mean, but at high rates it overflows the
   front-end buffers every few seconds. What matters is the tail (p99.9, p99.99), the maximum
   and the drop count, over a long run at the real rate.
2. **Page faults.** A minor fault cost about 1.5 µs per 4 KiB page on the book's machine, mostly
   zeroing the page; a transparent-huge-page fault about 50 µs; a major fault (reading from disk)
   milliseconds. Prevent them by taking them all at start-up: `mlockall(MCL_CURRENT |
   MCL_FUTURE)`, prefaulting stacks and buffers by writing to every page, allocating nothing on
   the hot path, and counting faults per thread in tests.
3. **60 µs against 10 µs.** Timer slack: the kernel may delay a normal thread's timer by up to
   its slack (50 µs by default) to batch wake-ups; real-time threads get no slack. Set it per
   thread with `prctl(PR_SET_TIMERSLACK, 1)`; `minidaq_jitter --slack-ns 1` then wakes up after
   about 10 µs under `SCHED_OTHER` on an idle machine.
4. **Two FIFO threads on one CPU.** The higher-priority one runs whenever it is runnable, so a
   busy one starves the other completely. In the first profile, pair (`SCHED_FIFO` 60) shared a
   CPU with the source (80): pair's service time reached 192 ms and 53% of the input was
   dropped.
5. **50 ms once a second.** Real-time throttling: real-time threads may use 950 ms of every
   second by default (`sched_rt_runtime_us` / `sched_rt_period_us`). Confirm with `dmesg` ("RT
   throttling activated") and by checking that the stage is busy more than 95% of the time.
   Fixes: make the stage block or sleep when idle and keep its load below the budget; run it on
   an isolated CPU; only then, on a dedicated system, consider raising the budget or disabling
   the throttle.
6. **PREEMPT_RT.** It makes almost all of the kernel preemptible: threaded interrupt handlers
   with priorities, and sleeping locks with priority inheritance instead of most spinlocks. The
   average is dominated by code paths that were already short; the worst case is dominated by
   the longest non-preemptible section, which is what `PREEMPT_RT` removes.
7. **What pinning does not remove.** Device interrupts (interrupt affinity, `irqbalance`
   configuration); the timer tick and RCU callbacks (`nohz_full`, `rcu_nocbs`); other threads
   scheduled on the same CPU (`isolcpus` or an isolated cpuset partition); kernel workqueues
   (the workqueue `cpumask`); and the SMT sibling (disable SMT or keep the sibling idle). Any
   three.
8. **`mlockall` alone.** It locks mappings, but stack pages that the thread has not reached and
   memory that a library maps lazily can still fault the first time they are touched;
   prefaulting touches them in advance. Reading an untouched anonymous page maps the shared
   zero page read-only, so the first write still takes a copy-on-write fault.
9. **Three clocks.** Timeout: `CLOCK_MONOTONIC` (`steady_clock`), because it never jumps. Log
   timestamp: `CLOCK_REALTIME` (`system_clock`), synchronized by NTP or PTP, because people and
   other systems compare it with their own. The time of a single: the detector hardware's
   clock, because only it has picosecond resolution and a common time base across boards.
10. **Coordinated omission.** A measurement that waits for the system under test stops taking
    samples while the system stalls, so a long stall counts once. In a DAQ, the detector does
    not wait, but the PC's measurement does if it timestamps data when the source *reads* it: a
    delayed source reads its backlog late and stamps it late. Measure from when the data was
    due (hardware timestamp, or the simulator's schedule).
11. **50,000 samples.** p99 (500 samples above it) and p99.9 (50 above it) are reasonably stable;
    p99.99 rests on the 5 largest samples and is barely more than the maximum. A useful rule:
    collect at least 100 times 1 / (1 - percentile) samples, that is 100,000 for p99.9 and
    1,000,000 for p99.99.
12. **cyclictest totals.** Over 14,965 + 9 = 14,974 samples: the overflows are real samples.
    p99.9 has rank 14,960, which lies within the histogram (131 µs in the fixture). If the rank
    falls among the overflows, report "above the histogram range" (or rerun with a larger `-h`),
    never the top bin.
