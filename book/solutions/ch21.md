- The most serious defect is the one no test finds: `counts_` is written on the receive thread

## Exercise 21.2: A crash from the field, from the core dump

```{.cpp include="exercises/ch21/e2_postmortem/solution/group_parser.cpp" snippet="group"}
```

**Key points.**

- Read the core in order: the signal (SIGSEGV with a positive code, a fault), the stack (one
  function calling itself, thousands of frames deep), the frame (`p depth`). The diagnosis takes a
  minute once the core is there.
- Measure, do not guess, how much stack a level takes: compare `$sp` of two frames far apart. At
  `-O0` it was about 64 bytes a level on the reference machine, so the 8 MiB main-thread stack
  ends near 131,000 levels.
- Check the depth before the recursion, against the limit the format allows, and report the byte
  offset. The input decides the resource; the code must bound it (the shape of MDQ-PR-001).
- The release build crashed later, not never: GCC's inlining of the recursion made a level cost
  about 5.4 bytes, so 1 MiB of braces fit and 16 MiB did not. A crash that depends on the build
  is still a defect; reproduce with the build that crashed.

**Common wrong answers.** Raising the stack size with `ulimit -s` or a bigger thread stack, which
moves the threshold; catching SIGSEGV; converting the recursion to a loop without a depth limit,
which turns a crash into unbounded memory.

**Key points.**

- The sequence word does two jobs: odd means "being written", and the even value `2n` names the
  event, so a slot that was overwritten by a newer event is recognized even if the reader never
  saw it odd.
- The fields are relaxed atomics. A plain read concurrent with a plain write is a data race, which
  is undefined behavior whatever the reader does with the value; ThreadSanitizer reports it.
- The writer's release fence after the odd store keeps the field stores after it; the reader's
  acquire fence before the second load keeps the field loads before it. Without the reader's fence
  the field loads may move after the check, and a torn event passes it.
- Stop at the first overwritten slot: the writer fills the ring in order, so every older slot is
  newer too.
- The single writer is what makes `next_` a plain load and store instead of a read-modify-write.
  With two writers per ring the design would need a different claim protocol; MiniDAQ gives each
  thread its own ring instead.

**Common wrong answers.** A mutex around the ring, which makes the writer wait for the reader;
`memcpy` of a plain struct, which is a data race; checking only that the word is even, which
accepts an event that was replaced while you copied it.

**Key points.**

- Rates come from the real time between snapshots. A poller is never exact, and a missed snapshot
  doubles an interval: divided by one second, it looks like a burst.
- A counter that goes down is a restart, not a negative rate; leave the interval out.
- A baseline from before the incident is what "slow" is measured against. The median resists the
  odd interval.
- The stages after a slow stage starve at once; the stages before it slow only when the queue in
  front of it is full, seconds later. So a tie goes to the stage upstream. In the simulator the
  writer slowed at 31 s, the source slowed at 53 s and began to drop at 52 s: the stage that lost
  data was the one that did nothing wrong.

**Common wrong answers.** Blaming the stage that is slowest at the end, or the one that drops data;
breaking a tie toward the stage downstream, which blames the starved stage (the exercise's own
first solution did this); dividing every interval by one second.

## Exercise 21.5: Bisect a regression through commits that do not build

```{.python include="exercises/ch21/e5_bisect/solution/bisect_tool.py" snippet="check"}
```

**Key points.**

- Exit status 125 tells `git bisect run` that a commit cannot be tested. A commit that does not
  build says nothing about the defect; calling it bad blames it.
- When skipped commits sit next to the defect, bisect lists candidates. Report them all; the next
  step is to read those diffs, not to pick one.
- A check that uses build outputs starts from a clean state. Here Python's bytecode cache, which
  compares modification time and size, ran an earlier commit's code; `-B` turns it off. In C++
  the same trap is an incremental build directory reused across checkouts.
- A crash of the check itself is a skip, not a verdict; only the failure you are looking for is
  "bad".

**Common wrong answers.** Returning 1 for every failure; parsing only "is the first bad commit"
and returning nothing when bisect cannot decide; leaving the repository in the middle of a
bisection when the check fails.
