# C++ from the ground up {#sol-chf1}

## Exercise F1.1: A RAII file handle

```{.cpp include="exercises/f1/e1_raii_file/solution/file.hpp" snippet="file"}
```

**Key points.** The destructor is the only place that closes the file, so every path out of a
scope closes it: a `return`, a `break`, an exception. The copy operations are deleted, because
two owners of one `FILE*` would close it twice. The moves use `std::exchange` to take the
pointer and leave `nullptr` behind, so the moved-from object's destructor does nothing. The move
assignment closes the target's old file first (or it leaks), and the self-move check keeps
`f = std::move(f)` from closing the file it keeps. `File::open` returns `std::optional<File>`,
so a `File` is always open or absent.

**Common wrong answers.** Moving by copying the pointer without clearing the source (two
`fclose` calls). A move assignment that forgets to close the old file (the test
`MoveAssignmentClosesTheOldFile` counts it). Moves without `noexcept`.

## Exercise F1.2: A rule-of-five buffer with a counting test

```{.cpp include="exercises/f1/e2_rule_of_five/solution/samples.hpp" snippet="five"}
```

**Key points.** The copy constructor delegates to `Samples{n}` for the allocation and then
copies the values: one allocation per copy, which the test counts. The copy assignment is copy
and swap: it builds a full copy first, so a throwing `new` leaves the target unchanged (the
strong guarantee), and self-assignment is harmless. The moves steal the pointer and free
nothing but the target's old array. Because they are `noexcept`, `std::vector<Samples>` moves
its elements when it grows; the test `MovesAreNoexceptSoVectorMovesOnGrowth` would see one extra
allocation per element and growth step otherwise.

**Common wrong answers.** A copy assignment that deletes its own array before copying from
`other` (destroys the source when `other` is `*this`). A move assignment that does not free the
target's old array (a leak the `EveryAllocationIsFreed` test sees). Forgetting to reset `size_`
in the moved-from object, so that it reports elements it no longer has.

## Exercise F1.3: Algorithms instead of loops on singles

```{.cpp include="exercises/f1/e3_algorithms/solution/singles.hpp" snippet="algorithms"}
```

**Key points.** Each function is one algorithm whose name is the question: `count_if`,
`max_element` with a projection, `accumulate`, `sort` with a total order, `is_sorted` with the
same order, and `erase_if`. The two functions that have no answer for an empty batch return
`std::optional`. The sort compares the crystal when the times are equal, so the output is the
same on every run.

**Common wrong answers.** `max_element` on an empty span followed by a dereference of `end()`.
Accumulating into `0` (an `int`) instead of `0.0`, which truncates every addition. A sort by time
alone, which passes the small test by luck and orders equal times differently from run to run.

## Exercise F1.4: A class that leaks on an exception

```{.cpp include="exercises/f1/e4_audit_leak/solution/run_log.hpp" snippet="fixed"}
```

**A model review.**

1. *Leak when the constructor throws.* `RunLog{7, "x", 0}`: `new Header` succeeds, `new Index{0}`
   throws `std::invalid_argument`, and the header is never freed, because the destructor of an
   object whose constructor did not complete never runs, and a raw pointer member has no
   destructor of its own.
2. *Double free on copy.* `RunLog b = a;`: the class declares a destructor but no copy
   operations, so the compiler's copy copies the two pointers and both objects delete them.
3. *The claim is not evidence.* "The unit tests pass" was true, but the assistant's tests never
   used a capacity of 0 and never copied a log. A review checks what the tests exercise.

**Decision.** Rejected. The fix makes both members values, so the class follows the rule of
zero: a throw half-way destroys the members already built, and the compiler's copies are deep.
If the parts had to live on the heap, `std::unique_ptr` members would fix the leak, and the copy
would then have to be written (or deleted) on purpose.

## Check yourself: model answers

1. **`#include` and translation units.** The preprocessor replaces each `#include` with the text
   of the file, expands macros and evaluates `#if`. A translation unit is one source file after
   that step, the unit the compiler turns into one object file.
2. **"Undefined reference".** A linker message. The definition's source file or library is not
   on the link line; the declaration's types differ from the definition's, so the mangled names
   differ; or the function was declared and never defined.
3. **Definitions in headers.** An ordinary function defined in a header is defined once per
   translation unit that includes it, which breaks the one definition rule ("multiple
   definition"). Templates and `inline` functions may be defined in several translation units as
   long as the definitions are identical; the linker keeps one.
4. **Vector storage.** The vector object (three pointers) is an automatic object on the stack;
   its 100 elements are on the heap. Both are freed when the function's scope ends: the
   destructor of the vector frees the heap array.
5. **Reference and pointer.** A reference must be bound to an object when it is created, cannot
   be null and cannot be rebound. A pointer can be null and can be changed. Use a reference for a
   parameter that must refer to an object; a pointer when "no object" is a valid value or the
   target changes. Neither should own.
6. **Rules of zero, three and five.** Zero: if the members manage themselves, declare no special
   members. Three: a class with a user-written destructor also needs its copy operations (or must
   delete them). Five: it also needs the two moves. A new class should follow the rule of zero.
7. **`noexcept` moves.** The library (notably `std::vector` on growth) moves elements only if
   their move constructor cannot throw, to keep its strong exception guarantee; otherwise it
   copies.
8. **Throw in a constructor.** The first array is leaked: the object's destructor does not run,
   because the object was never fully constructed, and only fully constructed members are
   destroyed. A raw pointer member does nothing when destroyed. Use `std::vector` or
   `std::unique_ptr` members.
9. **`std::move`.** Nothing: it is a cast to an rvalue reference, which lets overload resolution
   pick a move constructor or move assignment. The move happens there, if the type has one.
10. **Iterator invalidation.** When the vector reallocates (growth beyond its capacity, `reserve`,
    `shrink_to_fit`), every iterator, pointer and reference into it becomes invalid; an
    `insert` or `erase` invalidates those at and after the position.
11. **A search that may fail.** `std::optional<std::size_t>` (or an iterator compared with
    `end()`). `-1` is a valid value of a signed type and is easy to use as an index by mistake;
    the optional puts "not found" in the type.
12. **`assert` on network input.** Assertions are removed in release builds (`NDEBUG`), so the
    check disappears exactly where the program meets real input; and an assertion that fires
    stops the program, which bad input must never do.
