# Chapter 2: Memory, caches and data-oriented design {#sol-ch02}

## Exercise 2.1: How many bytes per second?

```{.cpp include="exercises/ch02/e1_stream_budget/solution/budget.hpp" from="constexpr Budget stream_budget" to="=}"}
```

| Record size | Bytes/s | GiB/s | Gbit/s | Records per 64 B line |
|---|---|---|---|---|
| 8 B | 240 MB/s | 0.224 | 1.92 | 8 |
| 12 B | 360 MB/s | 0.335 | 2.88 | 5 |
| 16 B | 480 MB/s | 0.447 | 3.84 | 4 |

The interpretation is the real answer. 1.92 Gbit/s of payload does not fit on gigabit
Ethernet, so a scanner at this rate needs 10 GbE (or several 1 GbE links, one per board
group) even with 8-byte words. Memory bandwidth is not the constraint: even 16-byte records
at 0.45 GiB/s per pass leave room for many passes on any modern machine. Disk is a
constraint for singles (0.86 TB per hour with 8-byte words), which is one reason scanners
store coincidences rather than singles. A 12-byte record wastes the advantage of
power-of-two sizes: 5 records per line leave 4 bytes over, so records straddle lines
(unaligned loads, two lines touched per record) unless padded to 16.

## Exercise 2.2: AoS vs SoA on 100 M events

The solution is straightforward code (see `exercises/ch02/e2_aos_soa/solution/layout.hpp`);
the value is in the measurement and its explanation. On the book's machine (4 vCPU Xeon
VM at 2.30 GHz, GCC 13.3, -O2):

| 100 M singles | Time | Bytes per event read |
|---|---|---|
| AoS energy sum | 198 ms | 16 |
| SoA energy sum | 84 ms | 4 |

**Explanation.** A cache line brings in all 16 bytes of each single even though the loop
uses 4, so AoS moves four times as much data from DRAM. The observed gap (2.3x) is smaller
than 4x because the SoA loop runs into the arithmetic limit (serial dependent `double`
additions). For a 64 Ki-event data set (1 MiB), which fits in L2, both layouts run at the
same speed, which shows the difference is purely a memory effect.

**On bare metal**, `perf stat -e cache-misses,cycles,instructions` should show roughly the
same instruction count for both loops and about four times more last-level cache misses
for AoS. If your machine shows a smaller ratio, check whether the hardware prefetcher is
hiding latency (it does for sequential streams); misses still cost bandwidth.

**Extension.** Unroll the SoA loop with four independent accumulators (`sum0` to `sum3`)
and you should see it speed up again, because the dependency chain is split. This is
exactly what `-ffast-math` lets the compiler do automatically, and why that flag changes
results in the last bits.

## Exercise 2.3: Take the heap out of the event loop

```{.cpp include="exercises/ch02/e3_pmr_arena/solution/stage.hpp" from="class EnergyWindowStage" to="=};"}
```

**Key points.** The arena is the only allocation and happens in the constructor. Each call
destroys the previous output vector, re-creates the monotonic resource over the same buffer,
and reserves exactly the batch size, so `push_back` never regrows. The upstream is
`null_memory_resource()`, so an undersized arena fails loudly. The capacity check rejects an
oversized batch before touching the arena.

The test replaces global `operator new` and counts calls during 1,000 batches after a
warm-up: zero. The starter allocates at least once per batch (more as the vector grows:
`push_back` doubles capacity a dozen times to reach a few thousand elements).

**Alternative.** A reused `std::vector` with `clear()` and an up-front `reserve(capacity)`
passes the allocation test too and is simpler. The arena earns its place when several
temporary containers per batch share it.

| fine time | 10 | 0 .. 1023 | 5 ps |

```{.cpp include="exercises/ch02/e4_packed_word/solution/word.hpp" from="inline std::uint64_t encode" to="return Single{t"}
```

**What the tests check and why.** Field independence (OR of all maximal fields is all ones,
pairwise ANDs are zero) catches overlapping or mis-shifted fields. The round trip of 200,000
random singles over three wrap periods checks truncation (time error in [0, 5) ps after
reducing modulo the wrap period), rounding (energy error at most 0.25 keV) and that crystal
ids are exact. The byte test checks that serialization is little-endian independently of
host order, because it is written with shifts on values.

**Other valid designs.** A 14-bit crystal id is too small for 18,432 crystals. A design with
more time bits and coarser energy (for example 9-bit energy at 2 keV, 40-bit time) is
defensible: 2 keV is still far below the energy resolution, and the wrap period grows to
5.5 s. What matters is that the design note states every range and resolution and why it is
sufficient.

## Check yourself: model answers

1. **Singles per cache line.** `minidaq::Single` is 16 bytes: 4 per 64-byte line. MDQ-P1 is
   8 bytes: 8 per line.
2. **False sharing** is a slowdown caused when threads write different variables that share
   a cache line, so the line ping-pongs between cores. In a profile it shows as stores or
   atomic operations that take far longer than expected on otherwise simple code; on Linux,
   `perf c2c` reports cache lines with HITM accesses from several CPUs at different offsets.
3. **64 Ki events.** About the same time per event for both layouts (the book measured 45
   and 44 µs), because 1 MiB fits in L2 and the loop is limited by its dependent additions,
   not by memory traffic.
4. **Monotonic resource and individual lifetimes.** It never reuses freed memory until the
   whole resource is released, so objects that are created and destroyed independently
   would make it grow without bound. Use a pool resource for that pattern.
5. **Bit-fields for wire formats.** Allocation order of bit-fields within a storage unit,
   straddling rules and the in-memory byte layout are implementation-defined, so the same
   declaration can produce different bit positions on different compilers or ABIs. A wire
   format needs positions defined independently of the compiler, which shifts and masks on
   values provide.
6. **Lost 0.8 s burst.** The unwrapper only sees raw counter values. A true forward jump of
   0.8 s is more than half the wrap period (0.687 s). If the counter did not wrap during the
   gap, the raw value jumps forward by 0.8 s and is taken for a late word from the previous
   epoch; if it did wrap, the raw value appears 0.574 s *earlier* and is taken for a slightly
   late word in the current epoch. Either way the reconstructed time is 1.374 s too early,
   and every later event inherits the error. Detect the loss with packet sequence numbers (a
   gap means lost data, Chapter 9), and recover with explicit time markers that carry the
   high bits of the counter so the receiver can resynchronize.
7. **TLB misses.** A TLB miss adds a page-table walk, typically tens of nanoseconds and
   sometimes more if the page tables themselves miss in cache, on top of the data access.
   With 4 KiB pages, a 1 GiB ring buffer needs 262,144 translations; with 2 MiB huge pages
   it needs 512, which fit in the second-level TLB, so random access within the buffer
   rarely misses.
8. **Saturation.** Saturating keeps an out-of-range energy recognizably high (and it is
   rejected by any energy window); wrapping maps a 1,100 keV event to 76 keV, a plausible
   but false value that could pass a scatter or calibration analysis and bias results
   silently.
9. **"malloc is fast".** True on average: in `bm_alloc`, per-batch allocation cost only
   about 12% throughput versus an arena. The arena is not about the average but about the
   worst case: no locks, no system calls, no first-touch page faults in the hot path, which
   are the events that create latency spikes and drops at peak load. It also makes the
   capacity explicit and testable.
10. **Energy sums.** From DRAM, the vector of floats is faster (2.3x in the book's
    measurement) because it moves 4 instead of 16 bytes per event; in cache they are equal.
    If a pass needs every field, both layouts read all bytes; the difference shrinks (and
    depends on code generation), so the choice should follow the access pattern of the
    passes that dominate.
