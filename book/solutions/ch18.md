## Exercise 18.1: Fifteen tests for the timestamp rollover

```{.cpp include="exercises/ch18/e1_unwrap_tests/solution/test_unwrap.cpp" snippet="wrap"}
```

**Key points.**

- The two starter tests kill none of the seven mutants: every mutant behaves like the real code
  until the first wrap or the first late word. Tests written only for the "normal" stream look
  complete and are not.
- Two mutants (1 and 6) need the *second* word after a wrap: a test with one word after the event
  passes on both. `TheWordsAfterAWrapStayInTheNewPeriod` has three.
- Mutant 7 is the classic unsigned trap: `time_code - last_ > half` without first checking which
  is larger. The difference wraps around to a huge number whenever a late word arrives, so only a
  test with a late word in the same period kills it.
- Every test must respect the precondition: consecutive words less than half a wrap apart. The
  first version of `ManyWrapsInARow` stepped by two thirds of a wrap and failed on correct code;
  the steps are now a quarter of a wrap.
- No test checks a difference of exactly half a wrap: SRS-FMT-012 says "less than half", so the
  behavior there is unspecified, and a test of it would pin an accident of the implementation.

**Common wrong answers.** Fifteen tests of increasing streams; tests that read the mutants and
target them by line instead of the specification; a test of the private `last_`; a wrap test
with a gap of more than half a period.

## Exercise 18.2: Properties of a coincidence sorter

```{.cpp include="exercises/ch18/e2_sorter_properties/solution/test_sorter_properties.cpp" snippet="generator"}
```

**Key points.**

- Five properties: agreement with a reference, every prompt in `[0, window]`, no single in two
  prompts, batch sizes do not matter, and the accounting identity.
- Invariants catch the paralyzable window, the reused single, the window lost between batches,
  the out-of-order single and the uncounted lone single without knowing any answer. They cannot
  catch a stricter window, a stricter gate or a wrong winner: those outputs are valid, only
  different. A reference catches them.
- The reference is simpler than the sorter because it may be slow: it filters the whole stream,
  then cuts it into windows. It shares no code with the subject.
- The generator decides what the properties can find. A uniform random energy is essentially never
  exactly 585 keV, so the mutant whose gate excludes its upper edge survives every property until
  the generator draws the edges on purpose; the same for a partner exactly one window later.
  Crowding matters too: with uniform time steps of up to five windows, three singles rarely share
  a window, and the paralyzable window and the wrong winner survive as well (four of eight in
  all, `measurements/ch18/uniform-generator.md`).
- The starter's single property catches only the reused single in a normal run. With 10,000 cases
  it also finds the paralyzable window and shrinks it to three singles: window 3317 ps, singles at
  0, 1 and 3318 ps.

**Common wrong answers.** Only invariants; a reference that calls the subject; the upper bound of
the window checked without the lower bound (a negative time difference passes); crystal IDs that
repeat, so "used twice" cannot be told apart.

## Exercise 18.3: Branch coverage of the sinogram

```{.cpp include="exercises/ch18/e3_branch_coverage/solution/test_sinogram_branches.cpp" snippet="tof"}
```

**Key points.**

- The two starter tests take 29 of the 70 branches (41%): every rejection rule of `validate()`,
  every outcome of `locate()` but `binned`, the TOF bins, delayed pairs and `collapsed()` are left
  half open. Almost all need one kind of test: an input on the wrong side of one rule.
- Ten tests take 69 of 70 (98.6%). A NaN radius needs its own case, because the radius is checked
  as `!(r > 0) || !(r < R)`; the TOF rejection has two sides, and the upper one needs the crystals
  swapped, because the sign of tau depends on which crystal is endpoint a.
- The open branch is the `switch (p.outcome)` value that matches no case. It cannot be reached,
  and a `default:` to cover it would cost the `-Wswitch` warning for a new enumerator, so the
  review accepts it with that reason.
- The checker refuses a review entry whose line changed or whose branch is covered: a review is
  of the code as it is, and a stale one is the same mistake as a stale measurement.

**Common wrong answers.** Tests that call `locate()` and assert nothing (the coverage is the same,
the evidence is not); a `default:` added to the switch to reach 100%; a review entry with "not
needed" as its reason; the edges of the TOF bins tested one unit away from the edge.

## Exercise 18.4: A detector that fails on purpose

```{.cpp include="exercises/ch18/e4_fault_injection/solution/fault_injection.cpp" snippet="read"}
```

**Key points.**

- Exactly N words: each read of the inner port asks only for the words left before the fault, so
  the fault cannot be overshot by a large read.
- After the fault the decorator returns 0 without calling the inner port, as a device that has
  stopped; a fault of the inner port is always reported, never hidden by the plan.
- What the monitor thread reads (`delivered_`, `dropped_`, `faulted_`) is atomic; what only the
  source thread touches is not.
- The drop counter is named `rejected_injected` because `assess_integrity` treats only
  `packets_lost`, `sequence_resyncs` and `rejected_*` as detector losses. With another name the
  status shows the drops and the verdict ignores them: the last test fails, as it should. Ask the
  same question of every new adapter.
- A decorator keeps the real stream and scripts only the failure; a fake suits tests where the
  data does not matter; a mock suits tests where the interaction is the behavior, such as
  `close()` after the last `write()`.

**Common wrong answers.** Counting drops per read instead of across the stream; delivering the
words of the read in which the fault happens; a counter named so that the verdict never sees it;
reading the inner port during a stall.

## Exercise 18.5: Kill the survivors

```{.cpp include="exercises/ch18/e5_kill_survivors/solution/test_tracker_mutants.cpp" snippet="hold"}
```

**Key points.**

- MiniDAQ's own tracker tests leave 7 of the 41 mutants alive (22 killed, 9 timeouts, 3 that do not
  compile). All seven are gaps, none is equivalent, so `survivors.json` argues for nothing.
- Six are in the hold clock: the tests had one gap, one held packet and a clock that started near
  zero, where restarting the clock per packet, never restarting it, reading unused slots or adding
  the start time all give the right answer. Two gaps, two held packets and a run that starts late
  tell them apart.
- One is the restart threshold: "more than `max_gap_packets`" is only tested at its edge with a
  small `max_gap_packets`.
- Read the specification first, then the mutant: the mutant says where the tests are blind, the
  class comment says what the right answer is. A test written to make one mutant fail, without the
  specification, can pin the wrong behavior.
- A timeout counts as killed only if it is a real hang: the tool kills the whole process group of
  the test, so a looping mutant cannot keep running and slow down the mutants after it.

**Common wrong answers.** Marking the hold-clock survivors equivalent because "expire() is called
rarely"; a test that checks `oldest_held_ns_` through a friend declaration; a report recorded before
the last change to the tests. The checker compares only the header's SHA-256, so it cannot see
that; rerun the tool whenever the tests change, and record the report with them.
