## Exercise 3.1: An SPSC ring for singles

```{.cpp include="exercises/ch03/e1_spsc_ring/solution/ring.hpp" snippet="pushpop"}
```

**Key points.** Each index has one writer, which reads it `relaxed`. The other side's index is
read with `acquire`, and each side publishes its own with `release`. The slot is written
before the release store and read after the acquire load: that pair carries the data. The
producer's cached `head` and the consumer's cached `tail` sit on the same cache line as the index
their owner writes, so each line has a single writer. The batched functions refresh the cached
index only if the cache says there is not enough room, and publish the whole batch with one
release store.

**Measured** (book's VM, GCC 13.3, -O2, pinned to CPUs 0 and 1, 8 repetitions): per item, min
29.2, median 33.3, max 349.6 M singles/s; batches of 64, median 314.4; batches of 256, median
347.8. The target of 50 M/s is met by batching. Per-item transfer of 16-byte singles missed it
on this VM, and its spread shows why a single number would be misleading. See `NOTES.md`.

**Common wrong answers.** Using `seq_cst` everywhere (correct but about 7x slower in
`bm_spsc`). Reading the slot after publishing `head` (the producer may overwrite it while you
read). Wrapping indices at the capacity without a spare slot, so that full and empty look the
same.

## Exercise 3.2: Catch a seeded race with ThreadSanitizer

```{.cpp include="exercises/ch03/e2_seeded_race/solution/monitor.hpp" snippet="fix"}
```

**Race 1** (lost updates): two threads do read-modify-write on plain integers. Fix: atomic
counters with `fetch_add(1, relaxed)`. Relaxed suffices because no thread infers anything about
other memory from a count. Per-thread histograms merged on read are faster still.

**Race 2** (publication through a relaxed flag): seeing the flag says nothing about the window
data, and the window is rewritten while readers copy it, so a reader can mix old and new
fields. Fix: publish the whole 8-byte window as one `std::atomic<EnergyWindow>` (lock-free,
checked by `static_assert`) with release/acquire, and fold the "has a window" flag into a
sentinel value. One atomic means there is no ordering between two variables to get wrong. For
larger configurations, use a mutex, a seqlock, or an immutable object published through an
atomic pointer.

The full report, with both TSan excerpts and the -O2 instrumentation finding, is
`exercises/ch03/e2_seeded_race/solution/REPORT.md`.

The decode stage applies the policy, and it is the only place that may drop:

```{.cpp include="exercises/ch03/e3_four_stage_pipeline/solution/pipeline.cpp" from="std::jthread decoder([&] {" to="decoded.close();"}
```

**Accounting.** Reports are plain integers written by one thread each and read after the threads
are joined. Joining synchronizes, so no atomics are needed. Pair conservation is
`in == 2 * out + filtered`, where filtered counts singles that found no partner, including the last
one carried at the end of the run.

**Expected bottleneck.** The sort stage. Its per-single cost grows with log(batch size): about 90,
45 and 36 M singles/s for 64, 512 and 4,096 on the book's machine, against more than 230 M words/s
for decode. At 64 the per-batch overhead of five threads on four cores dominates instead.

**Which policy where.** The network receiver drops the newest data and counts it, because the
hardware will not wait and loss there is explicit. Stages inside the PC use back-pressure (reject
and wait), because a drop there is invisible to hardware counters and silently biases rates and
dead-time corrections. `drop_oldest` suits live displays, not acquisition: in a time-ordered
stream it punches a hole in the past that downstream consumers cannot see without sequence numbers.

## Exercise 3.6: Shut down a waiting worker promptly

The starter has two bugs. The wait ignores the stop token, so an idle worker never wakes and
`stop()` hangs in `join()`. And the loop exits on a stop request without draining, so the test
saw 923 of 1,000 items processed. The solution waits with
`condition_variable_any::wait(lock, stop_token, pred)` and treats "returned with an empty queue" as
"stopped and drained". It sets a `stopping_` flag under the lock so that `submit()` refuses new
work, and it calls the handler without holding the lock. See the listing in Section 3.1.

## Check yourself: model answers

1. **SPSC and acquire/release.** Each decision depends on one index written by one other thread.
   The producer writes a slot, then release-stores `tail`. The consumer acquire-loads `tail`, then
   reads the slot (message passing). The same holds for `head` in the other direction.
   `seq_cst` adds a single total order across *different* variables, which matters only when a
   thread's correctness depends on ordering its own store before its load of another variable
   (store buffering). The ring never does that, so `seq_cst` would only add cost: about 7x in
   `bm_spsc`.
2. **Writer falls behind.** Back-pressure propagates through bounded queues (pair waits, then sort,
   then decode) up to the entry, where one deliberate policy decides between blocking the input
   (lossless if the link has flow control and buffers suffice) and dropping incoming batches with
   exact counts. Either way the condition is reported (counters, an alarm to the operator, an entry
   in the acquisition log), and data is never dropped silently in the middle.
3. **Data race.** Two conflicting accesses (same location, different threads, at least one a write)
   not ordered by happens-before, not both atomic. It is undefined behavior, so the compiler may
   assume it never happens. It can keep the counter in a register, merge or tear accesses, and
   reorder surrounding code, so the damage is not limited to "a few lost counts". It also hides
   real TSan reports among benign-looking ones.
4. **Store buffering.** The core's store buffer: a store waits there before it reaches the cache,
   and a later load of a different address can complete first, reading the old value. A `seq_cst`
   store on x86 is an `XCHG` (or `MOV` + `MFENCE`), which drains the store buffer before later
   loads, and the model requires a single total order of seq_cst operations, in which at least one
   store precedes the other thread's load.
5. **ABA and 64-bit indices.** ABA needs a value to come back to a previous state while a thread is
   not looking. Monotonic 64-bit indices never repeat in practice: at 10^9 operations per second,
   wrapping takes about 584 years. The ring also does no CAS on pointers and frees nothing while
   running.
6. **Receive, closed, exit.** The producer may publish its last batch between the consumer's failed
   `receive()` and its `closed()` check, then close. Exiting loses that batch. Fix: after seeing
   `closed()` (an acquire load pairing with the release in `close()`), call `receive()` again, and
   exit only if it is still empty.
7. **Stop token for the source only.** Stopping a pipeline means stopping its input. If every stage
   stopped on request, batches in flight would be lost without being counted. Each later stage stops
   because its input channel is closed and drained.
8. **Thread pool.** Any two of: ordering between batches must be preserved; stages have per-thread
   state (unwrapper, carried single, open file); latency must be bounded and not depend on unrelated
   queued tasks; pinning a stage to a core (Chapter 4) needs a dedicated thread.
9. **Batch size 4,096 slower.** Measured: the sort stage sorts each batch, which costs O(n log n),
   so its cost per single grows with the batch size (about 36 M singles/s at 4,096 against
   about 45 at 512). The cache-footprint hypothesis was tested by shrinking the channel to 8 batches
   and rejected (34.4 against 33.1 M/s). To confirm on your machine, time each stage separately, or
   use Exercise 3.3's busy-time reports, or profile with `perf` (Chapter 5).
10. **"TSan is clean."** (a) TSan only sees code that ran, with the interleavings and inputs of that
    run. (b) It can miss races entirely when accesses are not instrumented: in this chapter, Clang 18
    at -O1 and above did not instrument loads from a stack object and missed a real race in every
    run. Also: it does not detect atomicity violations built from individually atomic operations.
11. **Total order in the sort.** MDQ-P1 time has 5 ps resolution, so equal timestamps happen.
    `std::sort` is not stable, and ties come out in an unspecified order, which can change the
    pairing. Breaking ties by crystal makes the output a pure function of the input, which is needed
    for reproducible runs and exact regression tests.
12. **Dropped versus filtered.** Dropped data was lost because the system was too slow: a capacity or
    performance problem, and a data-integrity event that corrections must account for. Filtered
    data was removed by design: invalid words or unpaired singles, an expected result of
    processing. In a service report, a moving drop counter means "the PC cannot keep up", while a
    moving filtered counter may be perfectly normal, or may point to a detector or firmware problem
    (for example invalid words). Mixing them makes both unreadable.
