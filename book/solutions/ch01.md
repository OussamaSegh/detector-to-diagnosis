## Exercise 1.1: Strong types for picoseconds and keV

**Approach.** One class template, `Quantity<Tag, Rep>`, with an empty tag struct per unit.
The tag is never instantiated; it only makes the two instantiations different types.

```{.cpp include="exercises/ch01/e1_strong_types/solution/units.hpp"}
```

**Why each test passes.**

- *Different units do not mix:* the only `operator+` candidates are hidden friends of
  `Quantity<PicosecondsTag, int64_t>` and of `Quantity<KeVTag, float>`. Hidden friends are
  found only through argument-dependent lookup on the operand types, and each takes two
  operands of its own class, so `Picoseconds + KeV` has no viable function.
  `std::is_invocable_v<std::plus<>, Picoseconds, KeV>` is therefore false (it checks
  whether `a + b` is well-formed in an unevaluated context).
- *Raw numbers do not sneak in:* the constructor is `explicit`, so `int64_t` does not
  convert implicitly; there is no conversion operator out.
- *Zero cost:* a class with one `int64_t` member and no virtual functions has the same size
  and is trivially copyable, so it is passed in a register.

**Common mistakes.** Making the constructor implicit (`Picoseconds p = 5;` then compiles,
and `p + 5` works through the conversion); adding `operator Rep()` "for printing";
writing `operator+` as a member template that accepts any `Quantity`.

**Extra exploration.** Write a `static_assert` that `Picoseconds{1} * Picoseconds{1}`
does not compile (it should not: ps squared is not a time). Check with
`std::is_invocable_v<std::multiplies<>, Picoseconds, Picoseconds>`.

## Exercise 1.2: From raw pointers to the Rule of 0

**Diagnosis.** The starter has a destructor that calls `delete[]` and implicitly generated
copy operations that copy the pointer. Under ASan:

```text

    #1 ... in ex::EventBuffer::~EventBuffer() event_buffer.hpp:21
```

**Solution.** `EventBuffer` declares no special members. Its single member,
`FixedStorage`, is the one small class that knows how to copy (keeping the capacity) and
how to leave a moved-from object empty with capacity zero:

```{.cpp include="exercises/ch01/e2_rule_of_zero/solution/event_buffer.hpp" lines="17-49"}
```

`std::exchange(o.v_, {})` moves the vector out and replaces it with a fresh empty one in a
single expression, which is what makes the moved-from guarantee hold.

**Discussion of the alternatives.** `std::unique_ptr<Single[]>` plus size and capacity is
the leanest owner, but it is move-only: you would then delete the copy operations of

explicit `clone()`. Writing all five special members of `EventBuffer` by hand also passes
the tests; it is simply more code to review and easier to break when a member is added.

**Acceptance criteria met.** Deep copy (tests `CopyIsDeep`, `CopyAssignIsDeep`), `noexcept`
moves with an empty source, `view()` over exactly `size()` elements, `push()` refusing to
reallocate.

## Exercise 1.3: A parser that cannot be crashed

```{.cpp include="exercises/ch01/e3_parse_single/solution/parse.cpp"}
```

**Key points.**

1. The length check is the first statement, so every later read is in bounds.
2. `std::memcpy` into a local of the target type is the only portable way to read a
   multi-byte value from a byte buffer without alignment or aliasing UB. Compilers emit a
   single (unaligned) load for it.
3. `std::isfinite` must run before the range check: every ordered comparison with NaN is
   false, so `e < 0 || e > 2000` is false for NaN and a range check alone accepts it.
4. The function is `noexcept` and returns every failure as a named enumerator.

**The ten malformed inputs**, and why each is interesting: empty input and two truncations
(length handling at 0, mid-field and one byte short), negative time and `INT64_MIN` (sign
handling, and a value whose negation overflows if you ever wrote `-time`), crystal 18,432
(the first invalid id, off-by-one) and `0xFFFFFFFF` (wraps to -1 if someone stores it in
an `int`), NaN and negative infinity (non-finite values), and 2000.01 keV (just above the
upper bound).

**The mutation loop.** Two hundred thousand mutated records with one to four random byte
changes, a tenth of them truncated to a random length. Each input is copied into an
exactly-sized `std::vector<std::byte>` so that ASan can see any read past the end; on a
16-byte stack array a 15-byte input would still be inside the array. The run accepts tens
of thousands of records, so the success path is exercised too, and every accepted record
is checked against the invariants. Chapter 7 replaces this loop with libFuzzer, which
finds inputs guided by coverage instead of chance.

**What to learn from it.**

- *Bug 1* shows why overflow must be checked *before* the operation. Detecting it after the
  fact relies on the result being the wrapped value, which the standard does not promise
  for signed types, and the optimizer may remove the check entirely. GCC and Clang also
  offer `__builtin_add_overflow(a, b, &result)`, which compiles to an add and a jump on
  the overflow flag.
- *Bug 2* is a classic off-by-one in a clamp (`>` instead of `>=`). Note that UBSan alone
  does not catch it, because the write goes through `hist.data()[bin]`, a raw pointer; ASan
  does, because the array lives on the stack with poisoned red zones around it.
- *Bug 3* is the container-reallocation dangling reference from the chapter.
- *Bug 4* is the one people argue about: "x86 handles unaligned loads fine". The hardware
  does; the language does not, and compilers vectorize and reorder code under the
  assumption that a `uint64_t*` is 8-byte aligned. `memcpy` is both correct and as fast.
- *Bug 5*: the literal `1` is an `int`. Any shift of an `int` by 31 or more is UB, and on
  x86 the hardware masks the shift count to 5 bits, so `1 << 40` "works" as `1 << 8`.

## Check yourself: model answers

1. **When does `std::string_view` dangle?** When the storage it views is destroyed or
   moved: (a) it views a temporary `std::string` that dies at the end of the full
   expression (`std::string_view v = make_string();`); (b) it is returned from a function
   that built a local string; (c) it views a `std::string` that is later modified so that
   it reallocates (appending past capacity), or a string inside a container that
   reallocates. A view stored in a data member dangles as soon as its source's lifetime
   ends before the member's.
2. **Signed vs unsigned overflow.** Unsigned types are defined as arithmetic modulo $2^N$,
   so wraparound is specified. Signed overflow was left undefined historically (different
   signed representations, and freedom for optimizers to assume `i + 1 > i`); C++20 fixed
   the representation to two's complement but kept overflow undefined. A 32-bit hardware
   timestamp counter wraps by design, so store it as `uint32_t` and compute differences in
   unsigned arithmetic (`uint32_t delta = now - before;` is correct across one wrap), then
   convert to a signed 64-bit time after unwrapping (Chapter 9).
3. **`[[nodiscard]]` on an error type** makes every function that returns that type warn
   when its result is discarded, including functions written later by other people. On a
   single function it protects only that function. With `-Werror` the type-level
   attribute turns "forgot to check the error" into a build failure across the codebase.
4. **User-written destructor only.** Copy operations are still generated (deprecated but
   allowed), so copying copies members shallowly; if the destructor frees a resource, you
   get a double free. Move operations are *not* generated when a destructor is declared,
   so `std::move(x)` silently falls back to the copy constructor: the code compiles, runs
   slower, and has the same double-free bug.
5. **Why `vector` copies on reallocation.** `std::vector::push_back` offers the strong
   exception guarantee. If an element's move constructor can throw, a failure halfway
   through moving elements would leave both old and new storage partially moved, so
   `vector` uses `std::move_if_noexcept` and copies instead. Declare move constructors
   `noexcept` (or let the compiler generate them from members that are `noexcept`).
6. **Read-only batch parameter.** `std::span<const Single>`. The caller guarantees the
   underlying storage is alive and unmodified for the duration of the call; the callee
   guarantees it does not keep the span (or pointers into it) after returning.
7. **`int64_t` picoseconds vs `double` seconds.** A double has a 53-bit significand, so
   the gap between adjacent representable values grows with magnitude. Once an absolute
   time in picoseconds passes $2^{53}$ ps (about 2.5 hours), adjacent doubles are 2 ps
   apart; after 10 hours ($3.6 \times 10^{16}$ ps) the gap is 4 ps, after a day 16 ps.
   Storing seconds instead of picoseconds does not help: the relative precision is the
   same. Subtracting two nearby timestamps to get a coincidence time difference inherits
   that rounding, which is comparable to the fine-time resolution of the electronics.
   `int64_t` picoseconds are exact up to about 106 days and give exact signed differences.
8. **Which sanitizer.** Misaligned load: UBSan (`alignment`). Heap use after free: ASan.
   Data race: TSan. Shift by 40 of an `int`: UBSan (`shift-exponent`). TSan cannot be
   combined with ASan (or MSan) in one build; ASan and UBSan combine fine.
9. **Exceptions in config parsing vs packet parsing.** Configuration parsing happens once,
   at start-up or on an operator command, is not latency-critical, and a failure correctly
   aborts the operation the user requested; an exception with a clear message is ideal.
   Packet parsing runs millions of times per second on the hot path, malformed packets are
   expected occasionally, and a throw costs microseconds with unpredictable latency; the
   right response is to count the error and continue, which a return value expresses.
10. **`constexpr`, `consteval`, `constinit`.** `constexpr` on a function means it *may* be
    evaluated at compile time if called with constant arguments in a constant context; on
    a variable it means the variable is a compile-time constant (and `const`). `consteval`
    on a function means every call *must* be evaluated at compile time. `constinit` on a
    variable with static or thread storage duration requires constant initialization (no
    dynamic initialization, so no initialization-order problems) but does not make the
    variable `const`.
