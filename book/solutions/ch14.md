**Key points.**

- The checker enforces the consequences of a classification, not the classification itself:
  which hazards an item contributes to, and how severe they are after risk controls outside the
  software, are the team's judgment, written in the rationale.
- Inheritance by process is the rule that catches most mistakes. The audit log and the metrics
  harm no one by themselves, yet they share an address space with the sorter, so they are
  class B unless something segregates them.
- The client is class A because it runs in its own process and the server validates every
  request it sends: process isolation plus input validation is a segregation you can verify.
- The simulator is shipped inside the server, so it is classified like everything else there,
  and the classification exposes a design problem (MDQ-PR-009).
- The system's class is its highest item's; a document that says otherwise contradicts itself.

**Common wrong answers.** Class A for the simulator because "it is only for testing"; class A for
the audit log with a segregation claim that names a separate thread or library; one class for
the whole system without item rationales; a class lowered by an internal self-check.

## Exercise 14.2: Twenty testable requirements for the sorter

```{.python include="exercises/ch14/e2_sorter_requirements/solution/req_lint.py" snippet="rules"}
```

**Key points.**

- Each requirement states one behavior with its subject, "shall", the quantity with its unit,
  and a verification method. Defaults belong to the configuration; the requirement states the
  behavior for the configured value.
- "Fast" splits into throughput, verified by measurement on a named machine and preset, and
  latency, stated as an event (a later single inside the energy window) rather than a time,
  because the sorter cannot close a window before a later single proves it closed.
- "Reliable" becomes accounting: every single is counted in exactly one category.
- Checking the requirements against `coincidence_sorter.hpp` finds the fourth multiples policy,
  `keep_if_only_one_good`, and that a delay of zero disables the delayed window. Requirements
  written from memory miss both.
- The linter checks form only. "Inclusive" in the energy requirement is content, and only a
  reader of the code and the test can confirm it.

**Common wrong answers.** Requirements that name the design ("shall use a ring buffer"); a
latency requirement in milliseconds that the sorter cannot meet when the source falls silent;
two behaviors joined by "and shall"; numbers without units; every requirement marked T,
including throughput.

**Key points.**

- A pin is a commit hash or an archive digest; a branch or a tag name can move, so it is not a
  pin, and the checker refuses it.
- The list must name the same pin and version as the build. Checking that mechanically is what
  keeps the list from describing last year's dependencies.
- Only shipped SOUP needs the full record (purpose, requirements, known anomalies, risk, a dated
  review); development tools need identification, and their qualification is Chapter 20's.
- The review is dated for a MiniDAQ minor version, so each minor release forces a new one.
- The known-anomaly field records the evaluation, not a copy of the tracker: which fixes concern
  features MiniDAQ uses, and what that means for its requirements.

**Common wrong answers.** "Latest" or "3.11" as the version; listing what the library can do as
its requirements; an anomaly field that says "none known" without saying where you looked; no
risk field because "it is a well-known library".

**Key points.**

- Each tag belongs to the nearest test above it, C++ or Python; a tag may list several IDs.
- The check runs in both directions: requirements without tests, and tags without requirements
  (or with withdrawn ones). Requirements verified by measurement, analysis or inspection need an
  evidence entry instead of a test.

## Exercise 14.5: Check the release record

```{.python include="exercises/ch14/e5_release_check/solution/release_check.py" snippet="check"}
```

**Key points.**

- The record is checked against the development plan: every verification it lists needs a row,
  a result of exactly `pass`, and evidence that exists.
- "Pass (2 flaky)" is not a pass. A flaky test is an anomaly and gets a problem report.
- Every open problem report must appear among the known anomalies; the release states them.
- The checker cannot tell whether the evidence belongs to the released commit, whether each
  anomaly's decision still holds, or whether the archive restores. Those stay human checks.

**Common wrong answers.** Accepting any result that starts with "pass"; checking that an
evidence path is written but not that the file exists; a build section that says "the usual
CI".

## Exercise 14.6: The known anomalies of a release

```{.python include="exercises/ch14/e6_known_anomalies/solution/anomalies.py" snippet="validate"}
```

**Key points.**

- Every report, open or closed, is evaluated for safety relevance with a reason; that is the
  question clause 9 of IEC 62304 most wants answered.
- An open report records a decision ("release with it", "fix before release"); a closed one
  names its change and the test that verifies it.
- The known-anomalies list is generated from the open reports, sorted by ID, so it cannot drift
  from the reports.
- MDQ-PR-005's evaluation rests on one fact in the code, the integer check of the configuration
  reader. A change that removes that check makes the evaluation wrong; the rationale names the
  fact so that a reviewer can see it.

**Common wrong answers.** Listing closed reports as known anomalies; "safety relevant: no" without
a reason; an open report whose decision is "TBD".
