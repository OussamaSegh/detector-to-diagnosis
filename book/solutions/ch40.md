## Exercise 40.1: The kind of release a change needs

```{.python include="exercises/ch40/e1_kind_of_release/solution/release.py"}
```

**Key points.**

- Ask what a change does to a site, not why it was made. A fix that renames a field breaks every
  client that reads it, whatever problem report it closes.
- Check the largest effect first: breaking, then adding, then fixing. The starter checks fixing
  first, and so calls a breaking fix a patch.
- A release takes the largest kind of its changes. One compatible addition makes the whole release
  minor, which is why the fixes for an old line are kept on a maintenance branch, apart from new
  work.
- A new minor release resets the patch number and a major one resets both: 1.3.2 is followed by
  1.3.3, 1.4.0 or 2.0.0. The next version of `2.0.0-dev` is decided when it is released, so it is
  refused.

**By hand.**

1. 1.3.1, a patch on `release/1.3`. 2.0.1 contains the renamed fields of 2.0.0: installing it
   would break the site's clients, which is the very cost a patch release promises not to impose.
   The fix is made on main and cherry-picked to the maintenance branch.
2. Minor: a new field is a change of a data format, which the maintenance plan keeps out of patch
   releases even when every reader ignores it, because the site's own tools, archives and
   validations may not. A site that wants only the fix waits for, and validates, a minor release; if
   the problem is relevant to safety, look for a fix that needs no new field, so it can ship as a
   patch.
3. A new SOUP item brings its own anomalies, its own supplier's support and its own risk
   analysis: a patch release is installed with little validation at the site, and that is only
   reasonable when it brings nothing new to evaluate.

**Common wrong answers.** Deciding by the reason ("it fixes a report, so it is a patch"). Taking
the kind of the first or the last change of a release. `1.4.2` after `1.3.2`. Computing a version
after a development version.

## Exercise 40.2: The support matrix

```{.python include="exercises/ch40/e2_support_matrix/solution/support.py"}
```

**Key points.**

- A line's support starts with its `.0` release and nothing later moves it: it is a promise made
  when the line is released, and a site plans with the date printed in the release notes.
- Calendar months, ending on the last day of a short month: "24 months" is the period a person
  reads, and 730 days is a different date.
- Versions compare as tuples of integers. Text comparison is right until the first `1.10` or
  `1.3.10`, which is why the bug survives so long.
- "Before the horizon": an item supported until the horizon's own day covers the whole period and
  needs no plan. The function says which items need one; what that plan is stays a decision
  recorded in the SOUP list.

**By hand.**

1. Support would then be extended by every fix, so a line with problems would be supported longest
   and the end date could never be planned. A site on 1.3 would expect that one more patch buys it
   two more years, and the team would carry every old line for ever.
2. Both, in one row. MiniDAQ's SOUP list records the OpenSSL project's 2026-09-07 as the end of
   support, the conservative date, because it ends the upstream fixes that the distribution
   backports; the same row names Ubuntu's dates (standard support to 2029-05, ESM to 2034-04), which
   are why the package still receives security fixes. The date falls inside the support period, so
   the item needs an end-of-support plan, and the end-of-support plan says what the other date is
   for: rely on Ubuntu's backports and read its notices first, and move to OpenSSL 3.5 with the next
   platform under its own change request.
3. Each fix is made once and then cherry-picked, verified by the full release checks and released
   on each branch: about three times the verification and three release records. Choose the period
   from what the sites need (their validation cycle, the lifetime the product declares) and from
   what the team can afford to verify, and keep the number of lines small by having sites
   upgrade within it.

**Common wrong answers.** Measuring from the newest patch. 30-day months. Sorting versions as
text. Writing the OpenSSL project's date as "the" end of support without saying which package is
shipped.

## Exercise 40.3: Which releases contain a defect

```{.python include="exercises/ch40/e3_affected_releases/solution/affected.py"}
```

**Key points.**

- Walk every parent, iteratively, with a set of seen commits: a merge brings a whole branch, and a
  history has many paths to one commit. Recursion fails at the first long history.
- A cherry-pick has another id; only its message says what it copies, which is why the maintenance
  plan requires `-x`. Follow the chain: a pick of a pick names the pick, not the original.
- "Contains the defect" and "contains the fix" are different searches: the first is about one
  commit, the second about any copy of another. Conflating them is how a record says "not
  affected" about a branch that never received the fix.
- What the function cannot see: a fix rewritten by hand without a trailer, a defect introduced
  twice, a revert of the fix. The change request's list of the branches the fix reached is the
  second source.

**By hand.**

1. `git tag --contains` follows ancestry, and the defect's commit is an ancestor of every tag
   made after it on any line. The fix on a maintenance branch is a different commit, a copy, so
   the tag of 1.3.1 does not contain the fix's id even though it contains the change.
2. Write the message of the rewritten commit with a trailer naming the original
   (`(cherry picked from commit <id>)`, written by hand), and list the branch in the change
   request. The trailer is what the function reads; the change
   request is what a reviewer checks it against.
3. `git bisect` needs a test that fails with the defect, a good commit and a bad one, and a
   history where each commit builds; it then finds the first bad commit in about log2(n) builds.
   `git blame` on the lines the fix changed names the last commit that touched them, which is
   often, but not always, the one that introduced the defect: a defect can come from lines the fix
   did not change, or from a commit that only moved them.

**Common wrong answers.** First parents only. Looking for the fix by its id. Sorting versions as
text. Treating a defect fixed before any release as affecting the first release.

## Exercise 40.4: Is the version we ship affected?

```{.python include="exercises/ch40/e4_affected_version/solution/affected.py"}
```

**Key points.**

- OpenSSL before 3.0 numbers its patch releases with letters: no letter first, then by the number
  of letters (z before za), then alphabetically.
- Package versions are `epoch:upstream-revision` and compare as dpkg does: runs of digits as
  numbers, `~` before the end, letters before other characters. As strings, `-0ubuntu3.16` sorts
  before `-0ubuntu3.5`.
- A distribution backports fixes into the same upstream version: its advisory, with the package
  version that fixes it, decides. Without it, an upstream match is `affected-upstream`, a lead for
  the review.
- Check the comparison against the real tool: `dpkg --compare-versions` agrees on every pair tried.

**Common wrong answers.** Dropping the letters, which makes 1.1.1 and 1.1.1w the same version.
Comparing package versions as strings or as tuples of the dotted parts. Concluding "affected" from
the upstream range on a backporting distribution, or "not affected" because no distribution
advisory was found.
