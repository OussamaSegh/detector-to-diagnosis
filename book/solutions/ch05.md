**Reference results** (book's machine, `release`, pinned to CPU 2, 5 repetitions, median, M
singles/s; 100 M singles is 1.6 GB, far beyond every cache):

| Kernel | Random 10% | Random 50% | Random 90% | Sorted 10% | Sorted 50% | Sorted 90% |
|:-------------|-----:|-----:|-----:|-----:|-----:|-----:|
| branchy | 141 | 158 | 292 | 420 | 370 | 364 |
| branchless | 345 | 337 | 311 | 353 | 331 | 314 |
| SIMD (AVX2) | 338 | 346 | 317 | 340 | 328 | 313 |

For comparison, `memcpy` of 1,600 MiB runs at 1.40 ns per 16 bytes (714 M singles/s, 21 GiB/s
read plus write), and the chapter's in-cache numbers (4,096 singles per batch) are 2.6 times
higher for the branchless kernel.

**Key points.**

- *Random order:* the branchy kernel's speed follows the expected number of mispredictions per
  single (about 0.55, 0.50 and 0.10 at 10%, 50% and 90%; see the chapter's table), not the
  number of singles copied. *Sorted order:* outcomes come in long runs, the predictor is right
  almost every time, and the branchy kernel is the fastest because it copies least.
- The branchless and SIMD kernels do not depend on the data.
- *Bytes per second:* each kernel reads 16 bytes per single and writes 16 bytes per kept single
  (the benchmark's `bytes_per_second` counter). The branchless kernel at 50% moves 7.5 GiB/s by that count, a third of `memcpy`'s 21 GiB/s.
Most of the gap is the stores: a normal store to a line that is not in cache first reads the
line (a read for ownership), so a store loop moves about 48 bytes per 16 written, while glibc's
`memcpy` uses non-temporal stores for copies larger than the cache, which skip the read
(verify: glibc's `x86_shared_non_temporal_threshold` tunable). Every kernel is limited by
memory: at 100 M singles, SIMD and branchless are within 3% of each other, and the branchy
kernel on sorted data at 10% is the fastest because it writes only a tenth of the singles.
- *Why SIMD wins little:* memory-bound (compare with a `memcpy` of 1.6 GB), three wasted lanes
  in every four because of the AoS layout, and compaction costs shuffles.

**Common wrong answers.** Benchmarking 4,096 singles repeated (the predictor learns them);
forgetting the tail loop for sizes that are not a multiple of the register width; using `&&`
in the "branchless" version (the compiler may emit a branch); storing past the end of `out` in
the SIMD tail.

**Key points.** The profile of the starter is dominated by the standard distributions:
`std::normal_distribution` (a rejection loop with a logarithm and a square root),
`std::exponential_distribution`'s logarithm, `std::mt19937_64` and
`std::uniform_int_distribution`. The fixes, measured one at a time:

| Version | M singles/s | ns per single |
|---|---|---|
| Starter | 18.7 | 53.5 |
| xoshiro256\*\*, Lemire's multiply-shift for the crystal | 44.0 | 22.7 |
| Normal quantile table with interpolation, series logarithm | 74.7 | 13.4 |

The statistics tests are the safety net: each change is checked against the rate, the pair
fraction and the energy distribution before it is measured. **Costs to state:** the quantile
table clips the normal at about ±3.67 sigma (0.024% of samples); the series logarithm has a
relative error below 1e-6. Fine for a test source; not for the detector simulator of Chapter 8,
where the spectrum's tails are the point. xoshiro256\*\* is not a cryptographic generator. With
Clang 18 the solution runs at about 16 ns per single, which is why the budget is 18 ns (a third
of the starter).

**Common wrong answers.** Replacing `std::normal_distribution` with the sum of 12 uniforms
without checking the tails (it has none beyond 6 sigma, and its kurtosis is wrong); changing the
seed handling so that the same seed no longer gives the same stream; optimizing the pairing
code, which the profile shows is small.

**Key points.** The exact distribution of U is built by counting orderings: placing the pooled
values in increasing order, each is from `a` or from `b`, and a `b` placed after `i` values of
`a` adds `i` to U. With 5 and 5 repetitions there are 252 orderings, so the smallest possible
one-sided p-value is 1/252 = 0.004, below the default alpha of 0.01; with 4 and 4 it would be
1/70 = 0.014, and the gate could never fail. That is the real reason for the minimum of 5
repetitions. Both conditions are needed: the threshold makes the gate ignore real but tiny
differences, the test makes it ignore large differences that are noise. The repository's
workflow is `.github/workflows/perf.yml`; the baseline must come from the same runner.

**Common wrong answers.** Comparing means; a two-sided test (a speedup is not a failure); a
normal approximation for 5 samples; recording the baseline on a laptop; running the gate on
shared cloud runners.

**Reference results** (G codes/s): uniform 2.10 simple, 2.26 split; photopeak 2.06 and 2.11;
constant code 0.41 and 1.24. **Key points.** A run of identical codes turns `++h[c]` into one
dependency chain through store-to-load forwarding; four sub-histograms make four independent
chains. 32-bit sub-histograms (four of them, 32 KiB) stay in L1 and are merged into 64-bit
totals, so a bin cannot wrap as long as one call adds fewer than 2^32 codes to it.

**Key points.** The median, because benchmark times are skewed by interruptions; the bootstrap,
because the ratio of medians has no simple sampling distribution. Each side is resampled
independently, to its own size. The interval is coarse for 5 repetitions per side (few distinct
medians) and the percentile bootstrap under-covers for small samples, so for a decision that
matters use 10 or more interleaved repetitions. The result is deterministic for a seed with one
standard library; `std::uniform_int_distribution` is implementation-defined, so another
library may give a different (equally valid) interval.

## Check yourself: model answers

1. **Proving a speedup.** Run both versions interleaved on the same machine with 10 or more
   repetitions (protects against drift and other sessions' noise); compare medians (against
   skew from interruptions); give an interval for the ratio (against reading noise as effect);
   test significance with a rank test (against lucky runs); check the effect in the whole
   program with a benchmark and a profile (against optimizing what does not matter); explain the
   mechanism (against accidents of alignment and frequency).
2. **When SIMD does not help.** When the loop is memory-bound (the energy filter: the branchless
   loop is within a factor of two of `memcpy`); when the layout wastes lanes (AoS: one energy per
   16 bytes); when the work per element is small compared with the shuffles it needs
   (compaction); when the loop is short or has gathers and scatters; and on some CPUs when wide
   registers lower the clock frequency.
3. **The repeated batch.** The branch predictor learns the outcomes of the 4,096 branches from
   their history, so the branchy loop stops mispredicting; with fresh data, it mispredicts about
   0.5 times per single at about 8 ns each.
4. **`DoNotOptimize` and `ClobberMemory`.** The first makes the compiler treat a value as used,
   so the computation producing it is not deleted; the second is a compiler barrier that forces
   pending memory writes to happen. Without them, the compiler may delete the work, and the
   benchmark reports a time that does not depend on the input.
5. **Plateau and tower.** A plateau (nothing above) means the function spends the time in its own
   code; a tower means it spends it in callees. `time_order` was a wide plateau under the sort:
   a tiny function with large self time is being called, not inlined, an enormous number of
   times.
6. **Function pointer.** A function name passed to `std::sort` decays to a function pointer;
   the comparator's type is then shared by every function with that signature, and GCC at `-O2`
   did not propagate the constant pointer into the sort, so each comparison was an indirect
   call. A lambda has a unique type, so the sort is instantiated for it and the call inlines.
   `-O3` (and LTO and PGO) propagate the pointer or promote the indirect call, and inline it.
7. **Slower at 10%.** The first branch, `e >= 450`, is true 55% of the time on uniform energies:
   nearly a coin toss, so it mispredicts about 0.45 times per single, plus the second branch. At
   50%, the first branch (`e >= 250`) is true 75% of the time. Mispredictions cost far more than
   copies.
8. **`-march=native`.** It lets the compiler use every instruction of the *build* machine, so the
   binary may die with an illegal instruction on the target. Build for a baseline, compile the
   wide kernels with `__attribute__((target("avx512f")))`, and choose at run time with
   `__builtin_cpu_supports`, once.
9. **Threshold and test.** The test alone fails on tiny, real differences nobody cares about;
   the threshold alone fails on noise. A baseline from another machine measures the difference
   between machines.
10. **The constant code.** Each increment of the same bin must wait for the previous store
    (store-to-load forwarding), so the loop runs at the latency of one long dependency chain.
    Four sub-histograms used in turn create four independent chains that the core overlaps.
11. **Without hardware counters.** You can still sample with `cpu-clock` and get profiles and
    flame graphs, count software events (context switches, migrations, page faults, task clock)
    and measure wall-clock and CPU time. You cannot count cycles, instructions (IPC), branch or
    cache misses, or do a top-down analysis.
