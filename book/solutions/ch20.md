## Exercise 20.1: A manifest that notices

```{.python include="exercises/ch20/e1_manifest/solution/manifest.py" snippet="verify"}
```

**Key points.**

- Collect every difference, then report. A verifier that stops at the first changed file tells
  you about one problem in a package that may have five, and the next run tells you the second.
- Links are not followed and not trusted: a link in a package goes to `added`, so it cannot point
  the check at a file outside the package that happens to have the right digest.
- Parse the manifest strictly. A line that does not have the form `<64 hex digits>  <path>`, an
  absolute path, a `..` part or a duplicate is an error; a verifier that skips what it cannot
  read reports success on a manifest it never checked.
- Sorted POSIX paths make the manifest of the same files the same bytes whatever the order in
  which they were written, and `sha256sum -c` reads it, so anyone can check a package without
  the tool.
- The manifest protects against damage, partial copies and mistakes, not against someone who
  changes a file and its line together. That needs the package's digest kept where the package
  does not control it: the evidence archive and the committed release record.

**Common wrong answers.** Comparing only the files the manifest lists, which misses an added
file; reading the manifest with `split()`, which accepts paths with spaces cut in two and lines
with one space; returning `True` or `False` instead of the three lists.

## Exercise 20.2: Make a build reproducible

```{.cmake include="exercises/ch20/e2_reproducible/solution/CMakeLists.txt" snippet="maps"}
```

**Key points.**

- Three things make the starter's builds differ: the clock in the build information, the
  absolute path in `__FILE__`, and the paths in the debug information. Find them by building
  twice and comparing, not by guessing: `cmp -l` gives the offsets, `strings` and
  `readelf --debug-dump=info` say what is there.
- The version comes from the project, not from the clock. A build date says nothing the commit
  does not say better.
- One option covers both kinds of path: `-ffile-prefix-map` includes `-fmacro-prefix-map`
  and `-fdebug-prefix-map`. Map the build directory too, because generated sources and the
  compilation directory live there.
- When the build directory lies inside the source directory, both maps match. GCC uses the last
  one given and Clang the longest prefix, so give the source map first and both compilers agree.
- The debug information stays: the program is the same and a debugger still works from the top
  of a checkout of the same commit, with `directory` or `set substitute-path` in gdb.

**Common wrong answers.** Removing `-g` (the builds become equal and the core dumps of
Chapter 21 become useless); setting `SOURCE_DATE_EPOCH` and keeping the date; mapping only the
source directory, which leaves the build directory in the debug information.

## Exercise 20.3: Test the gate, then test the test

```{.python include="exercises/ch20/e3_gate_selftest/solution/selftest.py" snippet="faults"}
```

**Key points.**

- The control decides first. A gate that fails on the correct tree "catches" every fault, so
  "gate fails on correct code" wins over every other verdict.
- Each fault names the report it must cause. A gate that fails for another reason did not show
  that it can see the fault; the vague mutant, which says only "something is wrong", passes a
  self-test that checks only the exit status.
- The first set of faults, one per rule, misses three broken gates: the one that never reads
  `.hpp` files, the one that accepts the header on any line, and the one that accepts
  `TODO(anna)`. Each needs a fault at a boundary of the gate's promise: the other file type, the
  header just past line two, a parenthesis that is not an issue.
- Breaking the gate in plausible ways is the cheap way to find the missing faults. The same
  method applies to `tools/gate_selftest.py`: its fifteen faults show that each gate runs and
  reports, not that each covers every boundary of what it promises.

**Common wrong answers.** Treating any failure with the fault as "caught"; skipping the control
run because the tree is known to be correct; one fault per gate and no more.

## Exercise 20.4: A/B on a machine that drifts

```{.python include="exercises/ch20/e4_ab_drift/solution/ab.py" snippet="paired"}
```

**Key points.**

- Order is the whole result on a drifting machine. All of A and then all of B raised a false
  alarm in all 200 simulated jobs when the machine slowed by 2% per run, and found none of the
  real 10% regressions when it sped up by as much.
- Interleaving removes the bias but not the spread: the drift widens each side's runs over 20%,
  and the Mann-Whitney test of two such samples found the 10% regression in 0.5% of the jobs.
- The ratio of two neighbors cancels the drift. A sign test of ten rounds' ratios found the
  regression in every job, with no false alarm.
- A sign test of `n` rounds cannot give a p-value below `2^-n`. With five rounds the smallest is
  1/32, so it can never reject at 0.01: the number of rounds is part of the test's design.
- Pairing pays only when the machine moves. Without drift and with 3% noise, the unpaired test
  found a 7% slowdown in 89% of the jobs and the paired one in 62%.

**Common wrong answers.** Pairing the k-th run of A with the k-th run of B without regard to the
rounds; a paired t-test on ratios that are far from normal with ten values; concluding from one
simulated job instead of the alarm rate over many.

## Exercise 20.5: How sure is "not flaky"?

```{.python include="exercises/ch20/e5_flaky_triage/solution/flaky.py" snippet="interval"}
```

**Key points.**

- Ten clean runs bound the failure rate only below 31% (95%, two-sided). The claim "below 1%
  with 95% confidence" takes 299 clean runs: `(1 - 0.01)^n <= 0.05`.
- Eight failures in eight runs, MDQ-PR-019 under load, put the rate above 63%. Fisher's test of
  8 of 8 against 0 of 8 after the correction gives `p = 1/12,870`: the correction changed the
  behavior, not chance.
- A rule that reruns a failure once reports a test that fails with probability `p` as passed
  with probability `1 - p^2`. At 30% per run that is 91% with one retry and 97% with two.
- A flaky test is a defect with a measured rate. It gets a problem report with its interval and
  is fixed, or quarantined by a recorded decision while the gate still runs and reports it.

**Common wrong answers.** The normal approximation (`p +- 1.96 sqrt(p(1-p)/n)`), which gives an
interval of width zero for zero failures; "it passed ten times, so it is fixed"; a retry rule
justified by the failure that MDQ-PR-020 showed, where no retry would have helped and the log
without the test's output was the problem.
