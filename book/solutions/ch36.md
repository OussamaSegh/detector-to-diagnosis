**Key points.**

- Decide about the last paragraph as a whole: it is a trailer block only if every line in it is a
  trailer or a continuation. The question is about the paragraph, not about each line.
- The subject's paragraph is never a trailer block: without a blank line before the last
  paragraph, there are no trailers.
- A continuation (a line that starts with white space) adds to the value before it, joined with
  one space.
- Compare keys without regard to case, as `git log --format=%(trailers:key=...)` does.
- Test against `git interpret-trailers --parse`, the parser every other reader of the history
  uses.

**Common wrong answers.** Any line of the form `Key: value`, which finds a trailer in the subject
`Fix: the sorter`, in a URL and in a sentence starting with `Note:`. Taking the last paragraph's
trailer lines and ignoring its prose line, which git does not do without a line it generates
itself. Splitting on the first colon without checking that the key is made of letters, digits and
hyphens.

## Exercise 36.2: The name of an object

```{.python include="exercises/ch36/e2_object_names/solution/objects.py"}
```

**Key points.**

- Every object's name is the SHA-1 of `<type> <size>\0` and its content; one function for the
  header serves blobs, trees and commits.
- In a tree, each entry is `<mode> <name>\0` followed by the 20 bytes of the name, not its 40
  hexadecimal characters; a directory's mode is `40000`.
- Entries are sorted by name as bytes, a directory's name compared as if it ended with `/`: the
  file `a.txt` comes before the directory `a`.
- A commit's content is its tree, a parent line per parent, author, committer, a blank line and
  the message; the author and committer lines carry the time in seconds and the zone.
- An empty directory is not stored.

**Common wrong answers.** Hashing the content without its header. The mode `040000` that
`git ls-tree` prints. A plain sort by name. A newline added after the message that the message did
not have. Comparing with your own implementation instead of with git.

**Key points.**

- The stable points are the lines of the base that both sides keep, found with a diff of the base
  against each side (`SequenceMatcher` with `autojunk=False`).
- Between two stable points: a side that kept the base takes the other's version, equal changes
  are taken once, different changes are a conflict between markers.
- Changes of two adjacent lines are one region, since no kept line separates them, and so a
  conflict, as in git.
- The end of the files is a last region after the last stable point.
- Clean merges are compared with `git merge-file -p`; conflicts with its count.

**Common wrong answers.** Comparing lines at the same index, which shifts after any insertion or
deletion. Resolving a conflict by taking one side and counting it, which writes a file without
markers that may even compile. Forgetting the region after the last stable line. Leaving
`autojunk` on, which in longer files treats lines such as `}` as junk and finds another matching.
