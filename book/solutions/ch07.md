**Key points.**

- The starter has 15 findings. Four are bugs (`atoi` and `atof` three times, the unchecked
  `fclose` in `close()`, `strerror` in a threaded program), several are the same design smell
  (a raw owning `FILE*`), and three checks fire on one harmless line (`int n;` assigned inside
  an `if` and never read). Triage by *cause*, not by count: replacing the raw pointer with a
  `std::unique_ptr` and a deleter removes five findings at once.
- `close()` checks both `fflush` and `fclose`, and the result of every earlier write. On
  `/dev/full`, `fputs` succeeds (the data is only buffered) and the error appears at the flush.
- Parsing is all or nothing: the new values go into a copy, which is assigned only if every
  option parsed. A command line that is half applied is worse than one that is refused.
- The solution keeps two `NOLINT(cppcoreguidelines-owning-memory)` comments with a reason: the
  check cannot see that the `unique_ptr` and its deleter own the `FILE*`.

**What clang-tidy did not report.** The ignored `fputs` and `fputc` results (MiniDAQ's
configuration removes them from `cert-err33-c`, for terminal output; here they write a file),
the null `FILE*` dereference in `write()` after a failed open, and the half-applied options.
The tests found all three. `exercises/ch07/e1_tidy_zero/solution/NOTES.md` has the full table.

**Common wrong answers.** Casting every return value to `void` (silences the check, keeps the
bug); `// NOLINT` without a check name; keeping the raw pointer and adding a move constructor
by hand (now five special members to get right instead of zero); checking `fclose` but not
`fflush`, or the other way round.

**Key points.**

- The target checks three things: no memory error (AddressSanitizer sees every read, because
  libFuzzer passes each input in an allocation of exactly its size), the word count it
  promised is the count it delivered, and, for plain headers, that encoding what was parsed
  gives the input back. The third property found the unchecked reserved field, which is not a
  memory error at all.
- Run against the starter, the target found a crash in each of six 60-second runs within the
  first 30 executions: one round-trip failure (reserved field not zero) and five
  heap-buffer-overflows (a word count or a header length larger than the packet). All six
  inputs are in `tests/crashers/` and the unit test rejects each.
- Every length in a header is a claim. Check each against the bytes that arrived, before
  reading at any offset derived from it, and make sure the arithmetic of the check cannot
  overflow (here both products are below 2^19).
- A `header_words` of 0 or 1 never crashed: the words then overlap the header, which is valid
  memory. Only the unit test `RejectsEveryLieInTheHeader` catches it. A fuzzer finds what its
  properties can see.

**The decoder campaign.** On the book's machine, one hour on one vCPU from the four seed
inputs: 102,580,804 executions (28,486 per second), coverage from 83 to 101 edges with the
last increase after 7,755 executions, a final corpus of 85 inputs (25 KB), no crash. A good
report gives those numbers and their limits: coverage flat for 59 of the 60 minutes means the
target reached what it can reach early, and the rest of the hour tried new values on the same
paths; nothing outside the decoder was exercised, and properties the target does not check
(time unwrapping over hours of data, for example) were not tested. The full notes are in
`solution/NOTES.md`.

**Common wrong answers.** A target that parses and returns without reading the words (finds
nothing, because the parser itself never reads past the header); a target built without
AddressSanitizer (the out-of-bounds reads do not crash); fixing the crash and deleting the
input; a check of the form `offset + count * 8 <= size` with 32-bit arithmetic in a format
where the fields are wider (here they are not, but say why).

## Exercise 7.3: SBOM generation and review

```{.python include="exercises/ch07/e3_sbom_diff/solution/sbom_diff.py" snippet="diff"}
```

**Part 1.** nlohmann/json is `"scope": "required"` because it is compiled into
`minidaq_server` and `minidaq_ctl`; GoogleTest and Google Benchmark are `"excluded"` because
they build only tests and benchmarks. A dependency that is not in `KNOWN` stops the script
with a message: someone must state its license and scope. With the same
`SOURCE_DATE_EPOCH` two runs give identical bytes, including the serial number, which is
derived from the content; a release's SBOM can therefore be regenerated and compared later.

**Key points.**

- Identify components by group and name. The `bom-ref` contains the version, so matching on
  it turns every upgrade into a removal plus an addition, and the reviewer loses the one fact
  that matters: this is the same component in a new version, so read its release notes.
- Compare licenses as sets, hashes as sorted lists, and treat a missing `scope` as CycloneDX's
  default (`required`).
- The exit status makes the tool usable in a release checklist: 0 means no SOUP review is
  needed for dependencies, 1 means there is something to review.

**Common wrong answers.** Comparing the whole JSON text (the timestamp and serial number
differ in every SBOM); reporting only additions and removals; ignoring scope changes, although
a test-only component that becomes shipped is the most important change of all.

## Exercise 7.4: Reading a file whose name you did not choose

```{.cpp include="exercises/ch07/e4_untrusted_path/solution/untrusted_file.cpp" snippet="read"}
```

**Key points.**

- Open first, then ask every question of the descriptor (`fstat`), never of the name: the name
  can be replaced between a `stat` and an `open`, the descriptor cannot (CERT FIO45-C).
- `O_NOFOLLOW` rejects a symbolic link in the last component (`ELOOP`); `O_NONBLOCK` makes
  opening a FIFO without a writer return at once, so `fstat` can reject it. The starter's
  `std::ifstream` blocked forever in its constructor.
- The size is checked by `fstat` and again by reading at most `max_bytes + 1`, because a file
  can grow while it is read.
- A small RAII wrapper closes the descriptor on all ten return paths.
- `O_NOFOLLOW` does not cover the directories above the file. On Linux 5.6 and later,
  `openat2` with `RESOLVE_NO_SYMLINKS` does; whether you need it depends on who can write
  those directories.

**Common wrong answers.** `stat` then `open` (the race); `realpath` and a prefix check (the
same race, and symlinks inside the allowed directory still work); reading the whole file and
then checking its size (`/dev/zero` never ends); forgetting `O_CLOEXEC`, so the descriptor
leaks into any child process.

## Exercise 7.5: A strict duration parser

```{.cpp include="exercises/ch07/e5_strict_duration/solution/duration.cpp" snippet="parse"}
```

**Key points.**

- Integer arithmetic only: `4.1s` is exactly 4,100,000,000 ns. The starter computes
  `4.1 * 1e9 = 4099999999.9999995` in `double` and truncates it to one nanosecond less.
- Every multiplication and addition is checked against `INT64_MAX` *before* it happens;
  checking afterwards is too late, because signed overflow is undefined behavior.
- The unit must be the rest of the string exactly, so `10ms10ms`, `10ms ` and `10MS` fail.
- The overflow tests sit on both sides of the boundary. A test that only tries
  `99999999999999999999999s` does not show that the check is in the right place.

**Common wrong answers.** `std::stod` plus a range check (accepts `1e3`, `inf`, leading
spaces, and rounds); `std::stoll` (throws, and accepts leading spaces and a sign); computing in
`double` and rounding with `llround` (fixes `4.1s` but not values beyond 2^53 ns).

## Check yourself: model answers

1. **Violation versus defect.** A defect is code that does the wrong thing; a violation is code
   that matches a pattern that often does. A violation that is not a defect: the `std::hash`
   partial specialization flagged by `cert-dcl58-cpp`, which the C++ standard allows. A defect
   that is not a violation: the unchecked `eventfd` in the control server, which no enabled
   check reported, and in Exercise 7.1 the null `FILE*` dereference after a failed open.
2. **Why an SBOM.** So that the manufacturer, regulators and customers can tell, for any
   released version, exactly which third-party components it contains. The manufacturer uses
   it to check each new vulnerability report against every product in the field; a regulator
   (in the US, for cyber devices, by law) uses it to assess premarket submissions; a hospital's
   IT security team uses it to assess risk on their network. It is used at submission, at every
   release, and whenever a vulnerability is published.
3. **`atoi("70000")` in a `uint16_t`.** 70000 fits in an `int`, and the conversion to
   `uint16_t` keeps it modulo 65536: 4464. Nothing reports an error because `atoi` has no way
   to, and the cast is well defined. `parse_number` checks that the whole text is a number
   (`ptr == end`, no error from `from_chars`) and that it lies in the target type's range and
   the caller's bounds.
4. **Suppression forms.** `NOLINT(check): reason` on one line (or `NOLINTNEXTLINE`); a
   `NOLINTBEGIN(check)` and `NOLINTEND` region with the reason above it; a check disabled in
   `.clang-tidy` with the reason in its comment. A bare `NOLINT` hides every check on that
   line, including checks added later, and gives the reviewer nothing to check.
5. **The `fputc` exclusion.** In Exercise 7.1 the starter ignored the results of `fputs` and
   `fputc` while writing a file, which loses records on a full disk; clang-tidy no longer
   reports it. Tests that write to `/dev/full` catch it, and review should know which
   exclusions exist and look for what they hide.
6. **Decoder properties.** Every word is accounted for (decoded or counted invalid); every
   single is in range and encodes back to its word; decoding the bytes in arbitrary chunks
   gives exactly the same singles as decoding the words in one call. The last compares two
   code paths (with and without carry-over between calls) over every input the fuzzer can
   build, so a bug in either path shows up as a difference even if nothing crashes.
7. **`6e688`.** nlohmann/json reports a number too large for a `double` as
   `json::out_of_range`, and `parse_config` caught only `json::parse_error`, so the exception
   escaped and terminated the program. Afterwards: the reader catches `json::exception`; the
   input went into the seed corpus; a unit test (`Config.NumberOverflowIsAnErrorNotACrash`)
   pins the behavior; and the anomaly is recorded in the SOUP list.
8. **Descriptor checks.** Between `stat(name)` and `open(name)` another process can replace
   the file, so you check one file and read another; `fstat` on the open descriptor checks the
   file you will read. `O_NONBLOCK` stops `open` from waiting forever for a FIFO's writer; the
   `max + 1` read detects a file that grew after `fstat`, and bounds the read for files whose
   size `fstat` does not describe.
9. **GCC passes, Clang fails.** The hardening was coming from the distribution's GCC defaults,
   not from the build. Clang from the same distribution does not enable the same defaults.
   State the flags in the build (`cmake/Hardening.cmake`) and check the binary in CI for every
   compiler you ship with.
10. **`_GLIBCXX_ASSERTIONS`.** It turns on precondition checks in libstdc++: bounds checks in
    `operator[]` of `vector`, `array`, `span`, `string`, checks such as `front()` on an empty
    container, and others; a failed check aborts with a message. On the book's machine (medians of 5 interleaved
    runs, `measurements/ch07/`) the decode, energy filter, histogram and pipeline benchmarks
    showed no difference outside the VM's noise; only `std::sort` of a 4,096-single batch was 8
    to 18% slower, and a build with `_GLIBCXX_ASSERTIONS` alone reproduced it. The decision:
    keep the assertions in shipped builds, because the sort stage still has a margin of about
    11x at 10 M singles/s, record the cost in the performance budget, re-measure on the
    acquisition PC (verify on the acquisition PC), and let the performance gate catch any later
    change. Removing a safety check needs a measured reason, not a suspected one.
11. **A generated SBOM.** Because it then cannot disagree with what was built: it comes from
    the same pins the build uses. `make_sbom.py` refuses to run if a dependency in
    `cmake/Dependencies.cmake` has no entry in `KNOWN` (license, scope, purl) or has no
    version.
12. **Test frameworks in the SOUP list.** They produce the evidence (test results,
    benchmarks) on which release decisions rest; a defect in them can hide a defect in MiniDAQ.
    They are not in the shipped programs, so they need no requirements on their behavior in
    the field, only identification, pinning and awareness of their known defects.
13. **What a clean campaign shows.** That this target, built this way, ran this many inputs
    for this long, reached this coverage, and found no crash and no property violation. Not
    that the code is free of bugs, not anything about code the target does not reach, and
    nothing about properties the target does not check. Report it with those numbers and
    those limits.
