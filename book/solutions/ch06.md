## Exercise 6.1: The component diagram and the state machine

The reference diagrams are MiniDAQ's own (`docs/architecture/states.dot` and
`components.dot`); the solution directory holds copies. The chapter shows both rendered.

**Key points.**

- The state diagram has exactly twelve labeled edges, one per row of the table, plus the start
  point. Coloring the fault state is better than collapsing the four `error` edges into a note,
  because the test (and a reviewer) can then compare the drawing with the table edge by edge.
- The component diagram is drawn top to bottom, one cluster per layer, apps first. Every arrow
  points down or stays inside a layer. The dashed edge from `minidaq_ctl` to `ControlServer` is a
  network connection, not a code dependency, and the test skips dashed edges for that reason.
- Granularity: one node per thing a design review talks about, 12 to 20 nodes.

**Common wrong answers.** Arrows in the direction of data flow instead of dependency (the
detector "sends to" the service, but the detector adapter *uses* the port interface); a
"utils" node that everything points to; forgetting that the service uses the ports, not the
adapters; drawing what you intend instead of what the includes say (`tools/check_layers.py`
settles it).

**Key points.**

- 15 of the 42 pairs are legal. `calibrating` can be entered only from `configured` and left
  only by `drained` or `error`: no start, configure, stop or reset while calibrating.
- The listener runs after the state lock is released, under a second lock taken in ticket
  order. The state lock is never held while the second lock is taken, so a listener may call
  `state()`; calls never overlap and arrive in transition order.
- The concurrent test checks an invariant (the history is a chain of legal transitions and has
  one entry per successful `apply`) because the actual history cannot be predicted.

**Common wrong answers.** Calling the listener under the state mutex (deadlocks in
`ListenerMayReadTheState`); calling it after unlocking without ordering (the concurrent test
sees `from` not equal to the previous `to`); a `std::recursive_mutex` (passes the deadlock test,
but a slow listener then blocks every `state()` caller, and a listener that applies an event
recursively corrupts the order); a `switch` per state that forgets `calibrating` in the
`error` cases.

## Exercise 6.3: Three ADRs and a linter

```{.python include="exercises/ch06/e3_adrs/solution/adr_lint.py" snippet="lint_file"}
```

The reference records are MiniDAQ's ADRs 0002 (queue), 0003 (control protocol) and 0007 (file
format, proposed); `adr_location.py` points the tests at `docs/adr/`, so every CI run lints
them.

**Key points.**

- The linter splits on `##` and `###` headings and checks presence, order and non-emptiness.
  Options count as a numbered list or as `###` subsections. Numbering and "Superseded by"
  targets are directory-level checks.
- A good queue ADR cites measured numbers (Chapter 3's table: 5.2 M items/s for a mutex queue,
  387 M/s for SPSC batches of 256) and states the latency cost of batching and the fixed memory.
- A good file-format ADR is honest about what is unknown: "Proposed", with the measurements
  that would decide it (sustained write rate, crash behavior, reader support).
- A good protocol ADR says who owns the acquisition and what a disconnect does.

**Common wrong answers.** One option ("we use X"), which is a description, not a decision;
Negative consequences such as "none" or "slightly more code"; editing an accepted record when
the decision changes instead of superseding it.


**Key points.**

- Consume by advancing an index; compact (drop the consumed prefix) in `feed()` only when it is
  at least half the buffer, so each byte moves a constant number of times on average.
- Check the announced length before waiting for the payload: a hostile 0xFFFFFFFF must fail at
  once, not after buffering 4 GiB.
- Failure is permanent, because after a bad length no byte can be trusted to start a header.

**Measured.** The solution passes the linearity test in about 0.1 s in the `release` build. A
version that erases each frame from the front took 2.5 s for 200,000 frames at `-O2` and was
stopped by the 30 s watchdog in the test's runs of 250,000 and 1,000,000 frames.

**Common wrong answers.** `vector::erase` per frame (quadratic); reading the length with a
`reinterpret_cast` of the buffer (alignment, aliasing and byte order); allocating the payload
before checking the limit; resynchronizing after a bad length by scanning for something that
looks like a header.

## Exercise 6.5: Fault injection through the detector port

```{.cpp include="exercises/ch06/e5_fault_injection/solution/faulty_detector.cpp" snippet="read"}
```

**Key points.**

- The adapter is a decorator: a `DetectorPort` that owns another one. The service cannot tell
  the difference, so the production fault handling is what the test exercises.
- Only the link-down flag is shared between threads (`read()` on the source thread, `fault()` on
  the monitor), so it is an atomic. The counts the test reads live in a `shared_ptr`, because
  the service destroys the detector when the run is reset.
- The stall test passes only because latency is measured from when words were due (Chapter 4).
  Measured from read time, the 60 ms stall would be invisible in the latency, and only the
  elapsed time of the run would hint at it.
- Reordering must hold words back for longer than a batch; a shorter delay is repaired by the
  per-batch sort and is not detected. That is a property of the Chapter 3 sorter that Chapter
  10's sorter must handle deliberately.

**Common wrong answers.** A plain `bool` for the link-down flag (a data race, which TSan
reports); corrupting words by flipping a random bit (sometimes still a valid crystal, so the
filtered count does not match); stalling with `sleep_for` inside `read()` (it also blocks the
source thread's stop check, so a stop during a stall waits for it).

## Check yourself: model answers

1. **Testing the sorter without hardware.** Simulate the detector port and nothing else: a
   `DetectorPort` whose `read()` returns packed words chosen by the test (time order, gaps,
   pairs within and outside the window, words older than ones already sent). Assert on the
   service's state and status: counters conserved across stages, the expected number of
   coincidences, and a fault with the out-of-order message when time goes backwards across
   batches. Everything else, pipeline, sort, pairing and fault handling, is the real code.
2. **A client disconnects.** Nothing happens to the acquisition: the service owns the run, the
   server records the disconnect in the audit trail, and any client can see and stop the run. It
   is a design decision because a dropped connection is usually harmless (a sleeping laptop,
   a network hiccup) and stopping a patient scan for it is worse. If a risk analysis requires
   that an unattended run stops, implement a lease: the client sends a heartbeat, the service
   stops the run when the lease expires, and the lease length is configured, audited and tested.
3. **The dependency rule.** Source dependencies point from details (devices, sockets, files,
   apps) towards policy (the service, the state machine). Dependency inversion turns the arrow
   between the service and the detector around: the service defines `DetectorPort` and the
   detector adapter depends on it, instead of the service depending on a concrete detector.
   Tests can then supply scripted or fault-injecting detectors.
4. **No reset from running; fault left only by reset.** A reset from running would discard the
   batches in flight without counting them and end a run without the drain that makes the counts
   conserved. Leaving fault by `start` or `configure` would let a script overwrite the evidence
   of a fault without anyone acknowledging it.
5. **Listener under the lock.** Thread A applies an event, holds the state mutex and calls the
   listener; the listener calls `state()`, which needs the same (non-recursive) mutex: A
   deadlocks on itself. With a second mutex for ordering taken while the state mutex is held,
   and a listener that takes the state mutex, two threads can each hold one mutex and wait for
   the other. Tickets avoid both: the ticket is taken under the state mutex, the state mutex is
   released, and the listener runs under the ordering mutex only, in ticket order.
6. **Unknown keys.** In a configuration file they are errors because a person wrote the file,
   and an ignored misspelled key silently becomes a default (wrong settings for a whole
   acquisition). In a control request they are ignored because programs wrote it, and ignoring
   lets a newer client talk to an older server (independent upgrades) without changing the
   meaning of fields the server knows.
7. **Schema 1.1 read by a 1.0 program.** It refuses the file with "written for a newer MiniDAQ
   (1.1 > 1.0)". The newer file may depend on a key the old program does not know, and ignoring
   it would change the acquisition silently. A change that removes or renames a key, changes a
   unit or a meaning, or makes an optional key required needs 2.0.
8. **The cumulative histogram** has a single writer, the stage; a reset from another thread
   races with `record()` and can lose or tear counts. `status` reports the last second from
   two snapshots of the bucket counts taken by the monitor thread one interval apart, subtracted
   (`interval_summary`).
9. **The audit trail** records who (peer address), what (command and full effective
   configuration), when (UTC with milliseconds), the result including rejections, every state
   transition and fault, and connections and disconnections. Before it could be a regulated
   record it still needs authenticated users instead of addresses, protection against
   modification (permissions, signing or a write-once store), retention and backup rules, and
   time synchronization of the PC (assumption: confirm with team which of these your company's QMS
   requires).
10. **ADR sections:** title with number, date, status, Context, Options, Decision, Consequences
    (Positive and Negative). Options and Negative consequences carry the most value: they record
    what was rejected and what the decision costs. ADR 0007 is "Proposed" because the file
    format has not been measured yet (Chapter 12); recording the open question keeps it from
    being decided by accident.
11. **Segregation.** The description claims build-time separation (the core library cannot
    include the control plane or JSON, checked by the include test) and process separation of
    clients. It does not claim that a failure in the control plane cannot affect the pipeline,
    since both share an address space. In a regulated product a segregation claim can be part of
    a risk control and must then be justified and verified; claiming more than the design
    delivers would make the risk file wrong.
12. **gRPC vs NDJSON over TCP.** On one PC with local clients, NDJSON has no extra dependencies
    (less SOUP), is readable in logs and with `nc`, and its weaknesses (no generated types, no
    built-in security, polled telemetry) matter little. For a console on another computer,
    gRPC's TLS and authentication, deadlines, streaming and typed, generated clients become
    decisive, and its dependency cost is easier to justify.
