## Exercise 33.1: Counts that add up

```{.cpp include="exercises/ch33/e1_counts_add_up/solution/accounting.cpp"}
```

**Key points.**

- Write every equation as two sums compared, never as a difference of unsigned counters, which
  wraps and can hide the error it should show.
- Count the written coincidences by kind. A total would let a delayed coincidence written as a
  prompt pass.
- Keep the names of the equations fixed and in a fixed order, so that two reports can be compared.
- `multiple_windows` appears only in an inequality: a multiple holds any number of singles from
  three up, so no sum of the other counters fixes it. Counting the singles in multiples by window
  size, or the pairs considered in multiples, would make it exact.
- Under `take_all_goods` the pair windows equation becomes
  `prompts + geometry_rejected = pair_windows + pairs_in_multiples`, which needs a new counter.

**Common wrong answers.** `s.pair_windows - s.geometry_rejected != s.prompts`, which is right
until a counter is smaller than it should be, and then wraps to a huge value that may even compare
equal by chance after another error. Checking the written coincidences by their total only.
Checking `multiple_windows` with an equation the sorter does not satisfy, such as
`3 multiple_windows == singles_in_multiples`, which holds only when every multiple has three
singles and fails on the sorter's own counters at high rates.

## Exercise 33.2: An acceptance verdict that cannot be fooled

```{.python include="exercises/ch33/e2_acceptance_verdict/solution/verdict.py"}
```

**Key points.**

- Read the evidence inside a `try` that catches only what means "cannot be read": a missing file,
  an I/O or decoding error, invalid JSON. A bug in the specification (a criterion without a
  `limit`) must still stop the run.
- Check freshness (the commit, the dirty flag) before the target: evidence of another commit says
  nothing about the candidate.
- Refuse a value that is a `bool` (a subclass of `int`) or not finite before comparing, and compare
  in the positive form (`value >= limit`), which is false for NaN.
- Accept only a non-empty set of verdicts that are all PASS.

**Common wrong answers.** `except Exception`, which turns a bug in the tool into a MISSING verdict
nobody investigates. `startswith` in one direction only, which fails when the evidence holds the
full hash and the candidate is the short one. `"FAIL" not in verdicts`, the starter's line, which
accepts a candidate with no soak at all. `all(v == "PASS" for v in verdicts)` alone, which is true
for an empty specification.

## Exercise 33.3: A requirements freeze that sees every change, and only changes

```{.python include="exercises/ch33/e3_requirements_freeze/solution/freeze.py"}
```

**Key points.**

- Normalize white space inside each cell and join the cells with a separator, then hash. Rewrapping
  or padding a table is not a change of a requirement; a word, a number, the item or the method is.
- Report removed requirements as well as added and changed ones: deleting a row is the quietest way
  to drop a verified obligation.
- Count only change requests that are approved or implemented.
- A request that names a requirement by saying it does not change covers it under this rule. A
  structured table of the changes in each request, or the digest each request expects after its
  change, closes the hole without parsing prose.

**Common wrong answers.** Hashing the whole line, which makes every reformatting a change and
teaches people to retake the baseline without reading. Normalizing by removing all spaces, which
makes "at least 20 M" and "atleast20M" equal but also merges words that should differ. Letting the
check write a new baseline when it fails: the freeze then records whatever was written last.
