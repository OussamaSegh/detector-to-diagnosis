# Exercise 7.2: notes on the solution

## Part 1

The solution's fuzz target, run against the starter's `packet.cpp` (Clang 18,
`-fsanitize=fuzzer,address,undefined`, seeds from `tests/corpus`), found a
crash in each of six 60-second runs, every time within the first 30
executions. After each crash the run was restarted with the crash input
removed from the corpus, so the next run had to find a different input. The
six inputs are in `tests/crashers/`:

| Input | What the header claimed | What happened |
|---|---|---|
| `01-crash-037909c5` | reserved field 96 | Not a memory error: the round-trip property failed, because `encode_packet` writes 0 there. The starter accepted a header that the format reserves. |
| `02-crash-a9b8090c` | 3 words, 23 bytes of payload | heap-buffer-overflow reading word 3 |
| `03-crash-3f6a1054` | 3 words, 6 bytes of payload | heap-buffer-overflow |
| `04-crash-2abaa8e0` | a 3-word header, 63,488 words | heap-buffer-overflow |
| `05-crash-95867f5a` | a 93-word header (744 bytes) in 28 bytes | heap-buffer-overflow at the first word |
| `06-crash-7a688f41` | 8,195 words in 24 bytes of payload | heap-buffer-overflow |

Two bugs, then, plus one gap in the specification check: the header length and
the word count were trusted, and the reserved field was not checked. A
`header_words` of 0 or 1 never crashed: it makes the words overlap the header,
which reads valid memory and returns wrong data. Only the unit test
`RejectsEveryLieInTheHeader` catches that one. The fuzzer finds what its
properties can see.

In the `debug` preset (no sanitizer), inputs 02 to 06 did not crash
the starter's unit test at all: the reads past the end returned whatever was
in memory, and the test failed only because it expected a rejection. Out-of-
bounds reads are silent without a sanitizer, which is why fuzz targets are
always built with one.

## Part 2

The decoder campaign (`fuzz_decoder`, the solution's build, Clang 18.1.3 with
ASan and UBSan, one vCPU of the book's VM, from the 4 seed inputs in
`fuzz/corpus/decoder`):

| Number | Value |
|---|---|
| Duration | 3,601 s |
| Executions | 102,580,804 |
| Executions per second | 28,486 |
| Coverage (`cov:`) | 83 at start, 101 at end; last increase after 7,755 executions |
| Features (`ft:`) | 190 at start, 460 at end; last increase after 57.9 M executions |
| Corpus | 85 inputs, 25 KB |
| Crashes, leaks, timeouts | none |

What it shows: for 102 million generated byte streams, delivered in chunks of 1
to 64 bytes, the decoder never read or wrote out of bounds, never hit undefined
behavior that UBSan checks, and never broke one of the four properties (every
word accounted for, every single valid, valid words round-trip, chunked and
one-call decoding agree).

What it does not show: anything about code that `fuzz_decoder` does not call
(the pipeline around the decoder, threads, the network); anything about
properties it does not check (for example, that the time unwrapping is right
over hours of data: a 1-hour campaign of 4 KB inputs never produces a long
stream); and, because coverage stopped at 101 edges almost immediately, the
remaining hour mostly re-tested the same paths with new values. The plateau
says the decoder is small, not that it is correct. No crash was found, so
there was nothing to fix.
